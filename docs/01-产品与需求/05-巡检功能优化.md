# k8s-ai 巡检诊断体系升级：架构文档统一与功能落地实施任务

## 一、任务背景

项目：k8s-ai

GitHub：https://github.com/markguo123/k8s-ai

当前开发分支：DEV-v4.0.0

本次任务是对 k8s-ai 现有 Kubernetes 巡检能力进行一次系统性升级。

目前项目已经完成 CLI 扫描能力向 Web 平台的继承，并实现了 Web 巡检功能，支持：

- 全集群、Namespace、单 Pod 等不同巡检范围。
- 快速体检、标准巡检、深度巡检。
- 有 LLM 和无 LLM 两种运行模式。
- Kubernetes 资源采集。
- 规则引擎检测。
- Finding / Correlation / Incident 故障关联。
- LLM 根因诊断。
- 健康评分。
- JSON / Markdown 报告生成。
- 对象存储归档。
- Web 报告管理、下载和清理。

但实际使用效果不理想，主要表现为：

1. 巡检问题定位不准确，很多时候只能发现表面异常。
2. 多个有关联的异常没有形成完整的故障链。
3. Incident 根因识别能力不足，存在症状被当作根因的情况。
4. 无 LLM 模式下缺少足够的诊断深度。
5. LLM 模式下证据利用不充分，诊断结论和处理建议有时比较泛化。
6. 报告内容组织不够专业，信息密度和可读性不足。
7. Web 端报告体验较差，主要停留在报告列表和文件下载层面。
8. 巡检过程的执行阶段、采集质量、LLM 降级等信息不够透明。

本次已经完成总体技术方向和架构决策，不需要重新开展架构方案设计。

**你的任务是：理解现有代码 → 对照本任务确定的目标架构 → 更新历史设计文档及架构图 → 按照确定的技术方案直接分阶段实施 → 完成测试和交付。**

不要重新提出另一套架构，不要反复等待用户确认已经确定的技术决策。

如果发现目标设计与现有代码存在具体冲突，应在不改变总体架构方向的前提下采用兼容性最好的实现方式，并在实施记录中说明。

# 二、已经确定的总体技术决策

以下内容是本次改造的技术基线，必须遵循。

## 2.1 保留现有扫描架构，不推倒重建

保留现有：

- ScanService。
- 两阶段资源采集体系。
- Rule Engine。
- Finding。
- Correlation。
- Incident。
- Evidence。
- Diagnosis。
- LLM Client。
- ScanResult。
- Report Generator。
- Report Archive。
- 对象存储。
- Web ScanJob 及现有任务管理机制。

不重新实现 Kubernetes 扫描器，不重新实现 LLM Runtime，不引入没有必要的新基础设施。

本次属于现有扫描诊断体系的能力升级。

## 2.2 建立完整的诊断处理流水线

目标统一架构：

Kubernetes Resource Collection
→ Rule Engine
→ Resource Relationship Analysis
→ Finding Correlation
→ Incident Aggregation
→ Deterministic Diagnosis
→ Optional LLM Enhancement
→ Diagnosis Validation
→ Unified InspectionReport
→ CLI / Web / Markdown / JSON。

具体职责：

| 模块                    | 职责                                         |
| ----------------------- | -------------------------------------------- |
| Resource Collection     | 采集 Kubernetes 资源、状态、事件、日志和配置 |
| Rule Engine             | 识别确定性异常，生成 Finding                 |
| Resource Relationship   | 根据真实资源关系建立依赖图                   |
| Correlation             | 识别异常之间的关联关系                       |
| Incident Aggregation    | 聚合故障、症状和影响对象                     |
| Deterministic Diagnosis | 根据状态机、事件、资源关系和证据定位根因     |
| LLM Enhancement         | 对复杂问题进行上下文分析和诊断增强           |
| Diagnosis Validation    | 校验诊断结论与证据之间的一致性               |
| InspectionReport        | 统一输出结构化巡检报告                       |

特别强调：

Correlation 负责发现异常之间的关联，不负责直接宣布根因。

Incident 负责组织故障及其成员。

Deterministic Diagnosis 负责基于明确规则和证据推断根因。

LLM 负责复杂场景增强分析，不是事实来源。

Diagnosis Validation 负责确保最终结论有证据支持。

## 2.3 建立确定性诊断引擎

这是本次核心改造之一。

新增或完善 Deterministic Diagnosis 层。

该模块位于 Incident Aggregation 之后、LLM 诊断之前。

主要目标：

即使没有配置 LLM，k8s-ai 也能够完成有实际价值的 Kubernetes 故障诊断，而不仅仅输出 Finding 列表。

确定性诊断依赖：

- Kubernetes 资源状态。
- OwnerReference。
- UID。
- Selector。
- ResourceVersion（在需要判断采集时序时使用）。
- Kubernetes Events。
- Pod 状态和 Container Status。
- Workload 状态。
- PVC / PV / StorageClass 关系。
- Service / EndpointSlice 关系。
- Node 状态及资源压力。
- 已采集的关键日志。
- 现有 Finding 和 Evidence。

设计要求：

1. 诊断器可注册、可测试。
2. 每个诊断器有明确的输入证据。
3. 有明确触发条件和排除条件。
4. 输出结构化诊断结果。
5. 可以说明判断依据。
6. 支持无法确定根因时输出 unknown。
7. 不得通过缺少证据的推测生成 confirmed 根因。
8. 诊断器之间职责清晰，避免重复判断。
9. 诊断结果能够被 LLM 进一步增强。
10. 不影响现有 CLI 扫描结果。

优先完善以下场景：

- CrashLoopBackOff。
- ImagePullBackOff / ErrImagePull。
- Pending / FailedScheduling。
- FailedMount / FailedAttachVolume。
- Node NotReady。
- Node MemoryPressure / DiskPressure / PIDPressure。
- Deployment 副本不足。
- ReplicaSet 创建失败。
- StatefulSet 副本异常。
- DaemonSet 节点覆盖异常。
- Service 无 Endpoint。
- EndpointSlice 与 Pod Ready 状态不一致。
- Ingress 后端不可用。
- PVC Pending。
- PV Released / Failed。
- StorageClass 配置异常。
- HPA 无法扩缩容。
- PDB 阻断驱逐。
- DNS / CoreDNS 异常。
- NetworkPolicy 潜在通信阻断。

不要为了增加诊断器数量而重复实现已有规则。

优先解决现有真实问题，并为新增诊断器建立单元测试。

# 三、完善 Kubernetes 资源关系与故障因果分析

这是提升根因定位准确性的关键。

## 3.1 建立真实 Kubernetes 资源关系

重点完善：

- Pod → ReplicaSet → Deployment。
- Pod → StatefulSet。
- Pod → DaemonSet。
- Pod → PVC → PV → StorageClass。
- Pod → Node。
- Pod → ServiceAccount。
- Service → EndpointSlice → Pod。
- Ingress → Service。
- HPA → ScaleTarget。
- PDB → Workload。
- Event → 对应资源 UID。

关系必须来自真实 Kubernetes 对象：

- OwnerReference。
- UID。
- Label Selector。
- Spec 中的引用字段。
- Status 中的关联信息。

禁止仅通过名称相似度建立因果关系。

资源关系数据必须可以追溯来源。

## 3.2 增加故障因果关系

需要区分：

- Resource Relationship：资源依赖关系。
- Correlation：异常之间的关联。
- Causal Relationship：故障之间的因果关系。

例如：

PVC Pending
→ Pod FailedMount
→ Deployment AvailableReplicas 不足
→ Service 没有可用 Endpoint
→ Ingress 后端不可用。

这是一条可能的故障传播链，但每个节点都必须有真实证据支持。

不能仅因为它们处于同一个 Namespace 就认定存在因果关系。

因果关系应具备：

- source。
- target。
- relationType。
- evidence：跨 Finding 时统一 `<findingID>#<evidenceID>`。
- confidence。
- diagnosticRule。

允许存在多条独立故障链。单条 Incident 内从根信号生长故障树，每个症状最多保留一条最能解释
它的入边；关联层候选只能是 `probable`，确定性诊断器才能在证据充分时写 `confirmed`。

## 3.3 优化 Incident 结构

保留当前 Finding → Correlation → Incident 的总体设计。

明确以下概念：

- Root Cause：根因。
- Symptom：症状。
- Impact：影响。
- Independent Finding：独立异常。
- Unknown Cause：无法确定根因。

评估并扩展现有 Incident 模型，建议包含：

- rootCauseStatus：confirmed / probable / unknown。
- rootCauseConfidence。
- causalEvidence。
- impactChain。
- diagnosticMethod：rule / llm / hybrid。

字段命名应遵循当前项目风格，优先复用现有字段。

不能为了输出好看强行将所有异常合并成一个 Incident。

一个 Incident 只保留一个主结论（明确根因，或合法的 `unknown`），其他可能方向写入
`alternativeCauses`。最终合并与校验后的 `Diagnosis` 是根因唯一事实源，Incident 上的根因字段
只是其报告投影。

可信度必须具有明确计算或判定依据，不能随意生成看似精确的百分比。

# 四、LLM 诊断增强

保留当前 LLM Client、Provider、Model 配置及调用机制。

不重新实现模型调用框架。

## 4.1 调整 LLM 在诊断链路中的职责

LLM 输入应包含：

1. Incident 根因候选 Finding。
2. Incident 所有成员。
3. Kubernetes 资源关系。
4. 相关 Events。
5. 关键日志片段。
6. 资源实际运行状态。
7. 资源配置。
8. 确定性诊断结果。
9. Evidence 来源。
10. Evidence 采集时间。
11. 采集失败和证据缺失情况。

LLM 的目标是：

- 交叉验证已有诊断。
- 分析复杂故障。
- 识别多个可能根因。
- 分析故障影响。
- 补充下一步排查步骤。
- 提供有针对性的处理建议。

不能简单把全部资源 JSON 和所有日志直接塞进 Prompt。

需要控制上下文大小，优先传入与 Incident 直接相关的证据。

## 4.2 统一 LLM 输出

LLM 结果应结构化：

- symptom。
- rootCause。
- rootCauseStatus。
- confidence。
- impact。
- alternativeCauses。
- evidenceRefs。
- investigationSteps。
- remediationSuggestions。
- verificationSteps。

实际字段以项目已有 Schema 为基础增量完善。

严格要求：

- 所有事实必须有 Evidence 支持。
- 不允许编造资源状态。
- 不允许编造 Events 和 Logs。
- 不允许编造资源名称。
- 无法判断时明确 unknown。
- 区分事实、推测和建议。
- 不输出与故障无关的通用修复建议。
- 修复命令必须匹配实际资源和 Namespace。
- 修改类命令只能作为建议，不得执行。
- 保留现有输出 Schema 校验。

## 4.3 增加诊断结果校验

LLM 输出后执行校验：

- Evidence ID 是否存在。
- 跨 Finding 的 Evidence 引用是否使用 `<findingID>#<evidenceID>`，且属于当前故障链的真实证据。
- 资源是否真实存在于采集快照。
- 根因是否有对应证据。
- 建议是否与故障类型匹配。
- 命令是否存在明显参数错误。
- 是否出现不支持的资源状态。

校验失败时：

- 不得把不可信结论当成 confirmed。
- 保留确定性诊断结果。
- 记录 LLM 诊断失败原因。
- 进入明确的降级状态。

LLM 不得覆盖已有事实证据。

# 五、无 LLM 与有 LLM 的统一运行模式

无 LLM 模式不是低质量模式。

两种模式必须共享：

- Resource Collection。
- Rule Engine。
- Resource Relationship。
- Correlation。
- Incident Aggregation。
- Deterministic Diagnosis。
- Evidence。
- InspectionReport。

区别只在于是否增加 LLM Enhancement。

### 无 LLM

规则检测 + 资源关系分析 + 故障聚合 + 确定性诊断 + 证据 + 排查建议。

对可以明确判断的问题输出确定性结论。

对无法明确判断的问题输出可能原因和排查步骤。

### 有 LLM

在上述基础上增加：

LLM Enhancement + Diagnosis Validation。

不得让 LLM 成为所有问题的唯一诊断来源。

### 降级状态必须细分

至少区分：

- not_configured。
- request_failed。
- timeout。
- invalid_response。
- schema_validation_failed。
- evidence_validation_failed。
- partial_success。

不能将所有问题统一标记为 degraded。

报告中必须明确：

- 是否使用 LLM。
- 是否调用成功。
- 哪些 Incident 得到了 LLM 增强。
- 哪些 Incident 使用纯规则诊断。
- 降级原因。

# 六、巡检档位优化

检查现有 quick / standard / deep 的真实行为。

目标定义如下：

## 快速体检

- 轻量资源采集。
- 核心 Kubernetes 状态。
- 必要 Events。
- Rule Engine。
- 资源关系分析。
- 确定性诊断。
- 基础风险报告。

默认不采集大量日志。

## 标准巡检

- 完整资源采集。
- 完整资源关系。
- Events。
- Finding / Incident。
- 确定性诊断。
- 对异常资源按需采集关键证据。
- LLM 可选增强。

## 深度巡检

- 标准巡检全部能力。
- 扩大日志时间窗口。
- 采集更多故障关联资源证据。
- 更深入的跨资源分析。
- LLM 可选增强。

日志采集必须：

- 以异常资源和故障链为中心。
- 有时间窗口。
- 有并发限制。
- 有最大日志大小。
- 有超时控制。
- 有脱敏。
- 记录采集失败。
- 避免无差别读取所有 Pod。

前后端巡检档位说明必须和后端真实执行行为保持一致。

# 七、统一 InspectionReport 报告模型

这是本次改造的重要数据契约。

优先扩展现有 ScanResult，避免引入完全重复的结构。

在其基础上形成统一、版本化的 InspectionReport。

报告至少包含以下信息。

## 7.1 Overview

- 巡检范围。
- 集群。
- Namespace。
- 开始时间。
- 结束时间。
- 耗时。
- 健康评分。
- Finding 数量。
- 风险分布。

## 7.2 Conclusion

- 总体巡检结论。
- 主要风险。
- 重点故障。
- 优先处理建议。

## 7.3 Incidents

- 故障名称。
- 严重程度。
- 根因状态。
- 根因判断。
- 可信度。
- 影响范围。
- 关联 Finding。
- 故障传播链。
- 证据引用。
- 处理建议。

Incident 上的根因字段用于报告兼容与展示，其值来自最终 `Diagnosis` 的投影；最终 `Diagnosis`
才是根因、可信度、证据缺口与处置建议的唯一事实源。

## 7.4 Findings

- 规则 ID。
- 资源信息。
- 风险等级。
- 异常现象。
- 检测时间。
- Evidence。
- 诊断结论。

## 7.5 Remediation

- 排查步骤。
- 修复建议。
- 验证步骤。
- kubectl 命令。
- 命令风险等级。

## 7.6 ResourceStatistics

- Node。
- Namespace。
- Pod。
- Deployment。
- StatefulSet。
- DaemonSet。
- Service。
- Storage。
- Network。
- 其他当前已经采集的资源。

## 7.7 CollectionQuality

- 计划采集资源数。
- 成功采集资源数。
- 失败采集资源数。
- 跳过数量。
- 未覆盖资源。
- 采集错误。
- 资源采集完整性。

## 7.8 DiagnosisSummary

- 规则诊断数量。
- 确定性诊断数量。
- LLM 调用次数。
- LLM 成功次数。
- LLM 失败次数。
- LLM 降级次数。
- 实际诊断模式。
- 降级原因。

## 7.9 History

- 新增问题。
- 持续问题。
- 已恢复问题。
- 健康评分变化。

要求：

1. JSON 作为结构化事实来源。
2. Markdown 是 JSON 的一种渲染结果。
3. Web 是同一报告模型的交互式展示。
4. CLI 和 Web 使用同一份诊断结果。
5. 不允许分别维护多套诊断逻辑。
6. 报告 Schema 必须有版本号。
7. 兼容历史 JSON 报告。
8. 不破坏对象存储归档和下载。
9. 不向前端暴露对象存储内部 blob_key。
10. 保留现有报告权限及审计机制。

### 健康评分约束

健康评分必须考虑采集完整性。

如果关键资源没有成功采集，必须显示数据不完整或评分可信度受限。

不能因为没有发现问题就直接给出无条件的 100 分。

必须检查现有评分逻辑是否存在此类误导。

## 8.3 页面展示要求

报告顶部：

- 巡检时间。

故障诊断：

- 根因。
- 根因可信度及状态。
- 影响链。
- 关联资源。
- 默认折叠的关键证据、传播路径与派生症状。
- 处置框内的排查步骤、修复说明、按序修复步骤、验证步骤与风险边界。

展示要求：

- 业务故障链与安全/治理建议分开计数和展示，不得把缺少 default-deny 等建议混成业务故障。
- 根因、派生症状、业务影响由后端 `Finding.role` 判定，前端不得按标题猜。
- Evidence、传播路径、派生症状与待排除项默认折叠；完整 Finding/Evidence 仍保留在附录。
- 修复说明按 Markdown 渲染；命令使用代码块、复制按钮和文字风险标识，不允许只给命令。
- 新生成的证据引用统一 `FindingID#EID`，旧裸 `EID` 只做读取兼容。

证据详情：

# 十、诊断质量测试体系

本次必须建立故障场景回归测试。

至少覆盖：

1. CrashLoopBackOff。
2. ImagePullBackOff。
3. Pending。
4. FailedScheduling。
5. FailedMount。
6. Node NotReady。
7. Node Pressure。
8. Deployment 副本不足。
9. StatefulSet 异常。
10. Service 无 Endpoint。
11. EndpointSlice 异常。
12. Ingress 后端异常。
13. PVC Pending。
14. PV 异常。
15. StorageClass 异常。
16. HPA 异常。
17. PDB 阻断驱逐。
18. DNS 异常。
19. NetworkPolicy 潜在通信问题。
20. 容器高重启但退出码为 0（正常结束后被再次拉起，不得误报崩溃）。
21. RBAC Binding 通配风险与绑定列表采集缺失。

每个场景覆盖：

- 正常情况。
- 单一故障。
- 多个关联故障。
- 证据缺失。
- 采集失败。
- 容易误判的边界条件。

至少测试：

- 无 LLM。
- LLM 正常。
- LLM 超时。
- LLM 返回无效结构。
- LLM 诊断失败后降级。

建立质量指标：

- Finding Precision。
- Finding Recall。
- Root Cause Accuracy。
- Incident Correlation Accuracy。
- Evidence Support Rate。
- Remediation Relevance。
- No-LLM Diagnostic Coverage。

必须使用可重复的测试数据，不能依赖生产集群。

对于无法用自动化测试验证的场景，建立明确的测试夹具和人工验收标准。
