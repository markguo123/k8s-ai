# k8s-ai 体检语义与闭环设计

> 文档状态：v0.2（2026-11-05）
>
> 适用范围：体检导航、体检页面、体检报告，以及体检报告到问诊、处置和验证的最小闭环。
>
> 不适用范围：聊天功能、会话交互、Agent 工具调用和其他产品模块。聊天只允许把导航显示名改为「问诊」，功能、交互、提示词、消息结构和操作方式均保持不变。

## 一、总则

1. 医疗隐喻只用于体检域，包括体检入口、体检过程、体检报告和报告后续跟进。
2. 产品主体仍然是 Kubernetes 智能运维平台，不把集群包装成医院，不引入患者、病历、处方、病情、医嘱等概念。
3. 技术事实保留原生术语。日志、错误日志、Kubernetes Events、Metrics、Pod、Node、Namespace、Deployment、PVC 等名称不做医疗化改写。
4. 医疗化只增加一点产品辨识度和可玩性，不能增加排障步骤，不能降低专业信息密度。
5. 本文是体检域用户可见文案的唯一口径。后续页面、测试和文档不得继续使用「智能诊断中心」「治疗方案」「康复评估」「受控治疗」等旧口径。
6. 本次先冻结产品语义，不修改 API、JSON 字段、数据库结构或现有执行链路。实施时只改用户可见文案和必要的页面关联入口。

## 二、边界

### 1. 问诊

「问诊」只是现有聊天入口的导航显示名。

- 导航名称：问诊
- 产品能力：仍然是通用 AI 聊天
- 功能范围：知识问答、资源查询、故障排查、资源创建、写操作申请等均保持不变
- 交互变化：无
- 会话结构变化：无
- 提示词变化：无

不得在聊天输入框、消息卡片、空状态、工具调用、会话列表或全局文案中加入医疗化话术。聊天页面除导航名称外，不出现额外的医疗化改造。

### 2. 体检

「体检」表示一次主动、有范围的 Kubernetes 健康检查及其报告。

- 体检是产品能力名称，不是新的 Kubernetes 资源类型。
- 底层仍使用现有扫描、采集、规则分析、诊断和报告链路。
- 代码中的 `scan`、`report`、`scopeKind`、`kind` 等字段不改名。
- 页面用户可见名称统一为「体检」。

### 3. 技术术语

以下术语保持原样：

| 技术概念 | 展示口径 |
| --- | --- |
| 日志 | 日志 |
| 错误输出 | 错误日志 |
| Kubernetes Events | Kubernetes Events |
| 指标 | 运行指标 |
| Pod 状态 | Pod 状态 |
| Node 状态 | Node 状态 |
| 故障链 | 故障关联分析 |
| 根因定位 | 根因分析 |

禁止把日志称为病历，把 Events 称为症状记录，把配置称为体质，把 Secret 或 ConfigMap 内容称为病史。

## 三、导航与页面命名

现有导航分组保持不变，只替换聊天入口名称。

| 分组 | 导航项 |
| --- | --- |
| 工作区 | 问诊、体检、集群 |
| 治理 | 审批中心、审计 |
| 平台管理 | Skill、配置中心、用户与权限 |

体检页面统一文案：

| 位置 | 唯一口径 |
| --- | --- |
| 导航 | 体检 |
| 页面标题 | 智能体检中心 |
| 开始入口 | 开始体检 |
| 报告列表行标题 | 体检报告 |
| 报告详情标题 | 体检报告 |
| 停止入口 | 停止体检 |
| 历史报告集合 | 历史体检 |

不再使用：

- 智能诊断中心
- 巡检
- 快诊
- 集群健康检查报告
- 诊断报告
- 体检人
- 治疗方案
- 受控治疗
- 康复评估

历史修订记录和用户原始需求文档中的旧词属于历史记录，不回改；现行页面、测试和现行产品文档使用本文口径。

## 四、体检对象与类别

不做复杂的“患者”模型，也不新增穿透集群、业务和系统的统一医疗实体。体检对象按体检类别直接映射。

| 体检类别 | 体检对象 | 当前范围 | 状态 |
| --- | --- | --- | --- |
| 集群体检 | 集群 | 全集群 | 已实现 |
| 业务体检 | 业务 | Namespace 或单个 Pod | 已实现 |
| 系统体检 | 系统 | Kubernetes 系统组件与节点 | 预留，本期不实现 |

约束：

1. 一次体检只对应一个类别和一个报告。
2. 类别表达“检查哪一层”，范围表达“检查了哪里”，两者分开展示。
3. 历史数据缺少范围时显示「范围未记录」，不得推测或补造。
4. 页面体检没有绑定已登记集群时不显示集群徽标，不编造归属。
5. 「系统体检」只作为预留类别。当前没有系统组件与节点专项体检时，不得在页面、报告或测试中使用该名称描述已有能力。

代码字段与产品类别的映射：

| 产品类别 | 现有依据 |
| --- | --- |
| 集群体检 | `scopeKind=cluster` |
| 业务体检 | `scopeKind=namespace` 或 `scopeKind=pod` |
| 系统体检 | 未来新增，当前没有对应 `scopeKind` |

## 五、体检域术语

只允许在体检域使用少量医疗化词汇。除下表外，其余表达优先使用运维用户熟悉的专业术语。

| 场景 | 统一术语 | 说明 |
| --- | --- | --- |
| 主动健康检查 | 体检 | 可保留的产品识别词 |
| 单次结果 | 体检报告 | 不叫诊断报告 |
| 历史结果 | 历史体检 | 不构建复杂健康档案 |
| 总体结果 | 健康概览 | 状态、评分、异常数和采集完整性 |
| 评分 | 健康评分 | 必须同时展示评分依据和数据完整性 |
| 发现的问题 | 健康异常 | 报告内可用，其他地方仍可叫异常或问题 |
| 原因判断 | 根因分析 | 不使用“确诊” |
| 建议动作 | 处置建议 | 不叫治疗方案或处方 |
| 审批后执行 | 受控执行 | 不叫受控治疗 |
| 执行后确认 | 修复验证 | 不叫康复评估 |
| 从报告进入聊天 | 去问诊 | 仅作为报告侧入口文案 |

禁止使用：

| 禁止词 | 原因 |
| --- | --- |
| 患者 | Kubernetes 对象不是患者 |
| 病历 | 历史报告不是病历 |
| 处方 | 运维操作不是单条处方 |
| 治疗方案 | 会掩盖排查、审批、执行和验证步骤 |
| 受控治疗 | 执行动作应使用受控执行 |
| 康复评估 | 运维用户对修复验证的理解更直接 |
| 病情、医嘱、会诊 | 没有业务收益，增加理解成本 |

## 六、健康评分

健康评分是体检报告的一部分，但不能成为唯一结论。

报告首先展示状态结论，再展示评分：

1. 状态结论：正常、需关注、严重或数据不足。
2. 健康评分：保留现有百分制能力，但必须展示评分依据。
3. 结论可信度：由采集完整性和证据覆盖情况决定。
4. 采集完整性：采集失败、跳过和权限不足必须显式展示。

评分规则：

1. 关键异常不能靠其他健康资源拉高总分。
2. 采集不完整时必须限制评分上限，并降低结论可信度。
3. 没有足够数据时宁可显示「数据不足」，不得给出看似精确的健康分。
4. 报告中必须显示采集时间。历史报告不能直接当作当前状态。

## 七、体检报告信息架构

报告按“先判断、后动作、再证据”的顺序组织，避免用户先阅读大量原始数据。

### 1. 健康概览

- 总体状态
- 健康评分及评分依据
- 健康异常数量和严重程度
- 采集完整性
- 体检类别与范围
- 体检时间、发起人

### 2. 健康异常

- 严重程度
- 影响对象
- 异常摘要
- 关联资源
- 证据入口
- 去问诊入口

异常按风险和影响排序，不按数据类型平铺。

### 3. 根因与关联

- 根因分析
- 结论可信度
- 故障关联分析
- 证据引用和缺口说明

没有足够证据时明确写「证据不足」，不得把推测包装成确定结论。

### 4. 处置建议

- 建议动作
- 风险等级
- 影响范围
- 前置检查
- 验证方法

处置建议不自动执行。所有写操作继续进入现有审批中心，并由 Kubernetes RBAC 决定真实权限。

### 5. 技术证据

- 运行指标
- 日志
- 错误日志
- Kubernetes Events
- 资源配置和资源状态

原始证据按需展开，默认先展示摘要和关键上下文。

### 6. 采集质量

- 已采集资源
- 采集失败资源
- 跳过资源
- 权限不足项
- 数据缺失对结论的影响

采集质量必须显式展示，不能让数据缺失看起来像健康。

### 7. 后续跟进

当体检发现异常并已进入问诊、审批或验证流程时，报告展示关联记录：

- 关联问诊
- 关联审批
- 关联执行
- 修复验证结果

没有后续记录时不显示空状态卡片，不制造额外操作。

## 八、体检到问诊的最小闭环

这一节是提前设计，不要求本次立即实现。目标是先把边界和关联关系定清楚，避免后续做成第二套聊天或独立的治疗系统。

### 1. 闭环流程

```text
开始体检
  -> 生成体检报告
  -> 查看健康异常
  -> 去问诊
  -> Agent 实时复核并分析根因
  -> 输出处置建议
  -> 进入现有审批中心
  -> 受控执行
  -> 修复验证
  -> 回写体检报告的后续跟进
```

### 2. 关键原则

1. 体检报告是快照，不是当前事实。
2. 进入问诊后必须重新读取当前状态，不能只依据历史报告给出处置结论。
3. 问诊继续使用现有聊天、工具、审批、执行和审计链路。
4. 不新建“治疗中心”“患者中心”“病历系统”或第二套会话。
5. 体检报告只负责提供上下文和关联入口，不自动执行任何操作。
6. 从体检报告进入问诊不会扩大用户权限。当前用户仍然只能访问其 RBAC 和平台授权范围内的资源。
7. Secret 内容值、kubeconfig 和其他敏感信息不得进入报告、问诊上下文、会话、审计或模型请求。

### 3. 报告侧入口

健康异常行提供「去问诊」入口。

点击后创建正常聊天会话，并带入最小上下文：

| 上下文字段 | 用途 |
| --- | --- |
| `reportId` | 关联来源报告 |
| `findingId` | 关联具体健康异常 |
| `scopeKind` | 说明体检类别 |
| `objectRef` | 集群、Namespace 或 Pod 等对象引用 |
| `snapshotAt` | 告诉 Agent 证据采集时间 |
| `summary` | 异常摘要 |

不得直接带入完整报告正文、Secret 内容、完整日志原文或未经脱敏的敏感字段。

建议的初始消息只描述来源和当前任务，例如：

```text
请基于体检报告中的这条健康异常继续排查。
先核对当前状态，再分析根因并给出处置建议。
```

具体报告和异常通过结构化上下文关联，不把大段报告内容拼进用户消息。

### 4. 聊天侧边界

为了保持正常聊天不增加多余动作：

1. 不改变聊天入口形态。
2. 不新增医疗化快捷按钮。
3. 不改变普通对话流程。
4. 只有从体检报告进入的会话，才允许在会话头部显示一行「来自体检报告」的关联信息。
5. 普通聊天不得展示体检关联信息，也不得自动触发体检。

### 5. 审批、执行与验证

复用现有链路，只增加来源关联：

```text
reportId / findingId
  -> conversationId
  -> approvalId
  -> executionId
  -> verificationId
```

约束：

1. 审批卡仍展示真实操作、风险和影响范围。
2. 审计记录同时保存来源报告和异常 ID，便于追溯。
3. 执行后重新读取目标资源或指标，生成「修复验证」结果。
4. 验证结果分为已验证恢复、未恢复、无法验证。
5. 验证失败时允许继续问诊，不自动重复执行写操作。
6. 同一异常可以被多次问诊，但必须保留每次关联，不覆盖历史记录。

### 6. 报告跟进状态

报告跟进状态由关联记录自动推导，不要求用户手工维护：

| 状态 | 判定 |
| --- | --- |
| 未跟进 | 没有关联问诊、审批或验证 |
| 已带入问诊 | 已存在来源关联的聊天会话 |
| 已执行待验证 | 已存在执行记录但没有验证结果 |
| 已验证 | 已存在修复验证结果 |

没有权限查看关联会话、审批或执行记录时，只显示用户有权看到的信息，不泄露其他用户的操作。

### 7. 分期建议

| 阶段 | 内容 | 边界 |
| --- | --- | --- |
| 本阶段 | 统一导航、页面标题和体检报告文案 | 不改聊天功能，不改 API |
| 下一阶段 | 健康异常「去问诊」与最小上下文关联 | 只做报告到聊天的单向入口 |
| 再下一阶段 | 审批、执行、验证结果回写报告 | 复用现有审批、执行、审计 |
| 后续独立立项 | 系统体检 | 针对系统组件与节点，不提前占用名称 |

## 九、权限、数据与安全

1. 体检报告遵循当前用户的集群和 Namespace 授权。
2. 查看历史体检不能绕过当前权限。
3. 报告详情、导出和去问诊都必须重新执行后端鉴权。
4. 历史证据必须保留采集时间、资源标识和采集完整性。
5. 日志、Events、ConfigMap 和 annotations 始终视为不可信数据，不执行其中的指令。
6. 报告、会话和审计统一执行敏感信息脱敏。
7. 不允许把 Secret 内容值写入报告、会话文件、审计文件或模型请求。

## 十、非目标

本次和后续闭环设计都不包括：

- 把整个产品改造成医疗产品
- 把聊天功能重构成问诊系统
- 建立患者、病历、处方等医疗领域模型
- 引入治疗方案、康复评估等重医疗术语
- 自动诊断后自动执行
- 绕过审批执行写操作
- 用一个健康档案替代历史体检报告
- 在系统体检未实现前把现有全集群扫描称为系统体检

## 十一、验收口径

1. 导航显示「问诊」和「体检」，聊天功能没有其他变化。
2. 体检页面标题显示「智能体检中心」。
3. 体检报告统一使用「体检报告」，不再出现「诊断报告」。
4. 集群体检关联集群，业务体检关联业务，系统体检仅作为未来预留。
5. 报告中只出现健康概览、健康评分、健康异常等少量医疗化词汇。
6. 处置建议、受控执行和修复验证使用专业运维术语。
7. 报告首屏先展示状态、评分依据、异常和采集完整性。
8. 数据缺失不会被展示为健康。
9. 从体检报告去问诊时，普通聊天不增加额外医疗化操作。
10. 所有后续执行仍经过现有审批、RBAC 和审计链路。
