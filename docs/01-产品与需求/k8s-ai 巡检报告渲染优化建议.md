# k8s-ai 巡检报告渲染优化建议

> **实施状态（2026-11-04）**：核心建议已落地。当前权威口径见
> `docs/02-架构与设计/18-方案-体检诊断体系升级-四期.md` §16–§17；本文件保留原始问题分析与样例，
> 不再作为独立实现契约。已落地项包括：业务故障链优先、根因/症状/影响分层、治理建议分离、
> 关键证据与传播路径默认折叠、处置正文 Markdown + 命令代码块/风险标识、`FindingID#EID` 证据定位，
> 以及“退出码 0 不得误报为崩溃”的根因语义。

当前报告不是信息不足，而是信息组织方式还不够符合运维人员的故障排查习惯。

巡检报告不应该让运维人员从几十条 Finding 中自己寻找根因，而应该直接告诉他：

1. 当前最值得关注的问题是什么？
2. 为什么认为它是根因？
3. 有哪些证据支持这个判断？
4. 这个故障影响了哪些资源？
5. 下一步应该怎么排查？

我建议保留现有报告的整体视觉风格，重点调整内容层级，而不是重新设计页面。

## 一、当前报告存在的主要问题

| 当前表现                        | 存在的问题               | 优化方向                         |
| ------------------------------- | ------------------------ | -------------------------------- |
| 总体概览展示大量统计数据        | 数量多，但缺少故障重点   | 优先展示重点故障数量和采集完整性 |
| Finding 平铺展示                | 根因、症状、影响混在一起 | 按 Incident 组织                 |
| CrashLoopBackOff 只展示异常状态 | 没有深入分析退出原因     | 强化根因分析和关键证据           |
| 关联异常分别展示                | 同一故障重复占据视觉空间 | 归并到主故障下面                 |
| 建议以命令列表为主              | 没说明为什么执行         | 每个建议说明排查目的和预期结果   |
| 日志、Evidence 内容较多         | 影响主体阅读             | 默认展示关键证据，其他按需展开   |

特别是 CrashLoopBackOff：

Pod 处于 CrashLoopBackOff，只能证明容器启动后反复退出，不能直接证明应用配置错误、数据库连接失败或程序异常。

真正的根因应该结合：

- LastTerminationState
- ExitCode
- Reason
- Container Logs
- Events
- ConfigMap / Secret 引用关系
- 所属 Workload 状态
- 依赖服务状态

证据不足时，应明确显示“已确认异常，根因待进一步确认”。

## 二、建议的报告整体信息结构

我建议将报告组织为五个层次：

```
巡检报告
│
├── 1. 总体结论
│     ├── 健康评分
│     ├── 重点故障数量
│     ├── 风险分布
│     └── 采集完整性
│
├── 2. 重点故障诊断（核心）
│     ├── 根因分析
│     ├── 关键证据
│     ├── 关联症状
│     ├── 影响范围
│     └── 处理建议
│
├── 3. 其他异常
│     ├── 疑似故障
│     ├── 独立异常
│     └── 暂未定位异常
│
├── 4. 资源健康与采集质量
│     ├── Node / Pod / Workload
│     ├── Storage / Network
│     └── 采集失败与数据缺失
│
└── 5. 完整诊断数据
      ├── Finding
      ├── Evidence
      └── 原始 JSON
```

核心变化：重点故障诊断放在报告主体，而不是让 Finding 列表成为报告主体。

| Container Logs | 示例：启动日志存在异常 | 进一步定位应用问题 |

说明：以上传播链仅在实际采集到对应资源状态和因果证据时成立；否则应标记为待确认，不得自动推断。

建议排查步骤

1. 查看容器上一次退出状态和退出码，确认是否为应用主动退出、OOMKilled 或其他异常。
2. 查看容器上一次运行日志，定位应用启动失败的具体位置。
3. 检查启动参数、环境变量及配置引用，确认实际运行配置是否符合预期。
4. 检查应用依赖服务的连接状态，排除数据库、缓存等外部依赖异常。
5. 故障处理后验证 Pod Ready、Restart Count 和 Deployment AvailableReplicas 是否恢复。

关键排查命令

```
kubectl describe pod naviapp-backend-7597875c9d-jwsqs -n agentops

kubectl logs naviapp-backend-7597875c9d-jwsqs \
  -n agentops --previous
```

这些异常不应该与重点故障争夺首屏视觉焦点，但仍然需要保留。

| 严重程度 | 异常                         | 诊断分类                 |
| -------- | ---------------------------- | ------------------------ |
| MEDIUM   | HPA 目标资源指标异常         | 独立异常                 |

- 能关联到主 Incident 的 Finding，放入主故障详情。

- 暂未定位的异常，明确展示证据缺口。

## 五、最重要的架构建议

我认为这次报告优化，最重要的不是 Vue 页面怎么改，而是后端应该提供怎样的数据。

建议最终形成这样的数据结构：

```
InspectionReport
│
├── Overview
│
├── Conclusions
│
├── Incidents
│   ├── RootCause
│   ├── Symptoms
│   ├── Impacts
│   ├── CausalChain
│   ├── EvidenceRefs
│   ├── Diagnosis
│   └── Remediation
│
├── IndependentFindings
│
├── UnresolvedFindings
│
├── ResourceStatistics
│
├── CollectionQuality
│
└── RawFindings
```

这里有三个必须坚持的原则：

1. Finding 是异常事实，Incident 是故障组织单元。 不要把一个故障的十条 Finding 展示成十个独立问题。
2. 根因必须由证据支持。 CrashLoopBackOff 是异常状态，不等于已经找到应用崩溃的根本原因。
3. 报告渲染不能掩盖诊断不确定性。 不能为了让页面看起来更完整，就把相关性当成因果关系。

重点：我的最终建议：保留当前已经比较成熟的视觉设计，把优化重点放在后端 Incident 数据组织、根因诊断和前端分层展示。
