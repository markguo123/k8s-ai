# k8s-ai 数据模型与数据字典

- 版本：v3.0.0 → v4.0.0（四期落地跟踪）
- 日期：2026-10-23（2026-11-05 增补 canonical 证据引用、Finding 角色、故障树与最终诊断投影）
- 状态：四期企业平台落地中
- 范围：本文件是 k8s-ai 企业平台唯一的数据模型与数据字典，覆盖身份/角色、Session/Turn/Step、
  Skill、Approval、Audit、Cluster、AuthzGrant、配置与 Retention 模型

## 1. 总则

1. 所有模型定义在 `internal/model`，**不 import 任何内部包**，只依赖标准库。
2. 模型带 JSON tag，`ScanResult` 的 JSON 序列化即 1.2 趋势对比的数据契约，**字段一经发布不得随意改名**。
3. 模型分两类：**报告模型**（进入 ScanResult/JSON 报告）与**内部模型**（仅进程内使用，如 EventIndex、Rank）。
4. 生命周期统一由 `service.ScanService` 编排：创建 → 填充 → 消费 → 序列化；禁止绕过 service 直接构造完整结果。

## 3. ScanResult（报告根模型）

```go
type ScanResult struct {
    Meta             ScanMeta          `json:"meta"`
    Summary          ClusterSummary    `json:"summary"`
    Findings         []Finding         `json:"findings"`
    Diagnoses        []Diagnosis       `json:"diagnoses"`
    Incidents        []Incident        `json:"incidents,omitempty"`
    History          *HistoryDiff      `json:"history,omitempty"`
    HealthScore      HealthScore       `json:"healthScore"`
    Components       []ComponentInfo   `json:"components,omitempty"`
    CollectionErrors []CollectionError `json:"collectionErrors,omitempty"`
    LLMSummary       LLMSummary        `json:"llmSummary"`
    ReportPaths      []string          `json:"reportPaths,omitempty"`
    SchemaVersion    int               `json:"schemaVersion,omitempty"`
    Conclusion       *Conclusion       `json:"conclusion,omitempty"`
    Collection       *CollectionQuality `json:"collection,omitempty"`
    DiagnosisSummary *DiagnosisSummary `json:"diagnosisSummary,omitempty"`
    Stages           []StageRecord     `json:"stages,omitempty"`
    Statistics       []DomainHealth    `json:"statistics,omitempty"`
    Remediation      []RemediationItem `json:"remediation,omitempty"`
}

type ScanMeta struct {
    ToolVersion   string `json:"toolVersion"`
    Cluster       string `json:"cluster"`        // kubeconfig context 名
    ServerVersion string `json:"serverVersion"`
    ScanStartedAt string `json:"scanStartedAt"`
    ScanEndedAt   string `json:"scanEndedAt"`
    Duration      string `json:"duration"`
    Namespace     string `json:"namespace,omitempty"` // 空=全集群
    Pod           string `json:"pod,omitempty"`
}

type LLMSummary struct {
    Enabled        bool   `json:"enabled"`
    Calls          int    `json:"calls"`
    Failed         int    `json:"failed"`
    Degraded       int    `json:"degraded"` // 因超时/校验失败降级的 Finding 数
    TokensEstimated int   `json:"tokensEstimated"`
    Succeeded       int   `json:"succeeded,omitempty"`
    Skipped         int   `json:"skipped,omitempty"`
    Validated       int   `json:"validated,omitempty"`
    Rejected        int   `json:"rejected,omitempty"`
    Mode            string `json:"mode,omitempty"`
    StatusCounts    map[string]int `json:"statusCounts,omitempty"`

```

报告诊断与处置附加字段：

- `DiagnosisValidation.commandIssues []string`：模型命令因占位符、未知资源、交互语法或不完整参数
  被过滤的摘要；证据校验仍可通过，但页面必须提示“部分命令未收录”。
- `RemediationItem.format`：`text|command`。`text` 是完整修复方案/前置边界，按 Markdown
  渲染；`command` 才显示代码块、复制按钮与风险标签。

`ClusterSummary` 的 RBAC 计数为 `roles / roleBindings / clusterRoles /
clusterRoleBindings`。它们只代表本次报告可见范围内的采集量：命名空间与单 Pod 报告不把
集群级对象塞进汇总，零值不能被解释成集群里一定没有这些对象。

生命周期与所有权：

| 字段 | 创建者 | 填充者 | 消费者 |
|---|---|---|---|
| Meta | service | service（扫描起止时） | report、cli |
| Findings | rule | rule / evidence / scanner(Phase2 证据) | diagnosis、report |
| Diagnoses | diagnosis | diagnosis | report、cli |
| HealthScore | report | report | report、cli |
| CollectionErrors | scanner | scanner / diagnosis | report |
| LLMSummary | service | diagnosis 汇总 | report |

要点：
- **快照不进 LLM、不进报告**：报告只展示摘要（资源汇总节），原始快照仅进程内使用。
- `Annotations`、`CollectedLog` 在进入快照前已脱敏（ADR-006）。
- 大集群内存控制：Phase1 只保留上述精简字段，不保存完整 v1 对象（ADR-016）。
- RBAC 只采集规则、角色引用与主体声明，不采集 Secret 内容值；`SubjectInfo` 不表示
  User / Group 当前成员身份已被验证。

## 5. Finding 与 Evidence

```go
type Finding struct {
    ID         string        `json:"id"`         // 指纹，稳定
    Rule       string        `json:"rule"`
    Severity   Severity      `json:"severity"`   // 仅规则计算
    Title      string        `json:"title"`
    Summary    string        `json:"summary"`
    Resource   ResourceRef   `json:"resource"`
    Evidence   []Evidence    `json:"evidence"`
    Related    []ResourceRef `json:"related,omitempty"`
    Correlated bool          `json:"correlated,omitempty"` // 下游衍生，评分排除
    FirstSeen  string        `json:"firstSeen,omitempty"`  // 1.2 趋势
    LastSeen   string        `json:"lastSeen,omitempty"`   // 1.2 趋势
    Role       FindingRole   `json:"role,omitempty"`       // anchor/symptom/impact/advisory/independent
}

type Evidence struct {
    ID        string       `json:"id"`              // E1..En，按排序后稳定生成
    Kind      EvidenceKind `json:"kind"`
    Source    string       `json:"source"`          // 对象+字段路径，如 "Pod/payment-api-xxx/status.containerStatuses[0]"
    Key       string       `json:"key"`             // 如 restartCount
    Value     string       `json:"value"`           // 已脱敏、已截断
    Truncated bool         `json:"truncated,omitempty"`
    Redacted  bool         `json:"redacted,omitempty"`
    Rank      int          `json:"-"`               // 不进 JSON 报告
}
```

### 5.1 指纹（Finding.ID）

指纹输入 = `kind + group + namespace + 归一化名称 + rule + 证据签名`，其中：

- **归一化名称**：Pod 有 owner（Deployment/StatefulSet/Job 等）时使用 owner 的 kind+name；无 owner 的裸 Pod 使用 Pod 名。原因：Deployment Pod 名随机，重启后 Pod 名变化，若直接按 Pod 名做指纹，"持续问题"在 1.2 会误判为"恢复+新增"（ADR-003）。
- **证据签名**：取规则产出顺序中的前 3 条非日志证据 `key:value`（如 `lastReason:OOMKilled`）。
  证据 ID 的排序与指纹签名是两条独立步骤；日志内容不参与指纹（不稳定）。
- 输出：`SHA-256` 十六进制，截断为 16 字节（32 字符）可读。

指纹相关字段标注：

| 字段 | 用于指纹 | 用于 1.2 趋势 | 禁止进入 LLM |
|---|---|---|---|
| Resource.Kind/Namespace/Name | 是 | 是 | 否（可进入，仅名称） |
| Resource.UID | 否 | 否 | 是（避免泄漏内部信息，且无诊断价值） |
| Rule | 是 | 是 | 是（可进入，规则名无敏感信息；为省 token 默认不进） |
| Evidence 签名（非日志） | 是 | 是 | 是（摘要形式进入） |
| Correlated | 否 | 是 | 否 |
| FirstSeen/LastSeen | 否 | 是 | 是（时间戳无诊断价值） |

### 5.2 Evidence 生命周期

```text
创建（scanner/rule 采集原始值）
  → 脱敏（security.Redactor，采集边界，ADR-006）
  → 截断（行数/字节上限，Truncated=true）
  → 排序（Ranker：object_field > event > log > annotation）
  → ID 分配（按排序结果 E1..En，稳定）
  → 指纹签名（规则产出顺序前 3 条非日志证据）
  → 消费（diagnosis 取 top-K，跨对象引用统一为 FindingID#EID）
  → 校验（LLM 引用必须真实存在）
  → 渲染（report 二次脱敏）
```

`Finding.Role` 由 Incident 聚合后统一注入，表示报告语义，不改变 Finding 事实：
`anchor`（故障链主信号）、`symptom`（派生症状）、`impact`（业务影响）、
`advisory`（安全/治理建议）、`independent`（未归链异常）。

## 6. Diagnosis 与 Command

```go
type Diagnosis struct {
    FindingID      string           `json:"findingId"`
    Summary        string           `json:"summary"`
    RootCause      string           `json:"rootCause"`
    Confidence     float64          `json:"confidence"` // 0.0–1.0
    EvidenceChain  []string         `json:"evidenceChain"` // 引用 FindingID#EID，必须真实
    Impact         string           `json:"impact"`
    PossibleCauses []string         `json:"possibleCauses,omitempty"`
    Investigation  []Command        `json:"investigation,omitempty"`
    Remediation    []Command        `json:"remediation,omitempty"`
    Verification   []Command        `json:"verification,omitempty"`
    LLMUsed        bool             `json:"llmUsed"`
    Error          string           `json:"error,omitempty"` // 降级原因（LLM分析不可用/校验失败）
}

type Command struct {
    Category CommandCategory `json:"category"`
    Text     string          `json:"text"` // 完整可复制命令
    Risk     RiskLevel       `json:"risk"`
}
```

生命周期：diagnosis 创建；report 渲染；cli 展示。Command 仅文本，**任何代码路径都不得执行**（ADR-014）。

最终 `Diagnosis` 是根因唯一事实源。`Incident.RootCause*`、`Confidence*`、`EvidenceRefs`、
`EvidenceGaps` 是服务层在确定性诊断与 LLM 增强合并后写入的投影，报告和前端不得把它们当作
另一套可独立演进的根因。

```go
type Incident struct {
    ID                string       `json:"id"`
    Root              FindingRef   `json:"root"`
    Members           []FindingRef `json:"members"`
    RootCauseStatus   string       `json:"rootCauseStatus,omitempty"`
    RootCause         string       `json:"rootCause,omitempty"`
    RootCauseMethod   string       `json:"rootCauseMethod,omitempty"` // rule|deterministic|llm|hybrid|none
    CausalEdges       []CausalEdge `json:"causalEdges,omitempty"`
    EvidenceRefs      []string     `json:"evidenceRefs,omitempty"` // FindingID#EID
    EvidenceGaps      []string     `json:"evidenceGaps,omitempty"`
    AlternativeCauses []string     `json:"alternativeCauses,omitempty"`
    Independent       bool         `json:"independent,omitempty"`
}

type CausalEdge struct {
    SourceFinding string      `json:"sourceFinding"`
    TargetFinding string      `json:"targetFinding"`
    RelationType  string      `json:"relationType"`
    Mechanism     string      `json:"mechanism"`
    EvidenceRefs  []string    `json:"evidenceRefs,omitempty"` // FindingID#EID
    Confidence    string      `json:"confidence"`             // confirmed|probable
    Method        string      `json:"method,omitempty"`       // correlation|deterministic|llm
}
```

同一 Incident 的因果边从根 Finding 生长，每个症状最多一条入边。关联层生成的
`method=correlation` 只能是 `probable`；只有确定性诊断器可写 `method=deterministic`
并在证据充分时标记 `confirmed`。

> **诊断记忆契约**：latest.json 中的 diagnoses 数据专供 Agent 的 `--attach-report` 或后台
> 自动调用 scan Tool 时读取，用于继承历史诊断记忆；用户无需手动挂载文件。

## 7. CollectionError 与 HealthScore

```go
type CollectionError struct {
    Resource  ResourceRef `json:"resource"`
    Operation string      `json:"operation"` // list_pods / get_logs / list_events / ...
    Message   string      `json:"message"`   // 已脱敏
    Time      string      `json:"time"`
}

type Penalty struct {
    FindingID string       `json:"findingId"`
    Resource  ResourceRef  `json:"resource"`
    Severity  Severity     `json:"severity"`
    Points    int          `json:"points"`
    Reason    string       `json:"reason"`
}

type HealthScore struct {
    Score              int       `json:"score"`
    Max                int       `json:"max"` // 100
    Penalties          []Penalty `json:"penalties"`
    CorrelatedExcluded int       `json:"correlatedExcluded"`
}
```

计算规则（ADR-013）：`Score = max(0, 100 − Σ罚分)`，罚分表 CRITICAL 30 / HIGH 15 / MEDIUM 5 / LOW 1；`Correlated=true` 的 Finding 不计罚分，但计数进 `CorrelatedExcluded`；每条 Penalty 必须给出原因（如"Node node-03 NotReady（CRITICAL）"）。

## 8. 禁止进入 LLM 的字段清单（不变量）

1. Secret 数据（程序根本不采集）。
2. ConfigMap data/stringData 值（默认不采集；只采集对象名称等元数据，相关时按敏感键脱敏后才可使用）。
3. kubeconfig 内容、api_key、任何配置中的凭据。
4. 未脱敏的 annotations / labels / 环境变量字面值 / 日志 / Events 消息。
5. 完整 Pod/资源 YAML（只发送摘要字段）。
6. ClusterSnapshot 整体（只发送按预算裁剪的 DiagnosisContext）。
7. CollectionErrors 消息（可能含敏感错误串；不进入 LLM 上下文）。
8. UID、时间戳、ReportPaths 等无诊断价值的内部字段。

该清单由诊断上下文构造器（diagnosis）强制执行，并由 LLM 请求泄密测试守护（TESTING.md）。

## 9. 会话模型（internal/session）

会话是四期企业平台的用户对话与 Agent 执行载体。平台创建会话时必须写入所有者，
owner 归属性用于 API/SSE 访问控制，不参与 Agent 推理。

### 9.1 Message

| 字段 | 类型 | 说明 |
|---|---|---|
| role | string | `user` / `assistant` / `tool` |
| type | string | `text` / `reasoning` / `tool-call-response` / `error` 等 |
| name | string | tool 消息的工具名 |
| toolCallId | string | native Tool Calling 调用 ID（恢复会话回传必需） |
| arguments | JSON | 工具调用参数（恢复会话展示命令用，仅读回放不喂 LLM） |
| data | any | 工具结构化结果（恢复会话渲染表格用，仅读回放不喂 LLM） |
| ok | *bool | 工具执行是否成功（前端权威判定，回放兜底） |
| content | string | 消息正文 |
| timestamp | time.Time | 时间戳 |

约定：整个 Message 落盘前统一脱敏，不携带 Secret 内容值。

### 9.2 Session

| 字段 | 类型 | 说明 |
|---|---|---|
| id | string | 会话 ID |
| userId | string | 会话所有者；创建时由认证主体写入，创建后不可修改 |
| name | string | 会话名 |
| cluster | string | kubeconfig context 名 |
| namespace | string | 默认命名空间 |
| model | string | 模型标识 |
| state | string | AgentState 快照（避免包依赖环） |
| messages | []Message | 会话消息列表 |
| approvedWrites | []string | 本期会话已授权的"操作+资源"写操作 |
| approvalGrants | []Grant | 结构化授权记录 |
| declinedWrites | map[string]int | 会话内被拒写操作 key → 次数（≥2 硬拦截） |
| createdAt | time.Time | 创建时间 |
| lastModified | time.Time | 最后修改时间 |
| pinned | bool | 是否置顶，仅影响所有者视图排序 |

不变量：

- `user / operator` 的会话列表只返回 `userId` 等于当前登录主体的记录；
- admin 可读写全部会话并控制运行与审批；
- 所有按会话 ID 的 HTTP/SSE 操作必须校验 owner，非本人统一返回 `404`；
- 无 owner 会话属于异常数据，普通用户不可见且不可操作，由 admin 处置；
- 会话消息中的 Secret 值与敏感字段继续遵守全链路脱敏红线。

### 9.3 Turn（Agent 执行轨迹）

一条用户消息触发一轮完整 Agent 运行，可回放。字段：`id / sessionId / userId / status /
input / output / error / token / startedAt / finishedAt / createdAt / updatedAt`。

`TurnStatus`：`pending` → `running` →（`waiting` ⟷ `running`）→ `done` / `failed` / `canceled`。

### 9.4 Step（Turn 内可回放执行步）

字段：`id / turnId / sessionId / seq / type / status / tool / params / result / error /
startedAt / finishedAt / createdAt / updatedAt`。

- `StepType`：`reason`（模型思考）/ `tool`（工具调用）/ `observe`（观察结果）/ `approval`（审批）/ `response`（最终回答）。
- `StepStatus`：`running` / `waiting` / `done` / `failed`。
- `params`、`result` 为落库前脱敏后的 JSON/文本摘要。

### 9.5 TokenUsage

`promptTokens / completionTokens / totalTokens`（与 `llm.TokenUsage` 同构，避免反向依赖）。

## 10. 审计模型（internal/audit）

## 11. 审批模型（internal/approval）

### 11.1 Policy

| 字段 | 类型 | 说明 |
|---|---|---|
| RequireApproval | bool | 是否要求人工确认写操作 |
| SkipPermissions | bool | 是否跳过（非 shell）写操作的审批 |
| DenyOps | []string | deny_ops 硬拦截（子串匹配） |
| Mode | Mode | `strict` / `smart` |

### 11.2 Decision 与 Input

`Decision`：`auto` / `require_approval` / `deny`。

`Input` 为审批决策所需最小上下文（**不含 command/risk 原文**，避免审计泄漏）：

| 字段 | 类型 | 说明 |
|---|---|---|
| ReadOnly | bool | 是否只读 |
| Risk | RiskLevel | 风险等级 |
| Shell | bool | 是否含 shell 语法（永远要求审批） |
| Denied | bool | Code Guard 硬拒绝结论（优先级最高） |

判定链（`Policy.Evaluate`）：`Denied→DENY` → `Shell→REQUIRE_APPROVAL` → `ReadOnly→AUTO` →
`SkipPermissions→AUTO` → `!RequireApproval→AUTO` → 否则 `REQUIRE_APPROVAL`。

### 11.3 Grant 与 GrantRequest

`Grant`（任务级结构化授权，用户选"本次不再询问"后产生）：
`id / taskId / operation / kind / name / namespace / cluster / riskCeiling / createdAt / expiresAt`。

`GrantRequest`（单次调用匹配上下文）：
`taskId / operation / kind / name / namespace / cluster / risk / shell / noGrant`。
- 只允许 LOW/MEDIUM 风险形成 Grant，HIGH/CRITICAL 和 shell 永不命中。
- `NoGrant=true`（如一次创建多对象的 create_resource）不参与授权匹配，每次走人工确认。
- 四期平台化：应用层 `AuthorizationGrant` 迁移到 `AuthzGrant`（见 §13），主体维度为
  `principalType(user|group) / principalId`，委派 `namespaces[] + permissions[]`
  （`["*"]` 全量、`["destroy"]` 销毁类），可设 `expiresAt`，以 namespace 为唯一授权边界；
  Kubernetes RoleBinding 由 AuthzGrant 派生并带平台标签/ownerReference，定期对账回收，
  执行前 SAR 只验权限。

### 11.4 CommandTarget

从普通（非 shell）kubectl 命令提取的结构化操作目标：
`operation / kind / name / namespace`。含 shell 语法或无法解析返回零值（按 Shell=true 处理）。

### 11.5 创建风险模型

`CreateSubject`（单个创建对象风险要素）：`group / kind / scope / dangerous / escalations /
unknown / secret / dryRun / namespace / namespaceMissing / denied / notAllowed /
clusterKindDenied`。

`CreateRisk`：`level + reasons`。规则（只升不降）：
- dry run → `SAFE`（自动执行，不改变集群）；
- 含值 Secret → `MEDIUM`；
- cluster-scoped / 未知 Kind / 命中危险字段 / 命中 Skill 风险规则 / 不在良性 Kind 表 → `HIGH`；
- 其余"已映射 + namespaced + 良性 Kind" → `MEDIUM`（唯一可命中 Grant 的档位）。

`CodeGuard` 结论（`GuardResult`：`verdict / codes / reasons / level`），`GuardVerdict`：
`allow` / `review` / `deny`。门禁码见 `12-方案-资源创建能力.md` §5.2（`denied_kind` /
`kind_not_allowed` / `cluster_kind_denied` / `dry_run_required` / `namespace_missing` /
`dangerous_field` / `unknown_kind`）。

## 12. 创建通道模型（internal/tools）

### 12.1 Tool 契约

`Tool` 接口：`Name / Description / InputSchema / Execute / IsReadOnly / Risk`。

`ToolResult`：`Data`（结构化，JSON 给 LLM）、`Text`（人读摘要）、`Truncated`、`Redacted`。
Result 统一经截断/脱敏/定界后进入 LLM 与 UI。

### 12.2 create_resource

入参：`manifest / proposal_id / mode(dry_run|apply) / verify / timeout_seconds`。
- `mode=dry_run`：服务端全量校验并产出会话级提案（对象清单、风险等级与原因、待改字段），不改变集群，自动执行；
- `mode=apply`：必须先有同指纹的 dry-run 提案（`proposal_id`），否则拒绝；内容不一致被拒。
- 危险字段 / 未知 Kind 风险升到 HIGH；cluster-scoped 资源默认禁止创建；同名已存在对象 apply 拒绝。

### 12.3 Secret 值通道

- manifest 只写占位符：`$GENERATE`（执行器生成随机值）或 `$ASK`（用户在审批后单独填写）。
- 值走审批带外通道，只经内存与 context 传给一次 `executor.ApplyRequest`。
- 审计只记录键定位 + SHA-256 指纹 + 长度 + 来源，明文值不进入 manifest / ToolResult / 会话 / 审计 / LLM。

## 13. 四期：平台化持久化模型（internal/store/model.go）
