## 2. 取消传播（cancellation）

### 2.1 扫描路径（一期）

```text
main/signal(SIGINT/SIGTERM)
  → root ctx = signal.NotifyContext
  → scanCtx = context.WithTimeout(root, scan.timeout)
  → 每个请求：context.WithTimeout(scanCtx, kubernetes.timeout)
  → 每个 LLM 调用：context.WithTimeout(scanCtx, llm.timeout)
```

规则：
- 所有 goroutine 必须监听 `ctx.Done()`，不得阻塞等待。
- 取消后 worker pool 立即停止派发新任务；在途请求随 ctx 中止。
- 已产出的快照/Findings 保留，报告标注"扫描被中断"，退出码 1。
- 禁止在 worker 内吞掉 ctx 错误后继续循环；统一走 `collection_errors` 或直接返回。

### 2.2 Chat 路径（二期/三期）

- 每轮 Chat 拥有独立 `chatCtx`；`context.WithCancel` 生成的 `CancelFunc` 记入
  `Server.runs[sessionID]`，供 `POST .../cancel` 触发。
- HTTP 请求返回后 SSE 仍需持续推送，因此 Chat 生命周期独立于单个请求。
- `POST .../send-message` 由 `Server.pending[sessionID]` 保证每会话同一时刻最多一轮运行，
  运行中再次 send 返回 409。

```text
send-message → pending[id]=respond(chan string,1), runs[id]=cancel
  → service.Chat(chatCtx, req, respond) → events chan(ChatEvent,64)
  → goroutine: 消费 events → json → broadcaster.broadcast
  → cancel/delete session → 触发 cancel() → 在途工具/LLM 随 ctx 中止
```

## 3. Worker Pool 设计

### Phase1（并发 8）

任务队列 = 资源类型任务（约 16 个）+ namespace 事件任务（N 个）。实现：`errgroup` +
信号量（或固定 worker 数 + channel）。

```text
任务1: list namespaces（先行，阻塞后续事件任务生成）
任务2..17: list pods/nodes/services/...（并行）
任务18..: list events per namespace（并行，受同一信号量）
```

### Phase2（并发 4）

任务 = 异常 Pod（每 Pod 一个任务，内部串行 current + previous logs，单 Pod 有 30s deadline）。

## 4. SSE 扇出（二期 Web）

- 每会话一个 `Broadcaster`，`emit` 到 `map[chan []byte]struct{}`。
- 每个已连接 SSE 客户端一个带缓冲 channel（容量 256）；消费慢则**丢消息**，
  重连时以 `history` 快照兜底（见 `03-API接口文档.md` §9）。
- `broadcast` 持有互斥锁但非阻塞推入，防止慢客户端阻塞整个会话流。

## 5. 客户端限流与重试

- `rest.Config.QPS/Burst` 由 client-go 的 token bucket 限流器执行；Discovery/Metrics 客户端复用同一 config。
- 读请求重试：仅对 429（尊重 Retry-After）与 5xx 做有限退避重试（指数退避 + jitter，
  上限 3 次）；4xx 其他不重试；`ctx.Err()` 不重试。
- 重试预算计入 `kubernetes.timeout`：总耗时（含重试）不得超过单请求 deadline。
- 避免放大：重试只发生在 Reader 层，且并发被 worker pool + QPS 双重约束。

## 6. 阶段预算

```text
Phase2 截止 = min(scan.timeout 剩余, phase2_timeout 默认 2m)
LLM 预算   = min(scan.timeout 剩余, llm 阶段预算 默认 4m)
```

LLM 自适应预算（ADR-017）：

```text
可送诊数 = min(llm.max_findings, floor(llm.max_total_tokens / llm.max_input_tokens))
若剩余预算不足 → 继续下调 max_input_tokens 或截断送诊数
超出预算的 Finding → 规则结论 + Diagnosis{LLMUsed:false, Error:"预算不足"}
```

## 7. 大集群行为推导（示例：1000 Pod / 50 namespace / 7 异常 Pod）

| 阶段 | 请求数 | 耗时估算（QPS 20） |
|---|---|---|
| Phase1 list | ≈ 67（未分页） | < 5s |
| Phase2 logs | ≤ 7×2 = 14 | < 5s |
| LLM | ≤ 7（串行或并发 2） | 受 llm.timeout 约束 |

结论：API Server 压力与 Pod 数量解耦；日志请求只与异常数成正比。

## 8. 三期创建通道并发（dry run → apply）

- `create_resource` 每次调用先做服务端 dry run，产出会话级提案并**落盘**（非工具实例内存），
  因为 ChatService 每轮会重建工具实例。
- 提案按 `sessionID` 分桶，`ProposalStore` 内部互斥锁保证并发安全；带 `TTL=15m` 与
  单会话上限 `20`。
- `mode=apply` 必须携带同一会话、同一清单指纹 `proposal_id` 且内容一致，否则拒绝；
  避免用户确认的是已失效的集群状态。
- `NoGrant=true`（一次创建多对象）不参与 Grant 匹配，每次走人工确认。
- 含值 Secret（`$GENERATE` / `$ASK`）值经审批带外通道单次传给 `executor.ApplyRequest`，
  manifest / ToolResult / 会话 / 审计均只记录键定位与脱敏指纹。

## 9. 防 goroutine 泄漏

- 所有并发原语限定在 scanner/diagnosis/agent 包内部，通过 `errgroup.WithContext` 管理。
- channel 全部有界；无 unbounded 队列（SSE 缓冲、Chat events、审批 respond 均为有界）。
- LLM 并发上限（默认 2），避免打爆私有模型服务。
- Chat goroutine 以 `defer cancelChat()` + 清理 `pending/runs` 兜底，确保请求失败或
  事件通道关闭后立刻归还资源。
- `go test -race` 纳入每阶段出口标准。

## 10. 审批同步（二期）

- 审批等待用 `respond` 通道（容量 1）：一次写操作在审批通过前暂停（Turn → `waiting`），
  用户选择后经 `Resume` 继续（`waiting` ⟷ `running`）。
- `respond` 已被消费/已答过时再次 POST approve 返回 409（`approval already answered`）。
- shell 命令永远走人工审批，不进入 `SkipPermissions` / `require_approval=false` 自动化通道。
