# k8s-ai 测试架构设计

- 版本：v3.1.0
- 日期：2026-08-12（首版） / 2026-10-08（补齐二期、三期） / 2026-11-05（P9 体检诊断质量体系与证据语义收口）
- 状态：一期~三期已封版；四期 P9 体检诊断质量测试体系已落地（§3.4）

## 1. 测试目标

k8s-ai 的核心风险集中在权限与安全边界：读操作自动执行、写操作审批放行、
Secret 值永不进入 LLM / 会话 / 审计。测试的目标是证明这些边界在代码层被强制
执行，并保证扫描、诊断、Agent 循环、审批与创建流程在正常与异常路径下行为正确。

一期至三期的封版已交付以下能力，测试需覆盖：

- 一期：只读扫描与诊断。
- 二期：自然语言 Agent、审批写操作、会话与会话流。
- 三期：资源创建（create_resource 两阶段 dry_run→apply）与运行中取消。

## 2. 分层测试策略

| 层级 | 关注点 | 主要对象 |
| ---- | ---- | ---- |
| 单元 | 单模块正确性、失败收敛、脱敏 | `internal/kubernetes`、`scanner`、`rule`、`evidence`、`diagnosis`、`llm`、`report` |
| 单元（二期） | Agent 循环、审批决策、会话、取消 | `internal/agent`、`approval`、`session`、`tools` |
| 单元（三期） | 创建风险评估、提案、Secret 值隔离 | `internal/approval/create_risk.go`、`create_proposal`、`secret_values.go` |
| 集成 | 服务编排、SSE 扇出、会话存储、平台能力与红线 | `internal/server`、`internal/session/store.go`、`internal/sessionapi`、`tests/platform` |
| 架构/安全 | 依赖分层、写方法落点、Secret 泄漏 | 架构测试 + AST 断言 + 泄密扫描 |
| 端到端 | 真实集群上读/写/创建 | 一次性真机环境，人工值守 |

### 3.4 四期 P9：体检诊断质量测试体系

目标是证明「体检能定位根因」这件事可回归，而不只是证明代码不 panic。
测试全部使用可重复夹具，不依赖真实集群（需求 §10）。

**故障场景矩阵**（`internal/deterministic/fixtures_*_test.go`，场景名 = 诊断器 ID）：

| 夹具文件 | 覆盖场景 |
| ---- | ---- |
| `fixtures_pod_test.go` | CrashLoopBackOff、ImagePullBackOff、Pending、FailedScheduling、FailedMount、OOMKilled、Evicted、探针持续失败 |
| `fixtures_node_test.go` | Node NotReady、Node Memory/Disk/PID Pressure |
| `fixtures_workload_test.go` | Deployment 副本不足、StatefulSet 异常、DaemonSet 未覆盖节点、Job 失败、HPA 无法扩缩、PDB 阻断驱逐、配置引用缺失 |
| `fixtures_storage_test.go` | PVC Pending、PV 异常、StorageClass 异常、VolumeAttachment 卡住 |
| `fixtures_network_test.go` | Service 无 Endpoint、EndpointSlice 与 Pod Ready 不一致、Ingress 后端不可用、DNS/CoreDNS、NetworkPolicy 潜在阻断 |

每个场景覆盖六个条件：正常情况、单一故障、多个关联故障、证据缺失、采集失败、
容易误判的边界条件。断言不止「有没有 Finding」，还包括：期望根因诊断器 ID
（含期望 `unknown`）、故障链成员集合、每条因果边能自证资源关系路径、
处理建议是否含该场景规定的动作。

**LLM 维度**（`internal/diagnosis/enhance_test.go`）：无 LLM、LLM 正常、LLM 超时、
请求失败、返回无效 JSON、schema 不合法、证据编造退回、发明资源被识别、根因悬空下调、
预算跳过。核心断言是降级语义而不是返回值格式：降级时必须保留确定性结论，
`KeptDeterministic` 只在确定性引擎真的覆盖该故障时为真。

**运行模式**：有 LLM / 无 LLM 两条路径共用同一套确定性结论，测试断言无 LLM 路径
同样产出根因、影响链与处理建议（`Source=deterministic`、`Mode=rule_only`）。

**质量指标口径**：

| 指标 | 口径 |
| ---- | ---- |
| Finding Precision / Recall | 夹具里应报/不应报的 Finding 集合与实报集合比对 |
| Root Cause Accuracy | 期望根因（含期望 `unknown`）与最终 `Diagnosis.Diagnoser` / `RootCauseStatus` 比对，并断言 Incident 投影与之一致 |
| Incident Correlation Accuracy | 期望故障链成员集合与实际 `Members` 比对 |
| Evidence Support Rate | 根因结论的证据引用全部命中真实 `FindingID#EID` 的比例 |
| Remediation Relevance | 处理建议含该场景规定动作关键词 |
| No-LLM Diagnostic Coverage | `deterministic.Scenarios()` 中无 LLM 也能出结论的场景占比 |

**无法自动断言的部分**（真实集群上的 CNI/CoreDNS 行为、对象存储归档链路）：
以夹具 + 人工验收清单交付，验收点写在场景注释里，不允许用模拟数据冒充真实体检结果。

**过程与兼容性**：阶段记录测试（`internal/service/stages_test.go`、
`internal/server/scan_stages_test.go`）断言 13 项 StageRecord、无百分比、未启用 LLM 时该阶段为 `skipped`；
报告契约测试（`internal/server/report_structured_test.go`、
`internal/service/report_json_test.go`）断言历史 Markdown-only 报告返回 415 而不是被硬凑，
以及详情端点与下载端点的授权与错误映射同形。

P9.14 证据语义回归还必须覆盖：

- `internal/model`：`FindingID#EID` 生成、旧裸 E-ID 归一化不跨 Finding 串号；
- `internal/incident`：Finding 角色注入、每个症状最多一条入边、关联层不得写 `confirmed`；
- `internal/diagnosis`：canonical 证据行预算裁剪，长上下文不得绕过单条预算；
- `internal/service`：最终 Diagnosis 投影回 Incident，旧规则根因不能覆盖最终结论；
- `internal/deterministic`：`Running/Completed + exitCode=0 + 高重启次数` 必须描述为
  “正常结束后被再次拉起”，证据不足时只到 `probable`，且不得生成盲目 `rollout restart`。

### 3.5 四期 P9：页面体检交互与产物格式口径（P9.10–P9.13）

页面体检的体验口径同样是契约：文案、进度、能否停止、归档几份、总览怎么算，都要能被测试钉住。
前端 `web` 侧 `npm run test` 当前 **29 文件 196 用例**，后端配套用例见右列。

| 口径 | 断言要点 | 用例落点 |
| --- | --- | --- |
| 实时阶段进度 | 弹窗即时出现阶段清单与 `N / M 阶段`（done 与 skipped 一并计入 M），**不报百分比** | `web/src/views/report/__tests__/reportsView.spec.ts` |
| 停止体检 | 终态是 `cancelled` 而不是 `failed`，文案「已由发起人停止」，停止后按钮不再可点 | 同上 + `internal/server/scan_cancel_test.go` |
| 产物格式单选与按需导出 | 一次体检只归档选中的那一种；`GET /reports/{id}/export` 只渲染不归档 | `reportsView.spec.ts`、`reportDetailView.spec.ts`、`scans_test.go`（`format` 非法值 400 **先于**授权判定） |
| 总览与归属 | 五张总览卡与列表同源同过滤，`scopeCategory` 三类互不污染；行标题「体检报告」、归属「发起人：…」、类别与范围分列两枚徽标、没有登记集群就不显示集群 | `reportsView.spec.ts`、`internal/server/report_summary_test.go` |

## 4. 审批与安全边界测试

### 4.1 Policy.Evaluate 决策序

测试必须锁定以下决策链，不得随意调整顺序：

1. Shell 语法 → 无条件人工审批。
2. ReadOnly → 自动执行。
3. smart grant → 自动。
4. SkipPermissions → 自动。
5. !RequireApproval → 自动。
6. 其余写操作 → 人工审批。

### 4.2 写方法落点（架构测试）

AST 断言持续保证只有 `internal/executor` 允许变更式 client-go 调用；
三期 create 写路径同样收敛在该层。

### 4.3 Secret 值隔离

循环测试从证据、LLM 请求、会话文件、审计文件四个去处断言 Secret 内容值
永不可达；元数据/键级读取（键名、类型、immutable）允许。

### 4.4 运行中取消

`TestCancelActiveRun` 覆盖运行中停止：按 session 记录 `context.CancelFunc`，
取消后 SSE 正常终止、会话状态机迁移到 cancelled。

体检任务的停止走同一条思路：`POST /api/v1/scans/{id}/cancel` 只对发起人本人或 admin 放行，
他人任务与不存在同形 404，已结束的 409；状态**先**写 `cancelled`，再由收尾逻辑把 running 阶段冻结为
failed「已停止」，并落 `scan.cancel` 审计。停的是采集与诊断，不删已归档的报告。
`internal/server/scan_cancel_test.go` 覆盖 context 传播、终态不被后到的失败覆盖、重复停止幂等，
以及停止后闸门释放才能重新发起下一次体检。

## 5. 架构与依赖分层

保持所有业务逻辑不依赖 CLI，CLI、Server、Web UI、CronJob 复用同一批应用服务。
架构测试校验服务层不 import 客户端展示层，扫描、规则、证据、诊断分层不被破坏。

## 6. 压力与稳定性

- 大集群扫描：worker pool 上限、单资源超时、阶段预算。
- LLM 流式：背压、扇出到多个 SSE 订阅人不互相阻塞。
- 审批等待：waiting 状态不占用 Agent 执行 slot。

## 7. 准出标准

封版（一期~三期）需满足：

- `go test ./...` 全部通过。
- `go vet ./...` 无告警。
- 关键模块（scanner、approval、session、tools、agent、webui）单测齐全。
- 架构测试 + Secret 泄漏测试通过。

四期 P9 体检诊断准出：

- §3.4 故障场景矩阵全绿，且**每个场景在纯无 LLM 下**都能给出根因或明确的 `unknown` + 证据缺口。
- 采集失败场景必须让健康评分封顶并在结论里声明数据缺口，不允许出现「未发现异常」。
- 详情端点与下载端点授权同形（`report_structured_test.go`）。
- 停止面有测试：发起人判定、`cancelled` 不被后到的失败覆盖、重复停止幂等（`scan_cancel_test.go`）。
- 一次页面体检在对象存储里**只存选中的那一份**产物，另一种格式必须走按需导出（`reportsView.spec.ts` 与导出端点用例）。

四期（企业化平台化）上线前补充租户隔离与权限治理相关测试。
