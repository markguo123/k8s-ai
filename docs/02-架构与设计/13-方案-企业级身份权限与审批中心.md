## 1. 方案结论

- 角色仅三个：`user` / `operator` / `admin`。
- 权限拆成三层：平台 Permission、会话所有权、namespace 资源授权；三者不可互相替代。
- `user` / `operator` 的平台 Permission 默认集合为空；登录、创建会话和访问自己的会话属于
  已认证基础能力，不走平台 Permission。
- 授权以 **namespace 为唯一边界**：用户零权限起步，admin 划分配置 namespace；
  获得 namespace 后即拥有该 namespace 内全部操作能力。
- `operator` 不因角色自动获得跨 namespace 或节点级能力；所有资源 scope 都必须显式授权。
- 三类销毁操作（`delete namespace` / `delete pvc` / `delete pv`）**仅 admin 可执行**；
  `user` 与未被委派的 `operator` 发起时，直接提示"该操作需联系管理员处理"，
  不发起审批申请、不进入等待状态。
- 会话由 `ownerUserId` 隔离：普通角色只能访问自己的会话；admin 对全部会话拥有
  完整读写、运行控制与审批能力。
- 审批与角色解耦：是否确认由平台统一策略决定，与用户角色无关；
  审批主体只有操作者本人或平台子 agent（自动审批），不引入任何"他人在线审批"。
- 自动审批**采用显式白名单**，不依赖"可逆"等模糊定义；
  白名单外的写操作一律至少自确认，白名单内"需确认"项与高危类绝不自动。
- 自动审批总开关默认关闭，开启后每个会话可自行开关，放行决策必须落审计；
  总开关不能覆盖高危类。
- 平台演进为 **多 Agent 编排架构**：首个专用子 Agent 为承担自动审批工作的审批子
  agent（Approval Agent）；后续能力型子 Agent 通过统一注册契约接入，
  写路径与权限审计仍走同一链路。
- Secret 值读取红线与本套授权审批完全正交，不受影响。

## 2. 角色模型

| 角色 | 平台 Permission | 会话权限 | namespace 授权与操作能力 | 审批 |
| --- | --- | --- | --- | --- |
| `user` | 默认零 | 登录、创建会话、访问自己的会话 | 默认零；admin 按集群与 namespace 显式授权；授权后拥有除销毁类外的全部能力 | 本人自确认 / 审批子 Agent 白名单自动；销毁类未授权直接提示联系管理员 |
| `operator` | 默认零 | 登录、创建会话、访问自己的会话 | 默认零；必须逐 namespace 授权，不因角色自动跨 namespace；销毁类需 admin 显式委派 | 同 user；委派销毁能力后仍需二次确认与留痕 |
| `admin` | 全量 | 全部会话可读写、运行控制与审批 | 平台与集群全量；可授予/回收用户和组的 namespace 能力 | 销毁类二次确认，操作仍落审计 |

角色只决定"权限上限"，不决定普通业务会话"谁来审批"。`admin` 对全部会话的运行控制与审批
是独立的管理员能力，必须写审计，但不建模为"为他人指定审批人"。

创建用户时角色集合固定为 `user / operator / admin`，默认 `user`；角色列表和创建表单
不得出现其他角色。

### 2.1 平台 Permission

平台 Permission 只约束平台管理和治理 API。`user / operator` 默认集合为空，因此：

- 不展示 Skill 管理、配置中心、用户与权限、审计等平台管理入口；
- 调用对应 API 返回 `403`；
- 仍可登录、创建自己的会话、读取自己的会话并完成本人审批。

`chat.read / chat.write` 不列为平台 Permission。会话访问由下一节的归属性规则约束，
避免把“能否使用平台”与“能否读取某个会话”混成同一个权限。

### 2.2 会话访问矩阵

所有 `/api/v1/sessions*` API 与 SSE 端点均要求有效登录态。会话 owner 在创建时由后端
从认证主体写入，创建后不可由客户端修改。

| 操作 | user | operator | admin |
| --- | --- | --- | --- |
| 创建会话 | 允许 | 允许 | 允许 |
| 列出自己的会话 | 允许 | 允许 | 允许 |
| 列出全部会话 | 禁止 | 禁止 | 允许（只读） |
| 读取自己的会话历史/事件流 | 允许 | 允许 | 允许 |
| 读取他人会话历史/事件流 | 禁止 | 禁止 | 允许 |
| 发送消息、审批、取消运行 | 仅自己 | 仅自己 | 全部会话 |
| 重命名、置顶、删除 | 仅自己 | 仅自己 | 全部会话 |

约束：

- 非本人会话访问统一返回 `404`，不区分“不存在”和“无权访问”；
- SSE 历史快照、实时事件、审批回传和取消操作执行同一 owner 校验；
- admin 对他人会话的读写、运行控制与审批必须写审计；
- 无 owner 会话属于异常数据，由 admin 审计和处置；
- 审计记录包含用户、会话、动作和时间，不记录消息正文或敏感值。

## 3. 授权模型：namespace 即边界

### 3.1 授权前

用户未获得任何 namespace 授权时，不能对该 namespace 发起查询、诊断或任何操作。
未获得集群级授权时，不能读取 Node、PV、StorageClass 等集群范围对象。
登录、会话管理和普通 Chat 编排本身不授予任何 Kubernetes 资源访问权。

### 3.2 授权后

- 用户获得指定 namespace 后，拥有该 namespace 内除销毁类外的全部操作能力；
- 授权对象维度：`用户/组 × 集群 × namespace 集合`；
- 用户不能操作授权 namespace 之外的范围；
- `delete namespace` / `delete pvc` / `delete pv` 默认不授权，仅 admin；
  如需交给 operator，由 admin 单独显式委派（记录在案、可回收、有过期时间）；
- `delete pod`、重启属普通可操作范围，但按平台策略需显式确认。

### 3.3 诊断行为与授权 scope

Agent 在 Chat 内的行为与各角色统一，不因用户角色产生诊断差异：

- 诊断只读取当前用户已获授权的 namespace scope；跨 scope 请求必须显式授权；
- Node / PV / StorageClass 等集群范围信息不作为普通用户的默认读取能力；
- 不做"诊断投影层"式的复杂隔离，避免不同用户得到不同诊断结论；
- 只做一种简单区分：用户不能操作授权 namespace 之外的范围；
- 读取放开不等于写入放开，变更与销毁仍走统一确认与执行门禁。

## 4. 审批与自动审批白名单

### 4.1 读取与提案（恒自动）

以下不产生实际变更，直接执行并留痕，不属于"审批"：

```text
get / list / watch / describe / logs / events
dry-run / diff / plan（只产出提案，不落地）
```

### 4.2 自动审批白名单（显式枚举，可配置）

只有白名单内且标识为"可自动"的操作，才允许在自动审批开启时自动放行。
白名单是平台配置的具体枚举，不是宽泛的"可逆"判断：

| 操作 | 是否可自动 | 约束 |
| --- | --- | --- |
| `get/list/watch/describe/logs/events` | 恒自动（读取） | 授权 namespace 内；诊断投影只读 |
| `dry-run / diff / plan` | 恒自动（提案） | 只产提案、不落地 |
| `scale`（有界） | 可自动 | 仅授权 namespace 内可伸缩资源；副本数受上下限约束，单次变动在阈值内 |
| `rollout restart` | 需确认 | 可能引发雪崩，默认不自动 |

基线实现只开放上述最小集；管理员可按集群增删白名单条目。

### 4.3 白名单外 = 至少自确认

- 白名单外的任何写操作一律自确认（操作者本人弹框确认）；
- 即使某项操作在特定场景下"可逆"，只要不在白名单，就不允许自动；不可用"可逆"名义默认自动；
- 有版本化来源、可校验幂等的普通 namespaced 变更，可经管理员评审后加入白名单。

### 4.4 高危类：恒人工确认，未授权直接提示联系管理员

高风险类永不自动，且不引入审批等待：

```text
delete namespace / delete pvc / delete pv
shell 构造
未知或危险字段、回收类（GC / reclaim）
无法可靠解析的命令
```

- 未授权（`user` 与未被委派的 `operator`）：确定性拒绝，提示"该操作需联系管理员处理"，会话继续；
- 有授权（`admin` 或经委派的 `operator`）：二次确认，确认与执行结果强制留痕。

### 4.5 自动审批总开关

- admin 在平台配置"自动审批"总开关，**默认关闭**；
- 开启后，用户可在会话内自行开关；每次自动放行必须写审批中心 AUTO 记录并落审计；
- 总开关仅作用于 4.2 白名单"可自动"项；"需确认"项、高危类、shell 构造、scope 未授权一律不自动。

### 4.6 审批主体

审批主体只有两种：

- 操作者本人（会话内自确认，使用平台审批卡与 pending 通道）；
- 专门的**审批子 agent（Approval Agent）**代审：只接管自动审批路径，
  仅处理白名单"可自动"项，受总开关 + 会话开关 + scope 授权共同约束。

## 5. 审批中心：决策与治理面，不是"第二审批人"

### 5.1 定位

会话内“自确认”统一使用平台交互通道
（Agent loop `Confirm` + WebUI `/api/v1/sessions/{id}/approve` pending 通道）；
审批中心在其上收敛决策与留痕：

1. **统一策略中枢**：所有写操作走同一决策序列——风险目录 → 自动审批白名单 → scope/RBAC →
   自动 / 自确认判定；收敛当前分散在 agent loop、chatApprover、Session Grant 的判定逻辑；
2. **决策解释与留痕**：每条决策记录 why 字段，支撑审批历史与审计时间线；
3. **策略与授权管理面**：strict/smart、denyOps、Secret 策略、自动审批白名单、
   AuthzGrant 与 RBAC 对账、销毁能力委派；
4. **兜底与统计**：确定性拒绝（未授权销毁等）也入中心记录，作为被拒次数、风险分布、
   治理报表的数据源。

> 澄清"由谁确认"：确认主体只有两类——【本人自确认】或【策略 / 子 agent 自动（AUTO）】，
> 不存在第三类。纯交互 chat 中它就是“用户本人点确认”，
> 不承担在 operator / admin 之间挑选审批人的职责（该机制已废弃）；
> `admin` 对他人会话的读取、发送消息、运行控制和审批属于平台管理员例外能力；
> 每次动作以该 admin 为操作者写审计，不属于"第三方代确认"模型；
> 其真正增量在 1) 自动路径决策主体是非人类（策略 / 子 agent，落 AUTO 记录）;
> 2) 定时任务 / CI / MCP 等无人在线的执行面无"点确认"的人，由中心统一定义决策主体；
> 3) 资质约束是 scope 级（需持有对应 scope 的 approval.execute 且非请求人），
>    禁止第三方代确认、禁止把销毁类转成"找人在线审批"。

一句话：审批中心决定"要不要确认、由谁确认（本人自确认 或 策略 / 子 agent 自动）、
为什么放行、结果如何"，会话确认是"需要人工确认那一刻"的交互执行端子。

### 5.2 平台审批契约

- 平台统一使用 `Policy.Evaluate`、Grant、Code Guard、会话级已授权/已拒绝记录；
- WebUI `/api/v1/sessions/{id}/approve` + pending 通道作为自确认交互入口；
- 审批中心在其上增加决策收敛、历史沉淀与解释，不做大拆除。

### 5.3 记录模型增强

```text
requested_by      请求发起用户
decided_by        最终决策方（AUTO 时为 approval-agent / 审批子 agent）
scope             集群 / namespace / 资源类型与名称
plan_hash         提案指纹（平台 dry-run 指纹）
expires_at        审批有效期
policy_version    命中策略版本
whitelist_key     命中的自动审批白名单条目（AUTO 时必填）
resolved_by       interactive_self | auto
outcome           approved | rejected | denied | expired
```

每个审批可回答：谁发起、为什么、命中什么、谁能确认、结果如何。

### 5.4 P4.8 修正

原："非 admin 不能执行审批操作"。

改为：

```text
任何情况下不能审批自己的请求；审批人必须持有对应 scope 的 approval.execute，
且不能是请求发起人。
```

该条适用于平台代审路径；会话内操作者自确认是其自身操作，不受其约束。

## 6. 多 Agent 架构：审批子 agent 与扩展口

### 6.1 决策：引入独立审批子 agent（Approval Agent）

- 自动审批不作为散落在 Agent loop / chatApprover / Session 里的 if 分支实现，
  而是独立为一个**专门的审批子 agent（Approval Agent）**，作为唯一接管
  自动审批路径的执行主体；
- 会话内人工路径不变（本人自确认）；仅白名单"可自动"项会路由给 Approval Agent，
  且必须同时满足 总开关开启 + 会话开关开启 + scope 授权命中 + 非高危 + 非 shell；
- Approval Agent 只输出结构化审批决定：`decided_by = approval-agent`，
  `whitelist_key / plan_hash / reason` 必填，不输出自由文本"放行了"；
- 每条自动放行同步写审批中心 AUTO 记录并落审计；拒绝与越权同样留痕，供治理报表。

### 6.2 Approval Agent 职责边界

- **策略的执行器，不是策略的制定者**：风险目录、白名单、denyOps、Secret 策略、
  scope 授权均由 admin 在平台配置，Agent 只按规则裁决；
- 无独立写动力：只能对"已通过全部前置校验的白名单提案"签发放行，
  不能自建 scope、不能跨 namespace、不能提升自身权限；
- 可解释：每个决定携带命中规则链与理由，供审计与用户回看；
- 可关闭：总开关关闭时 Approval Agent 不可用，自动路径退化为自确认；
- 不作为安全兜底：SAR 与准入控制仍在链路上（见 7.4），Agent 放行不等于永久信任。

### 6.3 多 Agent 平台与注册机制（扩展口）

- 四期起平台演进为**多 Agent 编排架构**：主 Agent 负责任务编排与会话上下文，
  子 Agent 各自持专精能力；首个子 Agent 为 Approval Agent；
- 建立统一的 **Agent 注册与契约**（首个实现即 Approval Agent，为后续预留口）：

```text
agent_id          唯一标识
name / desc       显示名与职责说明
capabilities      可处理的操作类型与工具集声明
scope             允许触达的集群 / namespace / 资源范围
executor          是否可下发写操作（Approval Agent 仅签发决策，不直连 executor）
policy_binding    绑定的审批策略版本
lifecycle         注册 / 下架 / 能力变更均写审计
```

- 主 Agent 按 capability + scope 路由任务；任何子 Agent 的写操作仍走统一
  风险目录 → 审批策略 → SAR → Code Guard → Executor → 准入控制 → 审计，
  与用户写路径一致，不设豁免；
- 预留统一注册表与调度口供后续能力型子 Agent（如可观测性 / 安全巡检 /
  成本治理等）接入，避免每加一个 Agent 再造一套权限与审计。

### 6.4 主 Agent 与审批子 Agent 的职责收敛

- 主 Agent 只负责编排、工具调用和用户交互；
- Approval Agent + 统一策略中枢负责自动审批路径的决策；
- 会话内自确认、SSE 推送与 pending 通道由平台统一实现，所有子 Agent 共用。

## 7. 执行边界：谁来真正拦

### 7.1 纯平台网关不足

仅靠平台侧对 namespace 做字符串匹配放行，不能作为安全边界：一旦凭据泄漏或绕过平台直连 API，
平台检查即失效。强制点必须在 Kubernetes API Server。

### 7.2 身份映射 + RBAC

- 平台用户映射为 Kubernetes 主体：`k8s-ai:user:<id>`，组为 `k8s-ai:group:<id>`；
- 授权 namespace 时平台自动生成该 namespace 的 Role / RoleBinding；
- 变更执行前做 SubjectAccessReview，命中才下发；
- 集群侧 RBAC 提供第二重兜底，平台逻辑被绕过时 API Server 仍拒绝；
- 销毁类以单独 ClusterRole 下发，仅 admin 或经 admin 显式委派的 operator 持有；
- 企业 OIDC 作为可选身份来源，登录后映射到同一平台主体。

### 7.3 RoleBinding 对账与回收

- 平台 AuthzGrant 为权威来源，RBAC 为派生结果，避免出现"两套真相"；
- 平台只管理带 ownerReference / 平台标签（如 `k8s-ai.io/managed=true`）标记的
  RoleBinding / ClusterRoleBinding，不触碰用户自建 RBAC；
- 定期对账（reconcile）：列举平台管理的 RBAC 对象与授权库比对，增删改回环同步，
  清除漂移（drift）与孤儿对象；
- 撤销与过期即回收：grant 被删除或 `expires_at` 到期时，同步删除对应 RBAC 绑定，
  用户在集群侧的权限随之立即收回；
- 对账幂等、可重跑，失败必写审计，并可聚焦到"单集群 / 单 grant"重试。

### 7.4 SAR 只查权限，不替代安全

- SAR 只回答"该主体是否有权对某 scope 做某 verb"，不判断操作本身是否安全；
- 安全校验仍由既有链路负责：风险目录 → 审批策略 → Code Guard
  （deny_ops / forbidden / Secret 值与 --raw / 未知 kind / 危险字段 / 未 dry-run 拒绝）；
- 集群侧可用 ValidatingAdmissionPolicy / webhook 等准入控制作为最后防线；
- 完整执行序列：

```text
风险目录 → 审批策略 → SAR → Code Guard → Executor → 准入控制 → 审计
```

### 7.5 配置复杂度

管理员授权操作仅为"选用户/组 → 选集群 → 勾 namespace → 保存"，
销毁委派为"选用户为 operator 并勾选销毁能力 → 设置有效期"，RBAC 由平台自动生成与同步，
无需手写 YAML；每次变更写审计。

## 9. 边界

- 自动审批仅作用于显式白名单"可自动"项，不依赖"可逆"定义；
- 白名单外写操作一律至少自确认，"需确认"项与高危类绝不自动；
- 销毁类无授权即确定性拒绝并提示联系管理员，不建申请、不阻塞等待；
- 委派 operator 的销毁能力仍需二次确认并强制留痕；
- RoleBinding 对账收敛于平台授权库，撤销 / 过期即删，不产生漂移；
- SAR 只验权限，操作安全性仍由 Code Guard 与准入控制把关；
- 集群只读诊断同样受 namespace / 集群 scope 授权约束，不与写权限混用；
- 自动审批默认关闭，开启需 admin 配置且会话级留审计；
- Approval Agent 是策略执行器，不拥有策略制定权、无独立写动力、不自我扩权；
  其自动放行仅覆盖白名单"可自动"项；
- 所有子 Agent（含审批子 Agent）的写操作均走统一 风险目录 → 审批策略 → SAR →
  Code Guard → Executor → 准入控制 → 审计 序列，不设豁免；
- 本方案不设计独立于 Kubernetes RBAC 的平行权限体系。
