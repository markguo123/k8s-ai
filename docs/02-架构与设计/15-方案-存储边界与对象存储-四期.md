| # | v1.5 口径 | 代码实际落地 | 性质 | 落点 |

| 1 | §10 表 `dir` 行交付「`Ensure`/`GC`」 | 本批交付 `Ensure`（建根目录 + `.tmp` + 抢锁，幂等）与 `Probe`，**`GC` 仍随 P8.9**（§4.2 已定：`Maintainer` 只 `Ensure`，提前声明就是占位实现）；`.tmp` 崩溃残留不进 `List`，回收一并随 P8.9 | 批次澄清 | §10、§22 |
| 2 | §10/§11.2 以 unix flock 单平台描述「必须 flock 独占（`ErrLocked`）」 | 落地为**按平台取原生建议锁**：unix 系 `flock(LOCK_EX\|LOCK_NB)`、Windows `LockFileEx(LOCKFILE_EXCLUSIVE_LOCK\|LOCKFILE_FAIL_IMMEDIATELY)`（`ERROR_LOCK_VIOLATION` → `ErrLocked`），两者**都不等待**，第二个副本直接起不来；无任何锁原语的平台在 `Ensure` 返回 `ErrUnsupported`，不在「以为锁住了」的前提下并发写。锁文件 `.lock` 只写 pid/主机名供人工排查，**权威在内核**，进程被 kill 后自动释放，没有「人肉删陈旧锁文件」的运维陷阱 | 落地细化 | §10、§11.2 |

| 5 | `Put` 失败分支的临时文件清理未成文 | 每条失败分支（超限、上游读错、`Sync`/`Close` 失败、`rename` 失败、ctx 取消）都必须收走临时文件并各有断言；进程在 `rename` 之前被 kill 留下的残留不进 `List`（`.tmp/…` 不足 key 段数），回收随 P8.9 | 新增约束 | §10、§15 |

| 7 | `NewDir` 的构造时机未约定 | 构造函数**不碰文件系统**，建目录与抢锁统一在 `Ensure`（§11.2 的启动期 fail-fast 位置不变），配置校验与单测拿到「未启用」后端时零副作用 | 落地澄清 | §11.2 |

## 2. 双存储定位（总纲）

### 2.1 职责边界

| 载体 | 存什么 | 权威性 | 备份责任 |
| --- | --- | --- | --- |
| **MySQL**（`platform.store`） | 全部结构化业务数据（用户/角色/授权/集群凭据/设置/Skill/审批/审计/Turn/Step）+ **会话正文（现状列，见 §8.4）** + **对象元数据 `objects` 表** + 业务引用列 | **唯一权威源** | `mysqldump --single-transaction` / RDS 快照 / binlog PITR |
| **对象存储**（S3 兼容，`platform.blobs`） | 实际文件内容与大体积非结构化数据：巡检报告产物、会话附件、（预留）导出文件 | 内容权威，但**元数据以 MySQL 为准**；桶不是任何业务对象的清单 | `mc mirror` / 厂商复制 / PVC 快照；RPO = 镜像周期 |
| **容器卷 / 本地目录** | 临时缓冲（`/tmp`）、`report.directory` 现场副本、CLI 的 `~/.k8s-ai`、SQLite 兜底库文件 | **永不作事实源**（CLI 形态例外，见 §16） | 不承担 |

MySQL 的默认业务数据库地位**不因引入对象存储而改变**：不迁移业务表、不把结构化数据搬进桶、不引入第二套业务查询面。对象存储在系统里只是一个「内容仓」，回答不了「有哪些对象」——那永远是 MySQL 的职责。

### 2.2 四条不可动摇的口径

1. 业务模块只见 `objectstore.Store` 接口，看不见桶名、endpoint、AK/SK，更不允许 import S3 SDK（§4.4 门禁强制）。
2. 对象存储故障不得影响不依赖文件存储的基础业务：聊天、审批、审计、扫描采集、设置、鉴权必须照常（§11）。
3. 「引用存在 ⇒ 对象存在」由写顺序保证；「对象存在 ⇏ 引用存在」是允许的中间态，由 GC 收敛（§7、§9）。
4. 引用列只新增可空列/新表，不 backfill 历史数据，不做停机迁移。

### 2.3 目标

1. `internal/objectstore` 抽象 + 四后端（`off`/`db`/`dir`/`s3`），S3 兼容面覆盖 MinIO/Ceph RGW/AWS S3/私有化对象存储。
2. 会话事实源收敛（P8.0）：平台模式重启不丢会话，删除即真删。
3. 报告产物入对象存储且 Web 可列可下载；附件表结构与 API 契约本期定死（上传通道 P8.7 延 v4.2）。
4. 对象元数据模型、状态机、幂等、失败补偿、孤儿回收、逻辑/物理删除、对账与备份恢复全部在本方案定死，P5 只实现调度。
5. CLI 二进制零影响（§16 硬约束）。

### 2.4 非目标（本期明确不做，理由见 §23.2）

多 Bucket 调度与租户级桶隔离、冷热分层与存储类别转换、跨区复制、桶生命周期规则托管、桶版本化强制要求、客户端加密（SSE-C/KMS）、对象锁/WORM、客户端直传（presigned PUT / PostObject 表单）、分片上传与断点续传、CDN、会话正文整篇外置、Skill assets 外置、向量/嵌入存储、Prometheus 远端存储、多副本扩缩前置项（SSE sink 与 `ProposalStore` 外移）。

## 3. 设计原则

1. **接口无厂商性**：`objectstore.Store` 只允许 S3 通用语义（对象读写、前缀列举、条件探测、presign 下载）。禁止 bucket policy service、replication、object lock、lifecycle API 等厂商私有调用。
2. **默认后端零行为变化**：`platform.blobs.driver` 默认 `db`。未显式改配置的环境升级即无感，`config validate` 与启动日志明示当前后端。
3. **引用列，不搬列**：业务表新增可空引用列指向对象，不做历史 backfill；老库升级只加列建表。
4. **事实源唯一**：MySQL 是业务数据与对象元数据的唯一权威。**会话必须先收敛到 MySQL**（P8.0）——在大载荷落点定死之前，先把「谁说了算」定死，否则引用列会加在一张没人读、也从不删除的表上。
5. **内容寻址**：key 内含 `sha256`，同一字节序列天然去重、`Put` 天然幂等，失败重试无需事务协调；代价见 §8.4（整篇覆盖写会产生新对象，这是 `session_data` 不做的直接原因）。
6. **先内容后引用**：写顺序恒为「对象写成功 → 同事务写业务行 + `Acquire`」。崩溃只留下可回收的 `orphaned` 对象，绝不留下悬空引用（备份场景的唯一例外由 §12.3 的备份顺序与宽限期共同封死）。
7. **降级优先于熔断**：对象存储运行期故障只让对象类端点返回明确 503，不做熔断器、不做后台重试队列、不做写缓冲（§11.3）。宁可显式失败，也不要「看起来成功、其实没落盘」。
8. **可恢复性优先于容量优化**：任何落点选择都要能回答「备份谁、恢复谁、恢复后怎么证明一致」。做不到就退回 DB 行内存储。
9. **CLI 简单性优先于平台一致性**：见 §16。

## 4. ObjectStore 抽象与装配边界

### 4.1 命名决策

| 面 | 名字 | 理由 |
| --- | --- | --- |
| Go 包 / 接口 | `internal/objectstore`，接口 `objectstore.Store`，值类型 `objectstore.Ref` | 与「对象存储」这一交付词汇一致；实现落地前改名零成本（当前包不存在） |
| 配置命名空间 | **保留 `platform.blobs.*`**（P8.1 已落地） | `platform.store.*` 已被业务库占用，`platform.storage.*` 会与之混淆；改名要同时动 config、两套模板键集合、清单、`install.sh` 42 参数、`tests/arch` 门禁、部署手册六处，四期不划算。本文与数据字典统一记法：**`platform.blobs.*` 是 ObjectStore 的后端形态参数** |
| 表名 | `objects`（元数据）、`attachments`、`reports` | 表名不叫 `blob_objects`：MySQL 里它是「对象元数据登记表」，`blob` 前缀会误导成「这只是桶的附属表」 |

### 4.2 接口定义

```go
package objectstore

// Ref 是对象的自描述元数据。审计、SSE 事件、日志只允许携带 Ref，不携带内容。
type Ref struct {
	Key       string    `json:"key"`
	SHA256    string    `json:"sha256"`
	Size      int64     `json:"size"`
	MediaType string    `json:"mediaType"`
	UpdatedAt time.Time `json:"updatedAt"`
}

// Spec 描述"要写一个什么对象"，key 由实现端按实际 sha256 组装。
// v1.2 让调用方自己拼带 sha 的 key，等于要求调用方先把整个对象读进内存算摘要，
// 32MiB 附件就是 32MiB 常驻内存；且"调用方拼错 key"只能靠写完再比摘要兜住。
// 改由实现端组装后，流式写入边读边算，边校验 max_object_size。
type Spec struct {
	Category  string   // reports | attachments | exports | sessions（白名单，§5）
	Scope     []string // 命名空间段，逐段按 ValidateKey 段规则校验（如 clusterID/scanID）
	Ext       string   //  ".md" / ".json" / ".png"，参与 key 尾段可读性
	MediaType string   // 空则按 Ext 推断，再空回落 application/octet-stream
	CreatedBy string   // 触发写入的用户 ID；空表示系统任务，落库记 objectstore.SystemActor
}

type Store interface {
	// Put 流式写入：边读边算 sha256，超 max_object_size 立即返回 ErrTooLarge。
	Put(ctx context.Context, spec Spec, r io.Reader) (Ref, error)
	Get(ctx context.Context, key string) (io.ReadCloser, Ref, error)
	Stat(ctx context.Context, key string) (Ref, error)
	Delete(ctx context.Context, key string) error
	// List 按前缀流式回调，回调返回 error 即中止；禁止全量入内存。
	List(ctx context.Context, prefix string, fn func(Ref) error) error
	Driver() string // "db" | "dir" | "s3" | "off"
	io.Closer
}

// Presigner 仅 s3 后端实现；dir/db 走服务端流式下载端点。
type Presigner interface {
	PresignGET(ctx context.Context, key string, ttl time.Duration) (string, error)
}

// Maintainer 由 db/dir/s3 三后端实现：启动期就绪保障（失败即 fail-fast，§11.2）。
//
// GC 刻意不在本接口里声明：它与 blobs 命令组同批交付（P8.9），由 Store + ObjectStore
// 两个原语组合；提前声明只会得到一个没有实现的接口方法（AGENTS.md 禁占位实现）。
type Maintainer interface {
	Ensure(ctx context.Context) error // s3：HeadBucket→CreateBucket 幂等；dir：目录+flock；db：objects 表在位
}

// Probe 只读探测，供存储健康端点使用：只回答"现在能不能用"，不写、不建、不改状态。
// 对象存储不进 /readyz（§11.1）：它故障时基础业务必须继续可用。
type Probe interface {
	Probe(ctx context.Context) error
}
```

### 4.3 哨兵错误

```go
var (
	ErrNotFound    = errors.New("objectstore: object not found")
	ErrTooLarge    = errors.New("objectstore: object exceeds limit")
	ErrKeyInvalid  = errors.New("objectstore: invalid key")
	ErrDisabled    = errors.New("objectstore: backend disabled")
	ErrChecksum    = errors.New("objectstore: sha256 mismatch")
	ErrState       = errors.New("objectstore: invalid object state transition")
	ErrLocked      = errors.New("objectstore: directory backend already in use") // dir flock 冲突
	ErrUnavailable = errors.New("objectstore: backend unavailable")               // 运行期不可达（可重试）
	ErrUnsupported = errors.New("objectstore: operation not supported by backend")
)
```

调用方按 `errors.Is` 分流，禁止字符串匹配。`ErrUnavailable` 与 `ErrNotFound` 的区分是 §11 降级与 §12 对账的前提：**不可达绝不能被误判成「对象不存在」并标成 `missing`**，否则一次网络抖动就会把健康对象判死。

`driver: off` 由 `disabledStore` 实现同一接口，所有写返回 `ErrDisabled`，调用方把附件/报告端点降级为 `503 明确未启用`，不静默丢弃。

**`s3` 后端的判定表（v1.7，P8.4）**：`internal/objectstore/s3.go` 的 `classify` 是唯一认识 `minio.ErrorResponse` 的地方，其余后端按同一语义实现。

| SDK / HTTP 信号 | 映射 | 为什么 |
| --- | --- | --- |
| `context.Canceled`、`context.DeadlineExceeded` | 原样透出 | 那是调用方的意图，不是后端故障，不该计进存储健康度 |
| `NoSuchKey`、HTTP 404 | `ErrNotFound` | 对象确实不在，下载路径据此把元数据行标 `missing` |
| `NoSuchBucket`、`AccessDenied`、`InvalidAccessKeyId`、`SignatureDoesNotMatch`、`AllAccessDisabled`、`ExpiredToken`、HTTP 401/403 | `ErrUnavailable` | 配错桶与凭据失效是**故障**。报成 `ErrNotFound` 会让一次配置漂移把全库对象判成 `missing`，而 `missing` 是不可逆结论 |
| 其余 | `ErrUnavailable` | 认不准就判故障是安全侧：最坏是一次 503，不会误删、也不会误判任何对象 |

SDK 文本先过 `security.Redactor`，再以 **`%s`** 拼进错误而不是 `%w`：一旦进入 `Unwrap` 链，上层打印原始错误串就绕过了脱敏（§13.3）。

### 4.4 import 边界与架构门禁

- `minio-go` 只允许出现在 `internal/objectstore/s3.go`；`os.Open`/`os.WriteFile` 形式的对象读写只允许出现在 `internal/objectstore/dir.go`。
- **`objects` 表的 SQL 单源在 `internal/store`**：落地时把 `db` 内容后端放在 `internal/store/objectcontent.go`（不是 v1.4 设想的 `internal/objectstore/db.go`）。理由是这张表的元数据与正文**同表**，同一条 UPDATE 出现在两个包里早晚有一处漏掉 CAS 条件；把 `*sql.DB` 泄漏进抽象层同样是失败方案。因此抽象层反过来被禁止 import `internal/store` 与 `database/sql`。
- `tests/arch/objectstore_test.go` 已落四条门禁（沿用 `tests/arch/exec_channel_test.go` 的 AST 扫描范式，每条都带「检测规则本身失效也要 FAIL」的反空跑断言）：
  1. `TestObjectStorageSDKImportBoundary`：厂商 SDK（`github.com/minio/*`、`github.com/aws/aws-sdk-go`）只准出现在 `objectstore/s3.go`；
  2. `TestObjectsTableSQLSingleSource`：`objects` 表的 SQL 只准出现在 `store/objects.go`、`store/objectcontent.go`、`store/tx.go`、`store/migrate.go` 四个文件；
  3. `TestReadyzDoesNotDependOnObjectStore`：定义 `handleReadyz` 的文件不得引用 `objectstore`（§11.1 故障隔离的编译期表达）；
  4. `TestObjectStoreDoesNotDependOnStore`：`internal/objectstore` 不得 import `internal/store` 或 `database/sql`。
- 业务模块只依赖接口；`internal/report` 不 import objectstore（渲染与落点解耦，落点由 service 层决定）。

### 4.5 装配位置

`internal/cli/server.go` 与 `openPlatformStore` 同层构造，注入 `server.NewWithPlatform`、`service.NewChat*` 的可选字段（未注入即 `off`），保持既有签名兼容。构造入口是 **CLI 后端白名单的唯一硬拒点**（§16）：`Config.Validate` 没有 mode 上下文，白名单不能下放。

**交付批次澄清（v1.5）**：跨后端工厂 `objectstore.New(cfg)` 随 **P8.4** 一起收口，不在 P8.2/P8.3 半途开。当前只有 `off`/`db` 两个后端，工厂对 `s3` 只能返回一句占位错误，正是 AGENTS.md 禁止的假实现；配置面又已经允许 `driver=s3`，半途工厂等于给合法配置埋一个运行期地雷。P8.2 只交付 `Store.ObjectContent()`（db 后端装配入口，`prefix` 在此过 `NormalizePrefix`，非法前缀挡在装配期）与 `objectstore.NewDisabled()`，P8.3 交付 `dir` 后端本体，P8.4 补齐 `s3` 后一次性把工厂、CLI 白名单硬拒、`replicas>1` WARN 三件事收在同一处。

**工厂已落地（v1.7，P8.4）**：上段的收口承诺已兑现，签名以代码为准。

1. `objectstore.New(cfg Config, openDB func() (Store, error))` 供 server 使用，`off`/`db`/`dir`/`s3` 全允许；`objectstore.NewCLI(cfg Config)` 是 CLI 白名单的**唯一硬拒点**（只允许 `off`/`dir`，其余 `ErrUnsupported` 且点名配置键与本节理由，不猜默认值）。
2. 形态参数是本包自定义的 `objectstore.Config`（`Driver`/`Prefix`/`Dir`/`TmpDir`/`MaxBytes`/endpoint 段/`Replicas`），不是 `internal/config` 的类型——抽象层不认配置文件也不认 MySQL，由装配层逐键翻译，字段名与配置键同义以便一眼核对。改默认 driver 要同时改工厂与 `config.EffectiveDriver` 两处。
3. `db` 后端走**惰性注入**：`openDB` 只在 `driver=db` 时调用，传 `nil` 对其他 driver 安全。用 `dir`/`s3` 的部署不必为了构造一个后端先去开平台库连接池，这是 §4.4 禁止 `objectstore` import `internal/store` 之后唯一干净的接法。
4. `replicas>1` 且 `driver=dir` 的 WARN 收在同一工厂里（`warnReplicas`）：`Replicas` 为 0 表示未知即不告警，避免单测与 CLI 刷无用 WARN；配置面仍不管这件事（`Config.Validate` 无副本上下文，v1.57 已登记）。
5. **本批不接生产调用点**：server 装配随 P8.5/P8.6（与报告写桶同批），`blobs` 命令组与 CLI 侧构造随 P8.9。判据与反对半途工厂是同一条——装配点一旦接上就必须有可验证行为。

## 5. key 规则、命名空间与长度约束

```
{prefix}/{category}/{scope...}/{sha256}{ext}
```

| category | key 模板 | 本期是否写入 |
| --- | --- | --- |
| `reports` | `k8sai/reports/{clusterID}/{scanID}/{sha256}.md` | 是（P8.5）；同 scan 的 md/json 并列两个对象 |
| `attachments` | `k8sai/attachments/{userID}/{sessionID}/{sha256}{ext}` | 否（P8.7 延 v4.2，本期只定结构与 API） |
| `exports` | `k8sai/exports/{userID}/{yyyy-mm}/{sha256}.csv` | 否（只定义，无写入方） |
| `sessions` | `k8sai/sessions/{userID}/{sessionID}/{sha256}.json` | **否**（§8.4 决定四期不实现；白名单保留，避免将来加类时改校验） |

`ValidateKey`（三后端共享，位于 Store 入口，是唯一防穿越闸门）强制：

1. 匹配 `^[a-z0-9._-]+(/[a-z0-9._-]+)*$`；禁止前导 `/`、`//`、`..`、`\`、盘符、URL 编码残留、控制字符。`Spec.Scope` 的每一段进 key 前单独过同一规则，**净化点只有一处**。
2. 总长度 ≤ **191**（沿用 `colText` 约定：MySQL 渲染 VARCHAR(191)、`utf8mb4` 老行格式索引上限 767 字节）。`prefix` ≤ 32，`userID`/`sessionID` 取现网 ID 时最长约 145，留有余量；超长直接拒绝，不做哈希截断。
3. `category` 必须在白名单内。
4. 尾段必须以 64 位十六进制 `sha256` 开头（内容寻址不变量，GC 与去重依赖它）。

`Spec.Scope` 禁止使用用户可控原文（文件名、集群显示名等）——只允许内部生成的 ID；展示名一律只进 MySQL 元数据列，永不参与 key。

## 6. 对象元数据模型（schema v6）

新增列种类 `colBytes`：SQLite `BLOB`，MySQL `MEDIUMBLOB`。落地沿用既有声明式建表（`internal/store/dialect.go` 的 `tableSpec`/`indexSpec` + `d.createTable` 双方言渲染，版本号与表清单同址在 `internal/store/migrate.go`，当前 `schemaVersion = 5`）。

### 6.1 `objects`：对象元数据登记表（**与 driver 无关，恒在 MySQL**）

| 列 | kind | 约束/说明 |
| --- | --- | --- |
| `blob_key` | `colText` | PRIMARY KEY（191 由 `ValidateKey` 保证） |
| `sha256` | `colText` | NOT NULL，索引 `idx_objects_sha` |
| `size` | INTEGER | NOT NULL |
| `media_type` | `colText` | NOT NULL |
| `category` | `colText` | NOT NULL，索引 `idx_objects_category` |
| `driver` | `colText` | NOT NULL：写入时的后端。**混合后端读取的判据**（改配置不清库，旧对象仍要按原后端读） |
| `ref_count` | INTEGER | NOT NULL DEFAULT 0，服务层保证 `>=0` |
| `state` | `colText` | NOT NULL：`ready`/`orphaned`/`missing`/`deleting`（§7），索引 `idx_objects_state_updated` |
| `deleted_at` | 时间 | 逻辑删除时刻（进入 `orphaned` 时写入），GC 宽限期基准 |
| `created_by` | `colText` | 触发写入的用户 ID（系统任务写 `system`）；报告归属靠它（§1 现状 #6） |
| `payload` | `colBytes` | 可空；**仅 `driver: db` 写入**，其他后端恒 NULL。定位是「兼容/兜底后端的正文载体」，不是元数据表的一部分设计 |
| `created_at`/`updated_at` | 时间 | 现有时间列口径 |

元数据与正文同表的唯一理由是省一次 join；`db` 后端下容量闸门因此必须更严（§13.4）。

### 6.2 业务表

```
attachments(id PK, session_id idx, turn_id, user_id, name, blob_key, media_type, size,
            sha256, created_at, UNIQUE(session_id, sha256, name))
reports(id PK, cluster_id idx, scan_id, kind, blob_key, media_type, size, sha256,
        findings, created_by, available, created_at)
sessions  + data_blob_key colText + data_size INTEGER   （默认 ''/0 = 正文仍 inline）
```

- `attachments.name` 只存展示名（服务端净化：去路径、去控制字符、≤191），真名落 key，永不拼路径。`UNIQUE(session_id, sha256, name)` 是上传接口的幂等锚点（§9.1）。
- `reports.kind ∈ {latest-md, latest-json, daily-md}`，一个渲染产物一行；`scan_id` 允许为空（CLI 本地扫描不入表）。`created_by` 由写入方显式带（扫描任务是进程内对象、无 owner 列可继承）。`available` 由 `verify` 维护，`false` 时列表可见但下载返回 410。
- `sessions.data` 列保留不删（兼容 + inline 模式仍用）；两列只在 §8.4 的未来开关下才被读。

### 6.3 `colBytes` 方言三条硬约束（三期 v5 同类坑，别再踩一次）

1. `dialect.go:280` 是 `if c.def != "" && c.kind != colLong`：`colBytes` 必须一并排除，否则 MySQL 渲染出 `MEDIUMBLOB DEFAULT ''` 直接 DDL 失败。
2. `payload` 不可建索引，`ALTER` 走既有 `modifyColumn`；放宽路径必须覆盖 `BLOB`→`MEDIUMBLOB`（SQLite 侧 no-op）。
3. 门禁必须实跑 MySQL：v5→v6 双驱动迁移 + `colBytes` DDL 渲染 + `modifyColumn`（沿用 `K8S_AI_TEST_MYSQL_DSN` 门控，不得长期 skipped）。

### 6.4 事务设施（新增，`Acquire/Release` 的前置）

`internal/store` 今天没有任何事务入口（§1 现状 #7），因此 v6 一并交付最小设施：

```go
// WithTx 在一个数据库事务内执行 fn：fn 返回错误即回滚，返回 nil 即提交。
func (s *dbStore) WithTx(ctx context.Context, fn func(*Tx) error) error

// Tx 只暴露本期真正需要原子写的四个动作，其余 store 接口不动（避免大规模改造）。
// 构造未导出，只能从 WithTx 的回调里拿到：「改引用计数」与「写业务行」在类型层面不可分离。
type Tx struct{ tx *sql.Tx }
func (t *Tx) UpdateSession(ctx context.Context, sess *session.Session) error
// 命中唯一索引 (session_id,sha256,name) 时回写权威 ID 并返回 inserted=false，
// 调用方必须据此跳过 Acquire（§9.1 幂等）。
func (t *Tx) InsertAttachment(ctx context.Context, a *Attachment) (bool, error)
// 报告无幂等唯一索引：同 scan 重跑是合法历史，去重靠内容寻址，ref_count 自然到 2。
func (t *Tx) InsertReport(ctx context.Context, r *Report) error
// 插入或 ref_count++；state=ready，orphaned 顺带复活；命中 deleting 返回 ErrState。
func (t *Tx) Acquire(ctx context.Context, ref objectstore.Ref, driver, createdBy string) error
// ref_count--；归零则 state=orphaned + deleted_at；计数下溢返回错误而非钳零。
func (t *Tx) Release(ctx context.Context, key string) error
```

范围刻意收窄：不改 16 个既有 store 接口签名，不加通用 ORM 层。`db` 后端的 `payload` 写入在 `Put` 内单事务完成，业务行 + `Acquire` 在第二个事务完成——**同库两阶段**，不是跨库分布式事务，失败只产生 `orphaned`。

`WithTx` 带一条必须写进调用方心智的硬约束：**回调内只准用 `Tx` 上的方法**，不得再调 `Store` 的任何非事务入口。SQLite 侧连接池被限成单连接（`OpenSQLite`），事务占着池里唯一的连接，回调里再要一次连接会一直等下去——表现为整请求挂死而不是报错。事务前的读取（幂等判据、归属校验）必须在 `WithTx` 之前做完，把结果带进回调。

### 6.5 引用计数契约

```go
// 引用计数只能经 WithTx 的 Tx 改（见 §6.4）；Store.Objects() 给的是读面与生命周期动作。
type ObjectStore interface {
    // Register 幂等登记：同 key 重放只刷新体积/媒体类型/updated_at，不动 ref_count 与 state。
    Register(ctx context.Context, m *ObjectMeta) error
    Get(ctx context.Context, key string) (*ObjectMeta, error)
    ListByCategory(ctx context.Context, category string) ([]*ObjectMeta, error) // 按 blob_key 排序
    // ListCollectable 返回 state=orphaned 且 deleted_at < olderThan 的行（GC 候选）。
    ListCollectable(ctx context.Context, olderThan time.Time) ([]*ObjectMeta, error)
    // ClaimDeleting 是 §7 约束 1 的 CAS 认领：state/ref_count/deleted_at 三条件全中才置 deleting。
    ClaimDeleting(ctx context.Context, key string, refCount int64, olderThan time.Time) (bool, error)
    MarkMissing(ctx context.Context, keys []string) error   // verify 用，只接受 ready/orphaned
    Forget(ctx context.Context, keys []string) (int, error) // 只删 state=deleting 的行
}
```

`Acquire`/`Release` 只能在 `WithTx` 内调用（编译期用未导出构造保证），`ref_count` 变负直接返回 error 并 ERROR 日志——它是调用方漏配对的信号，不做静默钳零。P5 的 Retention 与 Memory 写入方直接消费这套契约，不重新设计。

两处细节按代码补记：`Register` 与 `insertObject` 是这张表 INSERT 的两个入口，后者单源，带不带正文只差 `payload` 一个实参（`db` 后端传正文、`Acquire` 传 `nil`）；`MarkMissing` 对「行已在 missing/deleting」按可重复执行处理，只有「行确实不存在」才报错，否则一轮 `verify` 会卡在一个早先已处理过的 key 上。

## 7. 对象状态机与删除语义

`objects.state` 只有四个取值，语义全部围绕「MySQL 行是不是活的」这条唯一判据。

| state | 含义 | 进入条件 | 允许的操作 |
| --- | --- | --- | --- |
| `ready` | 活对象：至少一个业务行引用它，或刚写入尚未挂引用 | `Put` 成功、`Acquire` | 读、下载、`Release` |
| `orphaned` | **逻辑删除**：引用归零，进入宽限期等待回收 | `Release` 使 `ref_count` 归零；或对账判定的无引用对象 | 读（仍可服务未提交事务的重试）、`Acquire` 复活、GC 标 `deleting` |
| `deleting` | GC 已认领，即将物理删除 | GC 的 CAS 认领 | 只允许 GC 完成删除；`Acquire` 命中它必须返回 `ErrState` |
| `missing` | 引用还在，但桶/目录里对象没了 | `verify` 或下载路径 `Stat` 返回 `ErrNotFound`（**不是** `ErrUnavailable`） | 读返回 410；`Put` 同内容可修复回 `ready` |

状态迁移（其余组合一律非法，返回 `ErrState`）：

```
(新建) ──Put──▶ ready ──Release→0──▶ orphaned ──CAS认领──▶ deleting ──Forget行──▶ (行消失) ──Delete──▶ (内容消失)
                 ▲                       │                                          ▲
                 └──────Acquire 复活──────┘                                          │
   ready/orphaned ──verify/Stat 命中 ErrNotFound──▶ missing ──重新 Put──▶ ready ────┘
```

四条实现约束：

1. **GC 认领必须是 CAS**：`UPDATE objects SET state='deleting' WHERE blob_key=? AND state='orphaned' AND ref_count=? AND deleted_at<?`，影响行数 0 就跳过本轮。禁止「先 SELECT 再 UPDATE」——`gc` 与 `Acquire` 并发时那是个真实的丢引用窗口。
2. **先删行，再删内容**：认领后先执行 `Forget`（`DELETE ... WHERE blob_key=? AND state='deleting'`），再 `Store.Delete(key)`。这样最坏情况是「行没了、内容还在」（桶扫描可回收）；反过来会造出「引用还在、内容没了」的悬空引用，那是本方案唯一绝不允许的终态。
3. **`ref_count > 0` 永不可删**：CAS 条件里带上 `ref_count`，配合第 2 条，任何误删都要先跨过引用计数。
4. **`missing` 是诊断态不是删除态**：业务行与引用关系全部保留，只把 `reports.available` 置 false。判 `missing` 之前必须确认不是 `ErrUnavailable`（§4.3），否则一次桶网络抖动就能把整批报告打成不可用。

内容层面：S3 无真正覆盖写，`Delete` 只作用于当前版本（本期不要求桶版本化，§23.2）；`dir` 后端删文件；`db` 后端把 `payload` 置 NULL 并保留行（`state=orphaned`），`Forget` 才删行。

## 8. 端到端流程

### 8.1 附件上传（端点契约本期定死，通道实现 P8.7 延 v4.2）

```
POST /api/v1/sessions/{id}/attachments   (multipart: file + 可选 name)
```

1. 鉴权与 owner 判定：复用 `internal/sessionapi` 现有 principal 链路（`requestPrincipal.sessionAccessVia` 的 owner / `chat.read.all` / `chat.manage.all` 三档，`sessionapi/audit.go:97`）。附件不新增权限位。
2. 传输闸门：`http.MaxBytesReader` 按 `max_object_size` 包裹请求体；超限 → 413 统一错误体。
3. 落临时文件（`os.TempDir()`，非 `/data`）：流式 `io.Copy` 边写边算 `sha256`，避免 32MiB 附件全程占内存；扩展名白名单 + 展示名净化（去路径、去控制字符、≤191）。
4. `objectstore.Put(Spec{Category:"attachments", Scope:[userID, sessionID], Ext}, file)`，拿 `Ref`。
5. `store.WithTx`：`InsertAttachment` + `Acquire(ref)` 同事务提交。
6. 事务失败 → 尽力 `Delete(ref.Key)`，失败也不回滚给用户的错误；对象留在 `orphaned`/桶内，由 GC 收（§9.2）。
7. 成功返回附件元数据（id/name/mediaType/size/sha256），**不返回 key、不返回预签名 URL**。
8. `defer os.Remove(temp)`；临时文件异常残留由下次启动清理同名前缀文件兜底。

上传全程不写会话正文：附件只作为 `attachments` 行 + 消息里的附件引用存在，Agent 需要内容时按 `attachment_id` 现取（§13.1 的敏感面由此收敛）。

### 8.2 报告产物写入（P8.5）

`internal/report/writer.go` 现在直接 `os.WriteFile`。改造边界刻意保持最小：**渲染层不感知落点**，由 service 层决定写哪儿。

1. 渲染出 md/json 字节（现状不变）。
2. `report.directory` 继续写现场副本（排障与 CLI 兼容，见 §16）。
3. `Put(Spec{Category:"reports", Scope:[clusterID, scanID], Ext})`。
4. `WithTx`：`InsertReport{Kind, BlobKey, ..., Findings, CreatedBy, Available:true}` + `Acquire`。
5. `Put` 失败：报告行**不写**（不造悬空引用），findings 结构化结论照常入库——这是 §11「对象存储故障不影响基础业务」在写入侧的具体形态；日志 WARN 一条带 `cluster_id`/`scan_id`，不重试。
6. 同 scan 重跑产生新 `sha256` → 新对象 + 新行，旧对象引用不变；历史报告因此天然保留，不需要覆盖语义。

`created_by` 必须由调用方显式传入：`server.go:64` 的 `ScanJob` 是进程内对象、没有 owner 可继承（§1 现状 #6）。

### 8.3 下载与读取

两条路径，按后端能力选：

| 路径 | 适用 | 要点 |
| --- | --- | --- |
| 预签名 URL（`Presigner`，仅 s3） | 大文件、走网关直出 | TTL = `min(presign_ttl, 15m)`；URL 只出现在响应体里，**不落库、不进 SSE、不进审计、不进日志**（§13.3 脱敏） |
| 服务端流式代理 | `dir`/`db`；或不便暴露 endpoint 的现场 | `io.Copy` 直出，不分片不进内存 |

两条路径共同的硬约束：

- 先鉴权再取对象：报告的归属判定见 §13.1；附件跟随会话 owner。
- 响应头强制 `Content-Disposition: attachment; filename*=UTF-8''<净化名>` + `X-Content-Type-Options: nosniff`。报告是 Markdown/JSON，`dir`/`db` 代理路径若放任浏览器嗅探，等于把平台域名变成富文本 XSS 面。
- 元数据在、对象缺（`missing`）→ `410` + 明确「对象已缺失，请重跑巡检或从备份恢复」；后端不可达 → `503` + `Retry-After`。这两个码不能混。
- `Ref.Key` 永不出现在响应里；客户端只认 `id`。

### 8.4 会话正文：四期不外置，改用闸门

v1.2 曾把 `platform.blobs.session_data=true` 当成会话大正文的解法。评审结论是**四期不做**，理由在内容寻址本身：会话每轮都在变，`session_data=true` 下每轮产生一个全新 `sha256` 对象，旧对象立刻无引用进 `orphaned`——写放大没有消失，只是从 MySQL 的行搬进了桶，还额外背上 GC、对账、备份三笔债。

替代方案（全部落在 P8.6，均不依赖对象存储）：

1. **列表不读正文**：`ListSessions` 走 MySQL 索引列（标题/时间/轮数/摘要长度），详情才按 `id` 取整行——这直接消掉 §1 现状 #3 的双线性放大。
2. **`agent.session_max_bytes` 闸门**（默认 12MiB，低于 `MEDIUMTEXT` 的 16MiB）：序列化后超限就**拒绝写库并明确报错**，绝不静默截断（三期 `Error 1406` 静默丢整轮是前车之鉴）。
3. **85% 一次性预警事件**：接近闸门时经 SSE 发一条 warning，让用户知道「该开新会话了」，而不是等到失败。
4. `sessions.data_blob_key`/`data_size` 两列仍建（v6 一并建，成本是一次 DDL），`session_data` 键保留但 `Validate` **硬拒 true**，把开关语义留给真出现「单会话常态超过 12MiB」的场景，届时的正确解法是分段对象 + 引用列表，而不是整篇覆盖。

## 9. 幂等、失败补偿与孤儿回收

### 9.1 幂等矩阵

| 操作 | 重复执行的结果 | 机制 |
| --- | --- | --- |
| `Put` 同内容 | 同一 key；实现端先 `Stat`，命中同 `sha256` 直接返回既有 `Ref`（省一次上传） | 内容寻址 |
| `Put` 命中同 key 但内容不同 | `ErrChecksum` 并 ERROR 日志 | 内容寻址不变量被破坏 = 编程错误，不可降级 |
| 附件重复上传同内容同名 | `UNIQUE(session_id,sha256,name)` 冲突 → 返回既有附件行，不报错、不新增对象 | 唯一索引即幂等锚点 |
| 报告同 scan 重跑 | 新 `sha256` → 新对象新行（非幂等，但幂等性不需要：旧行仍是有效历史） | `kind` 不唯一 |
| `blobs gc` / `blobs verify` | 可重复、可中断续跑 | 全部走 CAS 与只读探测 |

### 9.2 失败补偿矩阵

| 故障点 | 现场 | 收敛方式 | 人工动作 |
| --- | --- | --- | --- |
| `Put` 成功、事务回滚 | 桶里多一个对象，无引用 | 下次 `Put` 同内容命中 `Stat` 直接复用；否则 `gc` 回收 | 无 |
| `Put` 结果未知（连接断） | 可能已写入 | 用同 key 重试：内容寻址下重试天然收敛，不留第二份 | 无 |
| 事务提交成功、响应丢失 | 客户端以为失败 | 客户端重试命中唯一索引，返回同一附件行 | 无 |
| 桶不可达 | 写失败 | 返回 503，**不排队、不缓冲、不假装成功** | 恢复桶后由用户重触发 |
| 报告 `Put` 失败 | findings 已入库、无报告行 | 下次巡检自然补上 | 无 |
| `Forget` 后 `Delete` 失败 | 行没了、内容还在 | 桶扫描（`List` − 表内 key）无条件回收 | 无 |
| 引用在、内容缺 | 悬空引用（异常） | `verify` 标 `missing` + `reports.available=false` → 下载 410 | 从备份恢复桶或重跑巡检 |

「先内容后引用」（§3 原则 6）保证右列人工动作几乎总是空——唯一造出悬空引用的现实路径是备份不一致，见 §12.3。

### 9.3 GC 契约

```
k8s-ai blobs gc [--older-than 168h] [--dry-run]
```

1. `ListCollectable(now - gc_grace_period)` → 逐个 CAS 认领 → `Forget` 行 → `Delete` 内容。
2. `--dry-run` 只打印将回收的 key/size 合计，不动任何东西；生产首轮必须 dry-run。
3. `gc_grace_period` 默认 168h，且必须 **远大于备份窗口**（§12.3），否则「备份中的对象」可能被当成孤儿删掉。
4. 桶扫描差集（只增不漏）：`Store.List(prefix)` 与 `objects` 全表 key 求差，多出来的 key 只在**满足 `ValidateKey` 且首段属于本项目 prefix** 时才允许删，其余一律只报告不删——桶可能与别的系统共用。
5. P5 的 Retention 只实现「按保留策略调 `Release`」，清理执行器复用本节契约，不再设计第二套。

## 10. 后端矩阵与部署形态

| driver | 内容落点 | 适用 | 多副本 | 容量闸门 | 备注 |
| --- | --- | --- | --- | --- | --- |
| `off`（CLI 默认之一） | 不写对象 | 只要结构化结论 | — | — | 端点返回 503「未启用」，不静默丢 |
| `db`（平台默认） | `objects.payload` | 单实例、灰度、没桶可用的现场 | 随 MySQL | 建议 ≤8MiB（validate WARN） | 与业务表争 InnoDB 缓冲池，是**兼容/兜底**定位 |
| `dir` | `platform.blobs.dir` 下按 key 布局 | 单机/离线、PVC 交付 | 跨副本不共享 | `max_object_size` | 必须 flock 独占（`ErrLocked`）；扩副本前必须切 `s3` |
| `s3` | S3 兼容桶 | 生产多副本 | 可 | `max_object_size` | MinIO/Ceph RGW/AWS/国产对象存储 |

切换后端不清库：混合期读取靠 `objects.driver` 列判定走哪个实现取内容（§6.1），`platform.blobs.driver` 只决定**新写入**的去向。这是「改配置即丢历史报告」这类事故的防线。

**`dir` 后端落地事实（v1.6，P8.3）**：`internal/objectstore/dir.go` + `dirlock*.go` 已实现并通过与 `db` 后端同一套 contract 用例，四处与上表口径相关，以代码为准：

1. 正文写入是 `platform.blobs.dir/.tmp` 里的临时文件 → `Sync` → `rename` 到内容寻址名。临时文件**必须与正文同盘**，否则 `rename` 退化成跨盘拷贝，「要么完整要么没有」就不成立了。key 依赖实际摘要，只能先落临时名、读完再 rename；同内容重复 `Put` 落到同一个名字上，天然幂等。
2. 根目录独占锁按平台取原生建议锁（unix `flock` / Windows `LockFileEx`），一律不等待，抢不到即 `ErrLocked` 起不来；没有锁原语的平台 `Ensure` 直接 `ErrUnsupported`。上表「多副本：跨副本不共享」由此从约定变成强制——**扩副本前必须切 `s3`**。
3. 除 key 之外不存旁路元数据，`Ref.MediaType` 由 key 扩展名推导，`Spec.MediaType` 的声明值在 `dir` 无处落地（见 §0.1 第 3 条）。
4. `List` 只认「key 规则拼得出来且是普通文件」的条目：`.tmp` 崩溃残留、别人塞进根目录的杂物、非内容寻址尾段一律跳过，P8.9 的差集才不会把别人的文件当孤儿对象删。`replicas>1` WARN 与跨后端工厂 `objectstore.New` 已随 P8.4 收口（§4.5）。

**`s3` 后端落地事实（v1.7，P8.4）**：`internal/objectstore/s3.go` 已实现并通过与 `db`/`dir` 同一套 contract 用例，五处与上表口径相关，以代码为准：

1. **`Put` 经 `platform.blobs.tmp_dir` 中转发单次 PUT**（默认 `os.TempDir()`）。key 依赖实际摘要，而 S3 的签名与 `Content-Length` 都要求上传前就知道确切长度；不落中转就退化成 Multipart，ETag 变成 `<md5>-N`，§12.2 的校验没法抄近路。中转文件用 `defer` 统一收尾，去重靠「先 `Stat` 再 PUT」，同 key 体积不同直接报 `ErrChecksum`（内容寻址名上出现了别的对象，属于要停机看的事）。
2. 明文 HTTP（`use_tls=false`）下 SDK 对 PUT 体走逐块流式签名，服务端拿不到整包摘要，因此额外发 `Content-MD5`：读的是已落盘的临时文件，SDK 边读边算，不会把 32MiB 上限的正文读进内存；MinIO/Ceph RGW/AWS 都认，摘要不符直接 `BadDigest`。
3. `Get` 必须立刻 `Stat`：SDK 的 `GetObject` 是**懒执行**，不在这里 HEAD 一次，404 会推迟到调用方读第一块时炸在 io 边界上，`ErrNotFound`/`ErrUnavailable` 分流失效（§4.3）。
4. `List` 同样只回调「key 规则拼得出来」的条目：同桶里的他系统对象、控制台建的 `/` 结尾目录占位对象一律跳过，这是 §21「桶内含他系统对象时不误删」的前提。列举失败时**不能 `break`**：SDK 的列举 goroutine 靠 channel 被抽干收尾，提前 break 每次泄一个 goroutine。
5. `Delete` 幂等（重复删同一个 key 不报错），与 `dir`/`db` 同口径；`Close` 只回收连接池空闲连接，不谎称「关闭了与桶的连接」——`minio.Client` 没有 Close 语义，运行中的请求由各自 ctx 管。

## 11. 故障隔离与降级

### 11.1 探针分工（现状只有一个判据，必须区分开）

| 端点 | 现状 | 本方案 |
| --- | --- | --- |
| `/healthz` | 恒 200（`server.go:197`） | 不动 |
| `/readyz` | 唯一 `s.ready`（DB ping 等），2s 超时 → 503 | **不挂对象存储**。挂上去 = 桶抖动摘掉整个 Pod，聊天/审批/审计一起死，直接违反 §2.2 第 2 条 |
| `/healthz` 的组件字段（新增，可选） | 无 | 增加 `components.objectstore.{status,driver,last_error_category}`，只作可观测，不参与任何摘除判定 |
| `GET /api/v1/storage/health`（新增） | 无 | 运维专用：实时 `Probe` + 桶统计（对象数/容量/驱动/最近错误类别）。权限复用 `settings.read`——它已经代表「能看平台运行形态」，不新增权限位；只读、不写、不建桶 |

### 11.2 启动期 fail-fast（分类明确）

| driver | 启动期失败（endpoint 不可达 / 桶不存在且无权建 / 凭据错 / dir 被 flock 占） |
| --- | --- |
| `s3` | **拒绝启动**，日志给 endpoint/bucket 与错误类别（不打印凭据） |
| `dir` | 拒绝启动（目录不可写/被占用） |
| `db` | 随业务库失败与否，本来就会 fail |
| `off` | 跳过 |

启动期严、运行期宽是刻意的：配置错必须装不上，运行期抖动只降级。

**构造期与 `Ensure` 的分工（v1.7，P8.4）**：`NewS3` 不联网，只校验配置形状（endpoint 非空且不含 scheme、桶名过 S3 命名正则、AK/SK 必填、prefix 过 `NormalizePrefix`），错误一律复用 `ErrKeyInvalid` 家族并点名配置键；`NewDir` 不碰文件系统。建目录、抢锁、`BucketExists`/`MakeBucket`、建 `tmp_dir` 统一在 `Ensure`，重复调用幂等，`BucketAlreadyOwnedByYou` 视为成功（并发启动时另一个副本刚建好）。这样 `config validate` 与单测拿到「未启用」后端时零副作用，也不会因为做一次校验就把重试风暴打在一个不可达的桶上。`Probe` 只回答「现在能不能用这个桶」：不建桶、不写对象，桶不存在按 `ErrUnavailable` 而不是「对象不存在」。

### 11.3 运行期降级

1. 只降级对象类端点：报告列表/下载、附件读写、storage health → 明确 503 + `Retry-After`；其余一切照常 200。
2. **不做熔断器、不做后台重试队列、不做写缓冲**。写路径失败就是失败（§3 原则 7）。
3. 不重试建连风暴：单次请求内最多一次重试（幂等 GET/Stat），写路径不自动重试。
4. 巡检扫描、审批、审计、聊天、设置完全不 import objectstore（§4.4 门禁），因此隔离性是**结构保证**，不是靠运行时兜底。
5. **目录后端的「盘不见了」按不可用处理**（v1.6，P8.3）：`Get`/`Stat`/`Delete` 在报 `ErrNotFound` 之前先确认根目录在位，`List` 在开始扫描之前先 `Probe`。整块盘或 PVC 消失了必须报 `ErrUnavailable`——报成 `ErrNotFound` 会让 §12 对账把全部对象判成孤儿、让 §7 下载路径把健康的元数据行标成 `missing`，这是本方案最贵的一类误判；反过来把「盘还在、对象不在」报成 `ErrUnavailable` 也一样错，那只是普通 404。
6. **`s3` 的不可达判定与超时（v1.7，P8.4）**：错误分类见 §4.3 的判定表，认不准一律 `ErrUnavailable`。传输层显式建超时（拨号与 TLS 握手 10s、响应头 30s、空闲连接 90s），不复用 `minio.DefaultTransport`——内网 MinIO 常见「配了地址却连不上」，没有拨号与响应头超时的话一次 `Stat` 能挂到内核 TCP 超时（分钟级），把下载请求的 ctx 拖成摆设。SDK 内部重试关成 `MaxRetries=1`：一次业务请求里的重试由调用方超时兜着，不由 SDK 翻倍（本条是 §11.3 第 3 点的构造期实现）。

## 12. 一致性对账与备份恢复

### 12.1 不变量与破坏来源

不变量：**每个 `ready` 的 `objects` 行，桶里有同 key、同 size、同 sha256 的内容**。

破坏来源只有四种：桶侧被人为删/桶被回滚到旧快照、MySQL 恢复点早于桶（新对象在桶、引用不在库 → 孤儿，可接受）、MySQL 恢复点晚于桶（引用在库、内容不在桶 → **悬空，必须避免**）、写路径 bug。

### 12.2 `blobs verify`

```
k8s-ai blobs verify [--deep] [--strict] [--category reports]
```

| 模式 | 动作 | 代价 |
| --- | --- | --- |
| 默认 | 引用→对象：逐个 `Stat`，比 `size` | HeadObject × 行数，可全量跑 |
| `--deep` | 下载重算 sha256 比对 | 全量读流量，只在恢复后或抽查用 |
| `--strict` | 任一不一致即非零退出 | 用作恢复准出门禁 |

顺带做反向扫描（§9.3 第 4 条）：桶有、表无 → 报告为待回收孤儿，`--strict` 下同样非零退出。

`Stat` 返回 `ErrUnavailable` 时**必须中止而非标 missing**（§4.3）；`verify` 只在能确认「桶可达」的前提下才有资格下结论。

**ETag 不能当校验值**：S3 的 ETag 单次 PUT 是 MD5、分片上传是 `<md5>-N`，两者都不等于我们的 sha256。`--deep` 只能下载重算，别拿 ETag 抄近路。

### 12.3 备份矩阵与顺序（关键结论）

| 对象 | 手段 | 责任 |
| --- | --- | --- |
| MySQL | `mysqldump --single-transaction` / RDS 快照 / binlog PITR | 业务与元数据的唯一权威 |
| 桶 | `mc mirror` / 厂商复制 / PVC 快照 | 内容 |
| `report.directory` 副本、`/tmp`、`/data/sessions`（P8.0 后） | **不备份** | 不是事实源 |

**顺序固定：先备份 MySQL，再备份桶。**

推导：设库备份点 T1、桶快照点 T2。先库后桶 ⇒ T1 ≤ T2 ⇒ 库里每条引用在备份桶里都存在（对象只在引用之前写入），差异只可能是「桶里有、库里没有」= 孤儿 = 可回收。反过来先桶后库就会造出悬空引用，而悬空引用**不可修复**（内容已经没了）。

推论：`gc_grace_period`（168h）必须远大于「库备份到桶快照完成」的窗口，否则窗口内的对象可能被 GC 收走，而它正躺在已经备份的桶快照之外。

### 12.4 恢复流程（七步）

1. 恢复 MySQL 到目标点。
2. 恢复/镜像桶到 **≥ 库恢复点** 的状态（宁可多，不可少）。
3. 起服务前 `k8s-ai db migrate`（schema 必须 ≥ 备份时的 v6）。
4. `blobs verify`（必要时 `--deep --strict`）。
5. `blobs gc --dry-run` 看差异规模，再实跑回收孤儿。
6. 检查 `reports.available=false` 清单：可重算的重跑巡检，不可重算的走内容备份。
7. 抽样下载一份报告 + 一条会话，确认读路径与 `Content-Disposition` 正常。

**RPO 不对称**要写进运维口径：MySQL 丢了可以从 binlog 追平，**附件与报告内容丢了无法重算**（findings 结构化结论可以重渲染成新报告，但历史那份字节变了）。因此桶的镜像频率必须不低于业务对「历史报告可追溯」的要求，做不到就明确记录为可接受损失。

## 13. 访问控制、凭据与大小限制

### 13.1 category × 角色矩阵

| category | 读端点 | 权限判定 | 写端点 |
| --- | --- | --- | --- |
| `reports` | `GET /api/v1/reports`、`GET /api/v1/reports/{id}/content` | 新增权限位 `report.read`，种子授予 operator/admin；`user` 只能读 `created_by` 是自己的 | 无（由巡检任务写入，`created_by` 取触发者或 `system`） |
| `attachments` | 会话详情内的附件 | 跟随会话 owner（ADR-037 三档：owner / `chat.read.all` / `chat.manage.all`），**不新增权限位** | `POST /api/v1/sessions/{id}/attachments`（v4.2） |
| `exports` | 无端点 | 只预留 category | 无 |
| `sessions` | 无对象端点 | 四期不外置（§8.4） | 无 |

落地面（现有代码只有 15 个权限位，新增要同时改三处，漏一处就是 403 或漏门）：

1. `internal/permission/permission.go` 增常量 `ReportRead = "report.read"`。
2. `internal/server/permission.go` 的 `DefaultAPIPolicy()` 登记两条 reports 路由 —— **不登记就在网关处 403**（deny-by-default，`permission.go:86`），这是最容易漏的一处。
3. `internal/auth/service.go` 的 `defaultRoles()` 给 operator 加该位（admin 已是 `*`）；`reconcileRoles` 会在下次启动把权限口径纠正到设计值，所以**手工给内置角色加的权限会被覆盖**——要长期自定义只能建自定义角色，这条写进部署手册。

注意 `GET /api/v1/sessions*` 走 `newRootHandler` 的会话分支（`cli/server.go:170`），不经 `DefaultAPIPolicy`；附件端点因此要在 sessionapi 侧单独登记门，别指望平台策略表兜住它。

### 13.2 预签名 URL

- TTL = `min(platform.blobs.presign_ttl, 15m)`（运行期上限是常量 `MaxPresignTTL`，v1.7 落地）；配置面另有 24h 硬上限（`blobs.go` 的 `maxBlobPresignTTL`），三重收紧。`PresignGET` 的 `ttl <= 0`（含未配置）取上限而不是报错：预签名是读路径上的便利件，因为调用方忘传 ttl 就让它失败，代价落在用户身上。
- **离线可签的前提是显式 `region`**：未给 region 时 SDK 会为签名先打一次 `GetBucketLocation`，桶不可达时连签发 URL 都失败。§14 的 `region` 默认值因此不是占位而是必要项，换现场桶要一起改。
- 只在响应体里出现；**不写库、不发 SSE、不写审计、不打日志**。审计只记「下载了哪个 id」。
- 只支持 GET。presigned PUT 直传本期不做（§23.2）：它绕过 `MaxBytesReader` 与 owner 校验，收益不抵风险。
- 预签名 URL 泄露 = 该对象在 TTL 内公开可读，这是 S3 语义决定的既成事实，因此对「同一对象多次分发」要有节制：TTL 默认取短。

### 13.3 凭据与日志脱敏

- AK/SK 只经环境变量 / Secret 注入；配置文件出现明文只 WARN（沿用 `blobs.go` 的 `Diagnostics` 口径，不 fail，便于现场排障）。
- `internal/objectstore` 必须把 SDK 错误经 `security.Redactor` 过滤再向上抛：SDK 错误串里常带 URL 与凭据。**v1.7 实落两条正则即覆盖上述全部目标**（`internal/security/redact.go`）：一条覆盖 `x-amz-(signature|credential|security-token|date|algorithm)` 的 `=` 与 `:` 两种形态（头部写法与 query 写法都吃），一条覆盖预签名 URL 查询串里的 `[?&;](signature|awsaccesskeyid|accesskeyid|credential)=`。`Authorization:` 早被既有条目覆盖，不重复添加。
- **错误包装纪律**：`classify` 把脱敏后的 SDK 文本以 `%s` 拼入错误而不是 `%w`。哨兵语义靠 `%w: ` 前缀那一份就够，SDK 原文进了 `Unwrap` 链就会被上层原样打印，脱敏白做（§4.3）。
- 断言写进门禁测试（§21），别靠 code review 记着。

### 13.4 三层大小闸门

| 层 | 参数 | 默认/上限 | 超限行为 |
| --- | --- | --- | --- |
| HTTP 入口 | 网关 + `http.MaxBytesReader` | = `max_object_size` | 413 统一错误体 |
| 对象层 | `platform.blobs.max_object_size` | 默认 32MiB / 硬上限 256MiB；`db` 后端建议 ≤8MiB（validate WARN） | `ErrTooLarge`（流式，边读边算，不先攒内存） |
| 会话正文 | `agent.session_max_bytes`（新增） | 默认 12MiB（< `MEDIUMTEXT` 16MiB） | 拒绝写库 + 明确报错（§8.4） |

三层各有不可替代的职责：入口层防打爆进程，对象层防单对象失控，会话层防业务行超列宽。`agent.session_max_bytes` 要进 `platformStaticEngineKeys`（`keys.go:49`）——它是平台静态键，不加白名单会被 `config validate --mode server` 判成未识别键。

`db` 后端还多一道**列宽闸门**：`store.ObjectContentLimit` 把配置值与 `MEDIUMBLOB`（16MiB-1）取小，配置写得比列宽大就按列宽收紧。静默按更小的值执行是最难排查的一类配置失效，因此装配层要把收敛后的值和配置值比一次、不等即打 WARN 点名「配置写的是 64MiB，但 db 后端只吃 16MiB-1，要放大请换 dir/s3」；闸门函数随 P8.2 已落地；**WARN 到 v1.7 仍未接线**——工厂已实现但没有生产调用点，装配接线与这条 WARN 一并随 P8.5（§4.5、§6.1、§10）。

`s3` 后端的体积闸门在**落盘中转阶段**生效（v1.7）：`Put` 由 `StreamHash` 边读边计数，读到超过 `max_object_size` 的那一刻就断并返回 `ErrTooLarge`，此时一个字节都没进桶，不存在「先传一半再失败」的中间态对象。

## 15. 生命周期与清理

本期只做三件有真实需求的事：

1. **对象层**：`blobs gc`（§9.3）回收引用归零且过宽限期的对象。
2. **业务层**：P5 的 Retention 按保留策略调 `Release`（删除过期审计/Turn/报告行），执行器复用同一契约。
3. **报告层**：同 `cluster_id + kind` 可只保留最近 N 份（默认全留），收敛动作同样走 `Release` 而不是直接删内容；保留份数属 P5 的 Retention 策略配置，本方案不新增配置键。

明确不做（理由见 §23.2）：冷热分层与存储类别转换、桶生命周期规则托管、跨区复制、桶版本化强制、按分类的多 Bucket 调度。现场要省成本就在桶侧配厂商的生命周期规则——**桶策略管物理寿命，MySQL 管逻辑存在性**，两者冲突时以 MySQL 为准（`missing` + 410 是可接受结果，静默返回错内容是灾难）。

## 16. CLI 零影响硬约束

CLI 二进制必须继续是「一个可执行文件 + 一个 `~/.k8s-ai` 目录」，不依赖 MySQL、不依赖桶：

1. CLI 只允许 `platform.blobs.driver ∈ {off, dir}`；`cliPlatformKeys`（`keys.go:59`）已经只放行 `driver`/`dir` 两键。
2. **构造入口硬拒（`objectstore.NewCLI`，v1.7 已实现）**：CLI 装配路径只允许 `off|dir`，拿到 `db`/`s3` 直接返回 `ErrUnsupported` 并点名配置键与本节理由，不猜默认值。`Config.Validate` 没有 mode 上下文，这个白名单不能下放到 config 层。调用点随 `blobs` 命令组接入（P8.9），见 §4.5。
3. `~/.k8s-ai` 整目录自洽：会话、审计、附件、报告产物全在目录内，`mv` 走就能搬迁，无外部状态。
4. blob 写失败在 CLI 侧只 WARN，绝不丢本地产物（引擎侧失败隔离的老口径不变）。
5. `config validate --mode cli` 对 `platform.blobs.*` 的多余键继续点名告警。

## 20. 兼容、迁移与回滚

1. **schema v5 → v6**：只建三张表（`objects`/`attachments`/`reports`）+ `sessions` 加两列，无 backfill、无数据搬迁、无停机窗口。`schemaVersion` 从 5 升到 6（`migrate.go:11`）。
2. **升级即无感**：默认 `driver=db` 且没有写入方（P8.5 前报告不落对象），未启用环境升级后的行为逐字节不变——这条要有回归测试兜（§21 最后一条）。
3. **回滚**：`driver` 改回 `db`（或 `off`）并重启即可；已入桶的对象与行都留着，`objects.driver` 保证混合期仍可读。表结构不需要回滚（列都可空、表是新增）。
4. **P8.0 的兼容（v1.4 按实现写实）**：会话切 DB 权威时提供一次性 `k8s-ai migrate --platform --sessions-dir <目录>` 兜底导入（`internal/service/migrate.go`）。`--platform` 按 `platform.store.*` 连平台库、与显式 `--db` 互斥，MySQL 现场不必临时造 SQLite 文件；`k8s-ai db migrate` 仍只升 schema，不承担数据导入。整轮零失败后按目录打「已导入」标记，重复执行整类跳过并给出 `--force` 提示——否则平台上已删除的旧会话会被下一次 migrate 从旧文件里复活，「删除」就不是终态。平台模式启动时若 `session_dir` 里还有 `.json`，INFO 点名文件数与上面的导入命令，不静默忽略。
5. 不做双写灰度：会话读写一旦切 DB，就不保留「读文件失败回落 DB」的路径——双读必然造成两套真相，正是本方案要消除的东西。

## 23. 决策清单

### 23.1 已定（本轮评审落定，不再讨论）

| # | 决策 |
| --- | --- |
| 1 | 双存储：MySQL = 业务数据 + 对象元数据唯一权威；对象存储只承载内容；容器卷永不作事实源 |
| 2 | 先做 P8.0（会话事实源收敛），再做对象存储；顺序不可颠倒 |
| 3 | 包名 `internal/objectstore`，配置命名空间保留 `platform.blobs.*`，表名 `objects`/`attachments`/`reports` |
| 4 | `Put(Spec, r)` 由实现端按实际 sha256 组 key（不让调用方拼 key） |
| 5 | 状态机四态 + 逻辑删除 + GC 两段式（先 `Forget` 行再删内容） |
| 6 | `store.WithTx` + 收窄 `Tx` 方法集，不改 16 个既有 store 接口 |
| 7 | `/readyz` 不含对象存储；启动期 fail-fast、运行期只降级对象端点；无熔断/无重试队列/无写缓冲 |
| 8 | 备份顺序固定「先 MySQL 后桶」；`gc_grace_period` ≫ 备份窗口；恢复后 `verify --strict` 准出 |
| 9 | 会话正文四期不外置；`session_data` 硬拒 `true`；改走 `agent.session_max_bytes` 闸门 + 预警 |
| 10 | `db` 后端是兼容/兜底定位，有效上限建议 ≤8MiB（WARN 不硬拒） |

| 12 | 附件不新增权限位（跟随会话 owner）；报告新增 `report.read`；storage health 复用 `settings.read` |

### 23.2 暂不实施（含理由，将来按新需求重启评估）

| 能力 | 不做的理由 |
| --- | --- |
| 多 Bucket / 租户级桶隔离 | 单副本单租户形态下没有隔离需求；桶数一多，备份与权限矩阵成倍复杂 |
| 冷热分层、存储类别转换 | 没有容量数据支撑选型；先让 `verify`/统计把体量测出来 |
| 跨区复制 | 无多地域部署需求 |
| 桶生命周期规则托管 | 物理寿命交给现场桶策略（§15 的分工） |
| 强制桶版本化 | 内容寻址已保证不覆盖写；版本化会让 GC 与备份语义复杂化 |
| SSE-C / KMS 客户端加密 | 敏感数据红线在应用层（Secret 值永不落对象），不在桶侧 |
| 对象锁 / WORM | 无合规留单需求；有需求时与桶策略一起谈 |
| presigned PUT 直传 | 绕过 `MaxBytesReader` 与 owner 校验，收益不抵风险 |
| 分片上传 / 断点续传 | 单对象上限 32MiB（硬上限 256MiB），用不上；引入后校验与幂等都要重做 |
| CDN 分发 | 内网交付场景 |
| 会话正文整篇外置 | 内容寻址下等于把写放大搬进桶（§8.4） |
| Skill assets 外置 | 技能包量级小、走文件/DB 足够 |
| 向量 / 嵌入存储 | 属 RAG 议题，与本方案无关 |
| `no_s3` slim 构建 | 需要假实现才能编过；构建矩阵翻倍 |
| 多副本扩缩前置（SSE sink / `ProposalStore` 外移） | 属 D-19/D-20 的多副本专项，不能被存储方案夹带 |
