# k8s-ai 四期方案：容器执行通道与镜像基座（P6.3）

- 版本：v1.1（2026-10-29）
- 状态：**已签收**（2026-10-29，用户口径「安全重要，但平台已有能力不能因为部署在 K8s 里就丢失；shell 排查很需要；市面 Agent 普遍权限大、靠人审批兜底」）。改写 **ADR-044 v1.1** 与决策基线 **D-33**，实现归 **P6.3**（0.75d → **1.0d**，顺序提前到 `P8.1` 之前，理由见 §9）。
- 关联：ADR-006（D-06 写执行口径，本次同步修订措辞）、ADR-041 v1.1（镜像可复现构建）、ADR-043（存储边界，不受本方案影响）、AGENTS.md「Kubernetes Safety」与「Executor 唯一写入口」、部署手册 §2.2/§4.16/§4.17
- **一句话口径**：默认交付镜像自带 `/bin/bash` + coreutils + `jq` + `curl` + `kubectl`，**容器内 shell 通道默认可用**；安全不靠「镜像里没工具」，靠「含 shell 语法的命令必须真人审批 + 真实权限由集群 RBAC 决定 + 输出脱敏与全量审计 + Pod 加固」。`platform.exec.shell_enabled` 默认 `true`，硬合规现场可关并用无 shell 变体镜像；「按需执行 Pod」不再是 shell 的替代路径，降级为多租户隔离议题留五期。

---

## 1. v1.0 → v1.1 口径翻转的理由

| 维度 | v1.0 口径（distroless + shell 策略级关闭） | 问题 | v1.1 口径（工具齐备 + 审批闸门） |
| --- | --- | --- | --- |
| shell 命令 | 容器内一律显式拒绝，返回可指导文案 | 日志聚合、`grep`/`awk`/`sort` 再 `uniq -c` 计数、heredoc 建资源这类排障动作在 K8s 形态下整体不可用，等于部署形态阉割了本地 CLI 已有的能力 | shell 通道默认可用，命令仍走人工审批，能力与本地 CLI 对齐 |
| kubectl 来源 | initContainer 投递 + `K8S_AI_KUBECTL_PATH` 指向 | 多一个投递容器与一份现场镜像依赖，交付清单变复杂，现场还得 mirror 一个 kubectl 镜像 | 构建期按 checksum 内置进主镜像，零部署步骤 |
| 安全模型 | 靠「没有解释器」保证不可执行 | 属于障眼法级控制：LLM 真正的危险动作是写命令，靠审批与 RBAC 拦；没有 shell 只是让排障变瞎 | 审批、RBAC、红线、脱敏、审计一条不少，用 Pod 加固与可选 NetworkPolicy 收住容器侧风险 |
| 完整管道需求 | 指向方案 B（按需执行 Pod） | B 需要 `pods/exec` RBAC、第二镜像、TTL 回收，私有化现场比「不开 shell」更难批 | B 降级为五期多租户隔离议题；工具齐备后四期无此需求 |

一句话：**权限大不是问题，无闸门才是问题**。AGENTS.md 只要求「含 shell 构造的命令必须经真人审批、`--skip-permissions` 不覆盖」，从未要求镜像内不存在 shell；v1.0 把 D-06 读成「物理关闭」，属于我们自己加的约束，本次一并纠偏。

## 2. 现状（逐条可核对）

| # | 现状 | 证据 | 后果 |
| --- | --- | --- | --- |
| 1 | 交付镜像运行阶段是 `gcr.io/distroless/static-debian12:nonroot`，无 `/bin/sh`、无 `bash`、无 kubectl | 仓库根 `Dockerfile` 末段 | 任何依赖二进制的执行分支只能在运行时 `exec` 那一刻失败 |
| 2 | shell 分支硬编码 `exec.CommandContext(ctx, "bash", "-c", command)` | `internal/executor/kubectl.go:65` | 容器内报 `exec: "bash": executable file not found`，原文回给 LLM 诱发重试，语义误导（LLM 以为是权限问题） |
| 3 | argv 分支只在 `bin == "kubectl"` 时 `exec.LookPath("kubectl")` | `internal/executor/kubectl.go:42` | 同上，报 `kubectl not found in PATH`；结构化工具层有降级提示，kubectl 工具本身没有 |
| 4 | `kubernetes.kubectl_path` 已存在（空=PATH 查找） | `internal/config/config.go:35`，注入点 `internal/service/chat.go:318` → `executor.Options.KubectlBin` | 内置 kubectl 后无需改动；该键保留给自定义路径与非容器场景 |
| 5 | 交互式动词与 `exec -i/-t` 在解析层拒绝；非交互 `kubectl exec pod -- <cmd>` 允许（按写操作走审批） | `internal/executor/parse.go:27`、`:215` | 有 shell 后「进 Pod 看文件、跑只读诊断命令」的能力本就存在，不需要为它引入方案 B |
| 6 | 审批、Scope、SAR 判定全部在 tool 执行之前 | `internal/agent` + `internal/approval` + `internal/permission` | 命令最终在哪个容器里跑，不改变任何一条闸门语义 |

## 3. 四种形态先分清

| 形态 | 起什么 | 生命周期 | 结论 |
| | --- | --- | --- |
| 主镜像内置工具 | 服务容器自带 bash/coreutils/jq/curl/kubectl | 与服务进程同生命周期 | **本方案 A（默认，本期实现）** |
| 无 shell 变体镜像 | `Dockerfile.distroless` 产物 | 同上 | **本方案 A′（可选交付件，硬合规现场）** |
| 按需执行 Pod | 独立 ns 里带工具的普通 Pod，经 `pods/exec` 跑命令 | 首次需要时创建，空闲 TTL 或会话结束删除 | **方案 B：五期多租户隔离议题，本期不实现**（§7） |
| ephemeral debug container | 往别人的业务 Pod PATCH `pods/ephemeralcontainers` 加调试容器 | 不可删除，随宿主 Pod 消亡 | 方案 C，否决（污染业务 Pod、不可回收） |

内部同类产品 issuepilot 走的是「按需执行 Pod」且更重（每 Runtime Session 一个双容器常驻 Sandbox Pod + 预热池 + 容量调度 + Access Gateway 注入凭据，见其 ADR-0006/0007/0008/0015/0016）。它的服务镜像与执行容器镜像分离，执行容器就是 `debian:bookworm-slim` + bash/coreutils/jq + kubectl/helm/python，这恰好印证 v1.1 的取舍：**Agent 需要的是一套齐备工具箱加一套闸门，而不是一个没有解释器的镜像**。我们比它轻的地方是不搬预热池、容量调度与 Access Gateway。

## 4. 决策（v1.1，本期落地）

1. **运行阶段基座换 `debian:bookworm-slim`**，内置 `bash`、coreutils、`grep/sed/awk/sort/uniq/head/tail/wc/diff`、`jq`、`curl`、`ca-certificates`、`dnsutils`/`iputils-ping`、`less`；`kubectl` 在构建阶段按 `KUBECTL_VERSION` 下载并做 sha256 校验（`KUBECTL_DOWNLOAD_BASE` 可指内网 mirror，按 `TARGETARCH` 取架构），`apt-get clean` 并删 `/var/lib/apt/lists` 收体积。预计镜像 20MB → 约 180MB，离线交付 mirror 一次即可。
2. **保留非 root 运行**：镜像内建 `k8sai`（uid/gid 65532）用户并 `USER 65532:65532`，与现有 `runAsNonRoot` 清单一致；工具落在 `/usr/local/bin`、`/bin`，只读根文件系统不影响执行。
3. **保留无 shell 变体**：新增 `Dockerfile.distroless`（即 v1.0 形态），交付给安全基线明确禁止容器内 shell、或入口直接暴露公网的现场，配 `platform.exec.shell_enabled=false`。两个 Dockerfile 共用同一构建阶段，只差运行阶段与工具层。
4. **`platform.exec.shell_enabled` 默认 `true`**：仍保留这个静态开关。`=false` 时在 `Runner.RunKubectl` 判定为 shell 命令后、**构造 `exec.Cmd` 之前**返回可指导的工具级文案（不是 Go error 冒泡），`LookPath` 失败文案同步改写。启动时探测 `bash`/`kubectl`：开启态缺失打 WARN，关闭态打 INFO，都不阻塞启动（读链路不依赖它们）。
5. **清单侧加固**（`deploy/{allinone,separated}` 两个 Deployment）：`runAsNonRoot: true` + `runAsUser: 65532`、`allowPrivilegeEscalation: false`、`capabilities.drop: ["ALL"]`、`seccompProfile.type: RuntimeDefault`、`readOnlyRootFilesystem: true` 且补 `/tmp` 与 `/home/k8sai`（kubectl 发现缓存写这里）两个 emptyDir、`resources.requests/limits`；`deploy/example/networkpolicy.yaml` 给「只出站 API Server / LLM 网关 / MySQL」的可选样例。
6. **明确不做**：页面上传 kubectl 二进制（体积大、无完整性校验、需可执行挂载位、滚动更新要重传）；把 `helm`/`python`/`node` 等运行时塞进默认镜像（CVE 面与体积换不来当期收益，确有需求另做工具变体 tag）。

## 5. 安全模型：工具齐备之后靠什么收口

| 风险路径 | 现有约束（全部已实现，本方案不改） |
| | --- |
| LLM 发起写操作（delete/scale/patch/apply 等） | `Policy.Evaluate` 判为写 → 人工审批；`--skip-permissions` 与 `require_approval=false` 均不免除 shell |
| LLM 用 shell 构造绕过分类 | 引号外出现管道、串联、重定向、命令替换等元字符即标 `IsShell`，shell 永不自动执行、永不进 grant 命中 |
| 读 Secret 内容值 / `--raw` | `IsForbiddenCommand` 硬拒（AGENTS.md 红线），只允许元数据与键级读取 |
| 白名单外的危险动词 | `deny_ops` 与 `edit/attach/port-forward/proxy/run/cp/debug/auth/plugin`、`exec -i/-t` 在解析层拒绝 |
| 越出授权 namespace | Scope-aware Agent 在工具执行前按 namespace/cluster 拦截，越界不执行也不进审批 |
| 容器被攻破后横向使用集群身份 | ClusterRole 默认只 `get/list/watch` + `pods/log`，不含 `pods/exec`/`portforward`/`attach` 与写权限；写权限是现场显式 apply 的动作 |
| 敏感数据外泄到会话/报告/审计 | 工具输出统一脱敏后才进 LLM 上下文、会话落库与审计 |
| 全链路可追责 | 命令原文、审批人、风险等级、执行结果写审计 |

**残余风险（诚实登记，不靠隐藏工具回避）**：① 镜像 CVE 面与体积上升，纳入交付前镜像扫描基线；② 容器内具备本地命令执行能力，意味着进程可读写它挂载的 kubeconfig、可访问集群内网络，因此 §4.5 的加固项是必配，开放环境建议启用 NetworkPolicy；③ shell 命令的真实破坏力取决于现场 RBAC，交付文档必须写明「给了写权限就是给了真实破坏力」，该口径已在部署手册 §4.16。

## 7. 备选方案 B（五期，多租户隔离议题）

主镜像工具齐备后，B 的「补 shell 能力」理由消失，剩下的价值只有**爆炸半径隔离与 per-session 降权**。要做必须连身份一起做，否则 B 在安全上严格劣于 A：exec Pod 若挂平台 SA，权限与平台完全相同且多一个常驻可执行体；只有用 TokenRequest 派生 per-session 短效身份 + 派生 Role，才是更小权限。届时需新增第二执行镜像、`pods create/get/list/delete` + `pods/exec create` RBAC、冷启动等待、输出限额与流式截断、会话亲和、空闲 TTL 与泄漏回收，估 1.5d 以上并含真机 RBAC 验证。触发条件写清：**只有出现多租户共用平台、需要按会话降权或按租户限域时才排期**。

借鉴 issuepilot 的三条轻量语义（不搬架构）：执行环境不持长期凭据；起环境前先消费审批并冻结资源额度快照；沙箱只允许出站 API Server。明确不采纳：预热池、全局容量调度、Workspace 检查点恢复、自建 Access Gateway + kube-oidc-proxy、把结构化工具链换成通用 `exec_command`。

## 8. 测试与验收

1. 单测：`shell_enabled=false` 时含管道命令返回可指导文案且不 fork 进程（用不可存在的 `bin` 证明未进 `exec`）；`=true` 时 argv 与 shell 两条路径行为不回退；启动探测在二进制缺失时只打日志不报错。
2. `tests/arch`：shell 执行点唯一性红线 + 闸门包裹断言。
3. 构建断言：默认镜像内 `/bin/bash`、`jq`、`kubectl version --client` 可用且运行 uid=65532；`Dockerfile.distroless` 产物内 `/bin/sh` 不存在。
4. 容器内冒烟（**人工**，真机）：`kubectl get deploy -A` argv 成功；`kubectl get pods -A -o json | jq -r ...` 经批准后成功；`kubectl logs ... | grep ... | sort | uniq -c` 经批准后成功；关闭态返回可指导文案；一次写操作经审批后仍成功（证明写通道未被误伤）；`readOnlyRootFilesystem` 下 kubectl 发现缓存写入不报错。
5. 镜像扫描：默认镜像 CVE 报告随交付归档，HIGH/CRITICAL 逐条给处置结论。

## 9. P6.3 交付物与顺序（0.75d → **1.0d**）

1. `Dockerfile` 基座与工具层改造 + `Dockerfile.distroless` 变体 + 构建参数。
2. `platform.exec.shell_enabled`（默认 `true`）+ validate + 两套模板键集合。
3. executor 闸门、两处可指导文案、启动探测。
4. `tests/arch` 红线 + 单测三态。
5. 两形态 Deployment 加固与 `deploy/example/networkpolicy.yaml`。
6. 冒烟记录（§8.4 六条）+ 部署手册 §2.2/§4.16 更新与 §4.17「容器内执行通道与镜像分档」新增。

**顺序调整**：P6.3 提前到 `P6.12 剩余项` 之后、`P8.1` 之前执行。它改的是镜像基座，先做完，下一次人工构建就自带 shell 与 kubectl，避免为同一件事构建两轮镜像。
