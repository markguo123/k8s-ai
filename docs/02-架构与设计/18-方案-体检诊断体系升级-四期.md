## 2. 十段核心流水线与 13 项阶段账

主链路对外表达为九段（与架构图方框一一对应）：

```text
资源采集 → 规则引擎 → 资源关系分析 → 关联分析 → 故障聚合
        → 确定性诊断 → LLM 增强（可选）→ 结果校验 → 报告生成
```

实现上在「规则引擎」与「资源关系分析」之间还有**第十个内部阶段** `evidence`
（按需证据采集：只对规则判出的异常对象取 Pod 日志）。它不进对外九段，因为它不产出
新结论，只是把规则声明需要的证据补齐；但它有独立耗时、独立失败面（日志权限、超时），
所以阶段记录里单独一行，Web 与 CLI 都看得见。

`StageRecord` 不是十项：真机复验后补齐了流水线外的三个真实执行步骤
`connect`（连接集群）、`write`（写报告文件）与 `archive`（归档对象存储），因此页面与 API
统一展示 **13 项阶段账**。其中核心诊断逻辑仍是十段，13 项是用户可见的执行时间线。

| # | 阶段 id | 阶段标题 | 主要实现 | 输入 → 输出 |
|---|---|---|---|---|
| 1 | `connect` | 连接集群 | `internal/service` + Kubernetes 只读门面 | 目标集群 → ServerVersion / 连通性 |
| 2 | `collect` | 资源采集 | `internal/scanner`（list 采集）、`internal/kubernetes`（只读门面） | 集群 → `model.ClusterSnapshot` + `CollectionErrors` |
| 3 | `rules` | 规则引擎 | `internal/rule` | 快照 + 关联索引 → `[]model.Finding` |
| 4 | `evidence` | 按需证据采集 | `internal/scanner`（深度采集日志）、`internal/evidence` | 异常 Pod → 日志证据挂到 Finding |
| 5 | `relations` | 资源关系分析 | `internal/relations.Build` | 快照 + 索引 → `relations.Graph` |
| 6 | `correlate` | 关联分析 | `internal/correlation` | 快照 → `CorrelationIndex`（owner/Service/Events 索引） |
| 7 | `incident` | 故障聚合 | `internal/incident.Build` + `Relate` | Findings + Graph → `[]model.Incident` + `CausalEdge` |
| 8 | `deterministic` | 确定性诊断 | `internal/deterministic` | Incident + 证据 → 根因/影响链/可信度依据 |
| 9 | `llm` | LLM 增强诊断（可选） | `internal/diagnosis`（`enhance.go`） | 确定性事实 → LLM 增强结论 |
| 10 | `validate` | 结果校验 | `internal/diagnosis`（`validation.go`） | 诊断结论 ↔ 证据宇宙 → 校验标记/降级 |
| 11 | `report` | 报告生成 | `internal/report`、`internal/service/report_json.go` | ScanResult → JSON / Markdown |
| 12 | `write` | 写入报告文件 | `internal/report` writer | 报告正文 → 本地文件产物 |
| 13 | `archive` | 归档报告到对象存储 | `internal/service` + ObjectStore | 选中产物 → 对象存储归档 |

阶段清单与标题的单一来源是 `internal/service/stages.go` 的 `stageSpec`；
`stageRecorder` 只记录状态、耗时、失败原因与当前子步骤描述，**不记录百分比**（需求 §9：禁止伪造百分比）。
编排顺序在 `internal/service/service.go` 的 `scanService.Run`。

## 3. 与旧口径的差异（为什么必须改）

| 维度 | 旧口径（已废弃） | 本方案 |
|---|---|---|
| 诊断主体 | LLM 直接对 Finding 出根因 | 确定性诊断先出结论，LLM 只做增强；LLM 不是事实来源 |
| 无 LLM 模式 | 只有 Finding 列表 + 健康评分 | 同一套确定性诊断照常出根因、影响链、排查与处理建议 |
| 异常聚合 | Correlation 顺带给出「疑似根因」 | Correlation 只建候选索引；Incident 只组织故障与成员；确定性诊断优先，LLM 只补充候选，最终 `Diagnosis` 是唯一根因事实源 |
| 故障链 | 无因果边，只有成员列表 | `Incident.CausalEdges` 每条边必须能自证资源关系路径 |
| 采集失败 | 报告里只是一条 collection error | 汇聚成 `CollectionQuality`，参与健康评分封顶与结论可信度声明 |
| 报告 | Markdown 为主，JSON 是扫描结果转储 | 统一 `InspectionReport` 九区块，CLI/Web/JSON/Markdown 同源 |
| LLM 可信度 | 模型自评分直接进报告 | 结果校验核对证据引用与资源真实性，不通过则退回确定性结论 |

## 4. 资源关系与故障因果

### 4.1 真实资源关系图（`internal/relations`）

关系图只接受**有字段出处**的边，禁止用名称相似度推断：

| 关系类型 | 语义 | 出处 |
|---|---|---|
| `ownedBy` | OwnerReference 归属（Deployment→RS→Pod、STS/DS→Pod） | `ownerReference` |
| `runsOn` | Pod/VolumeAttachment 落在 Node 上 | `specField` |
| `selectedBy` | Service/EndpointSlice 通过 Label Selector 选中 Pod | `labelSelector` |
| `hasEndpoint` / `endpointOf` | EndpointSlice ↔ Service | `objectLabel` / `specField` |
| `routesTo` | Ingress 后端 → Service | `specField` |
| `mounts` | Pod → PVC | `specField` |
| `boundTo` | PVC ↔ PV | `specField` / `uid` |
| `provisionedBy` | PVC/PV → StorageClass | `specField` |
| `targets` | HPA → 伸缩目标工作负载 | `specField` |
| `protects` | PDB → 受保护工作负载 | `labelSelector` |
| `appliesTo` | NetworkPolicy → 被选中 Pod | `labelSelector` |
| `configRef` / `secretRef` | Pod/容器 → ConfigMap / Secret（**只引用键名，不读值**） | `specField` |

证据出处标记为 `ownerReference` / `uid` / `labelSelector` / `specField` / `objectLabel`，
`Graph.TextFor` 会把出处一并渲染进 LLM 上下文，形如：

```text
- Pod/prod/web-0 ownedBy StatefulSet/prod/web [ownerReference:metadata.ownerReferences]
```

能力：`Build` / `DirectEdge` / `Connected` / `Path` / `Out` / `In` / `All` /
`EdgesOfType` / `KindCounts` / `EdgeCount`。`Connected` 是判因果的准入门槛。

### 4.2 故障因果边（`internal/incident/causal.go`）

`Incident.CausalEdges` 每条边都是一个 `model.CausalEdge`：源/目标 Finding、源/目标资源、
关系类型、传播机制、规则、证据引用、可信度（`confirmed` / `probable`）。

Incident 内从根 Finding 生长一棵故障树，每个症状最多保留一条最能解释它的入边；边增加
`method=correlation|deterministic|llm`。关联层生成的候选边只能是 `probable`，确定性诊断器
才能基于更具体的事实写 `confirmed`。

硬约束：**两个资源之间没有真实关系路径就不许建边**。`relationPath()` 负责给出边的关系类型，
三种合法形状是同一对象（`sameObject`）、直接边（如 `boundTo`）、多跳路径
（BFS 后串成 `ownedBy->selectedBy`）。这条约束同时封掉了「同一 namespace 里两件事同时坏
所以有因果」这类臆造。

### 4.3 Incident 结构

`model.Incident` 承担「组织故障 + 展示最终结论投影」：

| 字段 | 职责 |
|---|---|
| `Root` / `Members` | 根 Finding 与成员 Finding（症状、影响对象） |
| `RootCause` / `RootCauseStatus` | 根因文本与 `confirmed` / `probable` / `unknown` |
| `RootCauseRule` / `RootCauseMethod` | 命中的诊断器 ID；`rule` / `deterministic` / `llm` / `hybrid` / `none` |
| `Confidence` / `ConfidenceBasis` | 数值可信度 + **可读依据**（不是模型自评分） |
| `CausalEdges` | 故障传播链（见 §4.2） |
| `ImpactChain` | 影响链（哪些资源/命名空间被拖下水） |
| `EvidenceRefs` / `EvidenceGaps` | 支持证据与**证据缺口**（缺口必须写出来） |
| `AlternativeCauses` | 无法确认根因时给出的备选方向 |
| `Independent` | 未与任何资源形成故障链的独立异常 |

上述根因相关字段是报告兼容层。服务层在确定性诊断与 LLM 增强合并完成后，会把最终 `Diagnosis`
投影到 Incident；Incident 不保存第二套可独立演进的根因结论。

## 5. 确定性诊断引擎（`internal/deterministic`）

四条硬规矩（与需求一致，写进代码注释）：

1. 只看已采集到的对象字段、事件与日志，不发起任何集群调用；
2. 结论只能挂真实证据 ID，没有证据就不许判 `confirmed`，最多 `probable`；
3. 资源关系与故障传播以 `relations.Graph` 为准，禁止用名称相似度推断因果；
4. `unknown` 是合法结论：证据不足时必须写清缺口，而不是把症状硬拗成根因。

诊断器接口 `Diagnoser{ ID / Match / Diagnose }`：`Match` 是触发条件（含排除条件），
`Diagnose` 只允许使用 `Match` 已确认存在的数据。`Register` 的注册顺序即优先级
（越具体越靠前），`Scenarios()` 输出已覆盖场景清单，供文档与测试矩阵核对覆盖率。

置信度阶梯刻意做得很粗：体检没有真值集，0.83 这类数字只会制造假的精确感。

覆盖场景（诊断器 ID 即下表结论 ID，与 `fixtures_*_test.go` 场景一一对应）：

| 域 | 场景 | 诊断器 ID |
|---|---|---|
| Pod | CrashLoopBackOff / ImagePullBackOff / Pending / FailedScheduling / FailedMount / OOMKilled / Evicted / 探针持续失败 | `POD_CRASHLOOP`、`POD_IMAGEPULL`、`POD_UNSCHEDULABLE`、`POD_FAILEDMOUNT`、`POD_OOMKILLED`、`POD_EVICTED`、`POD_PROBE_FAILING` |
| Node | NotReady / Memory·Disk·PID Pressure | `NODE_NOTREADY`、`NODE_PRESSURE` |
| Workload | Deployment 副本不足 / StatefulSet 异常 / DaemonSet 未覆盖节点 / Job 失败 / HPA 无法扩缩 / PDB 阻断驱逐 / 配置引用缺失 | `WORKLOAD_REPLICAS_UNAVAILABLE`、`WORKLOAD_DAEMONSET_GAP`、`WORKLOAD_JOB_FAILED`、`WORKLOAD_HPA_NOT_SCALING`、`WORKLOAD_PDB_BLOCKING`、`WORKLOAD_CONFIG_REF_MISSING` |
| Storage | PVC Pending / PV 异常 / StorageClass 异常 / VolumeAttachment 卡住 | `STORAGE_PVC_PENDING`、`STORAGE_PV_UNAVAILABLE`、`STORAGE_CLASS_INVALID`、`STORAGE_VOLUME_ATTACHMENT_STUCK` |
| Network | Service 无 Endpoint / EndpointSlice 与 Pod Ready 不一致 / Ingress 后端不可用 / NetworkPolicy 潜在阻断 | `NETWORK_SERVICE_NO_ENDPOINT`、`NETWORK_ENDPOINTSLICE_INCONSISTENT`、`NETWORK_INGRESS_BACKEND_UNAVAILABLE`、`NETWORK_POLICY_POSTURE` |
| Platform | DNS / CoreDNS 异常 | `PLATFORM_DNS_ABNORMAL` |

引擎不依赖 `llm` / `diagnosis` / `scanner`，只依赖 `model` 与 `relations`，
因此「无 LLM」与「有 LLM」跑的是同一套确定性结论，LLM 只在其上增强，不能覆盖已确认事实。

## 6. LLM 增强与结果校验

### 6.1 LLM 的职责（`internal/diagnosis/enhance.go`）

LLM 拿到的是**已经算好的确定性事实**：故障链成员、根因结论与依据、真实资源关系（带字段出处）、
证据（带 `FindingID#EID`）。提示词明确要求：跨 Finding 证据引用必须写成 `<findingID>#<evidenceID>`，
不得发明资源，不得把没有证据的方向写成确定结论。

预算闸门：单次输入与总量双预算（默认单条 8k / 总量 32k tokens，`llm.diagnosis.*` 可配），
超预算的故障链不送诊，记 `LLMStatusBudgetSkipped`，确定性结论原样保留。文本裁剪按 rune
边界，并追加可见标记 `…（增强上下文已达预算上限）`。

### 6.2 结果校验（`internal/diagnosis/validation.go`，口径 `p9-evidence-consistency-v1`）

证据「宇宙」只包含 canonical 引用：根 Finding 的 `rootID#EID` + 成员 Finding 的
`memberID#EID`。旧裸 E-ID 只在入口按当前根 Finding 归一化一次，不能作为新结果继续流出。
校验规则：

1. 出现宇宙外的证据 ID → 记入 `FabricatedEvidence`；
2. 出现 `ns/name` 形状的资源引用且该 namespace 真实存在、但资源不在快照里 → 记入
   `UnknownResources`（`linux/amd64`、`apps/v1` 这类镜像与 API 组不会被误判）；
3. `Passed = 无编造证据 且 无未知资源`；
4. 校验不通过 → 退回确定性结论，`RootCauseStatus=probable`、置信度下调至 ≤0.5、
   `ConfidenceLevel=POSSIBLE`；
5. 根因悬空（结论与故障链资源无支撑）→ 标记 `Downgraded` 并下调置信度，但 `Passed` 仍为真。

Finding 单点诊断路径（`New()` + `Diagnose`）保持更严的旧行为：非法引用直接丢弃。

## 7. 统一运行模式与降级矩阵

### 7.1 无 LLM

规则引擎出 Finding → 关系图 → 故障聚合 → 确定性诊断出根因/影响链/排查与处理建议 →
结果校验 → 报告。诊断来源标记 `Source=deterministic`、`DiagnosisSummary.Mode=rule_only`。
LLM 区块显示「未配置/未启用」，绝不显示为执行中。

### 7.2 有 LLM

同上，第 8 段把确定性事实连同证据交给 LLM 增强；第 9 段校验后合并，
来源标记 `llm` 或 `hybrid`，`Mode=llm_enhanced`；部分成功是 `llm_degraded`。

### 7.3 降级状态口径（`model.LLMStatus*`）

| status | 触发 | 结论处理 | `KeptDeterministic` |
|---|---|---|---|
| `not_configured` | 未配置 LLM | 用确定性结论 | 仅当确定性层真的覆盖该故障时为真 |
| `success` | 增强并通过校验 | 采用增强结论 | — |
| `partial_success` | 部分故障链成功 | 成功用增强、失败用确定性 | 视各条而定 |
| `request_failed` / `timeout` | 请求失败/超时 | 保留确定性结论 | 同上 |
| `invalid_response` / `schema_validation_failed` | 返回不可解析/不合 schema | 保留确定性结论 | 同上 |
| `evidence_validation_failed` | 证据校验不通过 | 退回确定性结论并下调可信度 | 同上 |
| `budget_skipped` | 预算不足未送诊 | 保留确定性结论 | 同上 |
| `degraded` | 其他降级 | 保留确定性结论 | 同上 |

`LLMDegradation.KeptDeterministic` 的语义是「**确定性引擎确实覆盖了这条故障并保留了结论**」。
确定性引擎没有覆盖到的故障，这个字段必须为假——否则报告会在没有根因的地方宣称
「已保留确定性结论」，那是编造。

## 8. 体检档位

档位是**行为预设**，锁在代码常量表并进测试，不进配置中心（否则「快速体检这次为什么跑了
5 分钟」就没有确定答案）。来源 `internal/server/scans.go`：

| 档位 | 超时上限 | LLM | Events | Pod 日志 |
|---|---|---|---|---|
| `quick` 快速体检 | 60s | 关 | 开 | 关 |
| `standard` 标准体检（默认） | 5min | 开 | 开 | 关 |
| `deep` 深度体检 | 10min | 开 | 开 | 开（近 1h 窗口） |

最终超时取档位值与配置上限的较小者。CLI 与 Web 共用同一张表，CLI 侧对应
`--preset`，档位差异只体现在采集与 LLM 开关，**不影响诊断链路形状**。

## 9. 统一 InspectionReport 报告模型

`model.InspectionReport` 是 `model.ScanResult` 的别名（保持向后兼容的别名，而不是再造一个
结构），JSON 产物即它的序列化。九个区块：

| # | 区块 | JSON 字段 | 来源 |
|---|---|---|---|
| 1 | Overview | `meta` + `summary` + `healthScore` | `report.ComputeHealthScoreWithQuality` |
| 2 | Conclusion | `conclusion`（`level`/`headline`/`summary`/`topRisks`/`priorities`/`dataCaveats`） | `report.BuildConclusion` |
| 3 | Incidents | `incidents`（含 `causalEdges`/`impactChain`/`evidenceRefs`/`evidenceGaps`）+ `diagnoses` | `internal/incident` + `internal/deterministic` |
| 4 | Findings | `findings`（含 `evidence`/`category`/`kind`） | `internal/rule` |
| 5 | Remediation | `remediation`（`kind`=investigation/remediation/verification + `risk`/`target`/`required`） | `report.RemediationItems` |
| 6 | ResourceStatistics | `statistics`（按域 total/unhealthy/critical）+ `components` | `report.DomainHealthList` |
| 7 | CollectionQuality | `collection` + `collectionErrors` | `scanner.CollectionQuality` |
| 8 | DiagnosisSummary | `diagnosisSummary` + `llmSummary`（含 `statusCounts`/`degradations`） | `internal/service` 诊断合并阶段 |
| 9 | History | `history`（added/continued/recovered + 上一轮时间） | `internal/history` |

`stages` 数组另存十段执行记录（状态、耗时、失败原因、当前子步骤），供体检过程展示。

### 9.1 采集完整性与评分封顶

`scanner.CollectionQuality` 由「计划采集项」与「实际失败/跳过项」推导，不是把
`CollectionErrors` 条数简单换算成百分比：

| integrity | 判定 | 健康评分封顶 |
|---|---|---|
| `complete` | 全部计划资源类型采集成功 | 不封顶 |
| `partial` | 有非关键类型失败 | 85 |
| `insufficient` | 关键类型（Pod / Node / 工作负载 / Events）失败 | 60 |
| 任意 | 存在失败或跳过的类型 | 满分减 1（不给满分） |

未登记的采集操作也会显式出现在 `failedKinds` 里（形如 `other:get_xxx`），不允许静默消失；
集群级 list 失败按「影响全部命名空间」记账，不会被读成「只坏了一个 ns」。
封顶原因写入 `healthScore.capReason`，`conclusion.dataCaveats` 同步声明，
保证「采集失败」在任何一处都不会被解读成「资源正常」。

### 9.2 兼容历史报告

`report.ParseReportJSON` 返回 `legacy` 标记，`service.StructuredReport.SchemaVersion`
对 v1 老报告归一化为 1。老报告缺失的区块是零值，前端按 `schemaVersion` / `legacy` 分支渲染；
只归档了 Markdown 的老报告走 `ErrReportNotStructured`（HTTP 415），诚实提示改走原文下载，
绝不拿 Markdown 硬凑一个结构化对象。

## 10. 体检过程展示

- 数据源：`ScanJob` 阶段记录（`internal/server/scan_progress.go`）+ SSE 阶段事件（`internal/sse`），
  复用既有任务机制，不新增调度基础设施。
- 每个阶段真实状态：`running` / `done` / `failed` / `skipped`（含跳过原因）。
- 阶段耗时真实测量；`stageRecorder.done` 在失败时如实写 `failed`。
- 禁止百分比：`stageRecorder` 没有百分比字段，`StageRecord.Progress` 只有子步骤文字描述。
- 未启用 LLM 时 LLM 阶段记 `skipped` 并给出原因，不会显示为执行中。
- 任务取消、服务重启、轮询失败、任务终态、归档失败沿用 `internal/server/scans.go`
  与 `internal/service` 既有语义。

### 10.1 页面上的实时阶段进度（P9.12）

「点了按钮页面什么都没动，最后报告末尾才补一段过程」是不可接受的：一次体检要跑 1~10 分钟，
进度必须是**发起时就出现、随轮询推进**的过程，不是事后复盘。

- 发起：`POST /api/v1/scans` 回 202 与 `scanId` 后，列表页立刻挂出进度横幅并开始轮询
  `GET /api/v1/scans/{id}`；阶段账取自 `ScanJob.stages`（JSON `stages`），与报告里的
  `StageRecord` 同源同结构，页面上不存在第二套阶段命名。
- 阶段行只画后端给的四态：`running` 进行中 / `done` 完成 / `failed` 失败 / `skipped` 跳过，
  附真实耗时与子步骤文字；没有百分比，没有前端编造的预估进度。
- 计数 `N / M 阶段` 数的是**已收尾**的阶段（`done` + `skipped`）：剩下那一个就是进行中的那个，
  既不把 running 算成已走完，也不会因为某阶段被跳过而永远差一格。
- 任务已受理但第一个阶段尚未记账时显示「任务已排队，等待调度…」，不留一条空白横幅。
- 终态文案：成功落报告、失败给后端原因、`cancelled` 提示「本次不产出报告」且不跳详情页。

### 10.2 停止体检（P9.11）

`POST /api/v1/scans/{id}/cancel`：没有停止端点的话，一次跑偏的体检只能等超时，用户只能刷新页面赌它结束。

- 只有发起人本人（或 admin）能停：他人任务与不存在的任务同形 404，job id 不能变成
  一个可探测存在性、可被别人按下的按钮。
- 已在跑的任务才停得动：终态任务回 409「该次体检已经结束，无需停止」，页面把 409 翻译成中性提示。
- 停止靠 context 向上传播，不强杀 goroutine：采集、规则、关系、诊断每一步都用同一个 ctx 调
  API Server，取消后在下一个调用点自行退出，因此扫描器无需为取消额外配合实现。
- 状态在响应返回前就写成 `cancelled`，按钮不必等 goroutine 真正退出；挂在 `running` 的
  阶段一并冻结成 `failed` + 「已停止」，绝不留一条永远转圈的进度条。
- 每次停止落一条 `scan.cancel` 审计：谁在什么时候中断了对哪个范围的一次采集。

## 11. Web 体检页面（报告列表 + 详情）

### 11.1 报告列表

`web/src/views/report/ReportsView.vue`。列表页的口径同样是契约的一部分：

- 顶部按钮与弹窗标题一律「开始体检」；页面大标题为「智能体检中心」（口径见 §15）。
- 报告格式在发起弹窗里**单选** `JSON` / `Markdown`，一次体检只归档选中的那一种，对象存储里
  不留第二份产物，页面上也就不存在「哪一份才是最新的」。
- 每行大字标题是「体检报告」，格式退成 mono 小字 `JSON` / `Markdown`。徽标分两枚：**类别**只说
  `集群体检`（cluster）/ `业务体检`（namespace、pod）/ `范围未记录`，**范围**另开一枚说
  `全集群` / `命名空间 <ns>` / `单 Pod <pod>`：类本回答「这是哪一类体检」，范围回答「扫了哪里」。
- 集群徽标只在报告确实绑定了登记集群时出现。页面体检的 `clusterId` 由服务端判定、不接受请求体值，
  因此这类行就不显示集群，不再拿「平台集群」这种并不存在的归属去占位。
- 归属显示「发起人：<用户名>」（`createdByName` 由 handler 侧查用户表补齐，取不到退回 ID；
  `createdBy` 为空或 `system` 显示「发起人：系统自动」）。
- 顶部五张总览卡：可见报告 / 集群体检 / 业务体检 / 范围未记录 / 归档对象，数据来自
  `GET /api/v1/reports/summary`，与列表共用同一组过滤条件；统计的是**全部可见行**，翻页不改变它。
  「当前页」这类数字已删除：它回答不了「我手上有多少报告」。
- 「导出 Markdown」只出现在 JSON 行上（`GET /api/v1/reports/{id}/export`）：由后端用同一份
  数据当场渲染成可读正文，不写回对象存储，因此不构成第二份归档。
- 进度横幅右侧的「停止体检」只在本机有在跑任务时出现（§10.2）。

### 11.2 报告详情

- 路由：`/app/report`（列表）→ `/app/report/:id`（详情，`web/src/views/report/ReportDetailView.vue`）。
- 数据：`GET /api/v1/reports/{id}/report`（`web/src/api/reports.ts` 的 `getStructuredReport`），
  授权判定复用列表同一套 `reportScopeFor`，跨 owner 读取同样落审计。
- 区块顺序与 §9 一致：报告头 → 概览 → 结论 → 故障诊断（根因/影响链/证据/排查/处理）→
  Finding 列表 → 资源健康 → 采集质量 → 历史对比 → 原始数据。
- 前端不做任何诊断推断（需求 §13.11）：根因状态、可信度、影响链一律来自后端字段。
- 严重程度图标 + 文字并存；日志默认折叠；命令与资源名可复制；大型列表按需渲染。

## 12. 诊断质量测试体系

测试全部使用可重复夹具（`internal/deterministic/fixtures_*_test.go`、
`internal/diagnosis/enhance_test.go`），不依赖真实集群。

每个故障场景覆盖六个条件：正常情况、单一故障、多个关联故障、证据缺失、采集失败、
容易误判的边界条件。LLM 维度覆盖：无 LLM、LLM 正常、LLM 超时、返回无效结构、
诊断失败降级、证据编造退回、预算跳过。

| 指标 | 口径 | 采集方式 |
|---|---|---|
| Finding Precision / Recall | 场景夹具里应报/不应报的 Finding 与实报集合比对 | `scenarios_test.go` 场景断言 |
| Root Cause Accuracy | 场景期望根因（含期望 `unknown`）与最终 `Diagnosis.Diagnoser` / `RootCauseStatus` 比对，并断言 Incident 投影一致 | 夹具 `wantDiagnoser` |
| Incident Correlation Accuracy | 期望故障链成员集合与实际 `Members` 比对 | 夹具成员断言 |
| Evidence Support Rate | 根因结论的证据引用全部命中真实 `FindingID#EID` 的比例 | `diagnosis/validation.go` + 夹具 |
| Remediation Relevance | 处理建议必含该场景规定动作关键词（如 ImagePull → 镜像地址/tag） | 夹具建议断言 |
| No-LLM Diagnostic Coverage | `Scenarios()` 中无 LLM 也能出结论的场景占比 | `deterministic.Scenarios()` |

无法自动断言的部分（真实集群上 CNI/CoreDNS 行为、对象存储归档）以夹具 + 人工验收清单
形式记录在 `09-测试方案.md` §3.4。

## 14. 已知边界

- 确定性引擎的诊断器按「先解决真实问题」推进，未覆盖的 kind 走规则 Finding +
  `unknown` 根因，不会伪造结论。
- 关系图基于快照，跨轮体检的关系变化不做时序回溯；需要判断采集时序时用 `ResourceVersion`。
- LLM 增强不引入 Function Calling / 工具调用，仍是单轮结构化 JSON，避免与二期 Agent
  循环的权限模型混淆。
- `evidence` 阶段只在规则声明 `NeedsLogs` 的 Pod 类 Finding 上触发，其余档位下为 `skipped`。

## 15. 术语与文案口径（2026-11-05 冻结）

体检相关的用户可见文案统一用「体检」，页面大标题为「智能体检中心」，报告本身一律叫
「体检报告」。左侧导航把聊天入口显示为「问诊」，**只改入口名称，不覆盖聊天页面标题、
提示文案、会话行为或后端流程**。医疗化表达只允许出现在体检域的轻量语义中，不向聊天、
集群、审批、审计等其他产品面扩散。

报告分析使用运维语义：「根因分析」「故障关联分析」「处置建议」「受控执行」「修复验证」。
不使用「治疗方案」「康复评估」「受控治疗」等会让人误以为平台具备医疗决策或自动处置能力的词。
代码枚举与 JSON 字段（`scope` / `preset` / `kind` / `scopeKind`）一律不动，本节只约束看得见的字。

**2026-11-04 二次收口**（用户真机复验后定稿）：报告行标题改「体检报告」、归属改「发起人」、类别与范围
拆成两枚徽标、取消「平台集群」这个并不存在的归属占位。

| 位置 | 定稿文案 | 依据 |
|---|---|---|
| 左侧导航·聊天入口 | 问诊 | 仅换入口名称；聊天功能、页面文案与交互均保持原样 |

## 16. RBAC 采集与报告渲染收口（v1.2）

### 16.1 报告以 Incident 为主体，不全量平铺 Finding

现有 `ScanResult` 已经包含 `Incidents`、根因状态、因果边、证据缺口与处置建议，**不新增平行的
`InspectionReport` 数据结构**。Web 详情页与 Markdown 都按以下顺序展示：

1. 总体结论、健康评分、采集完整性；
2. **业务故障链**与根因分析；
3. 安全/治理建议与未归入故障链的其他异常；
4. 资源健康与处置建议；
5. 完整 Finding / Evidence 附录。

业务故障与 `Suggestion=true` 的治理建议必须分开计数，不能把“缺少 default-deny”与“业务 Pod
全部 NotReady”混成两条业务故障链。故障链首屏直接展示最终 `Diagnosis.RootCause`；
`Incident.RootCause` 是服务层投影出的兼容字段，不是第二套可独立演进的结论。
诊断摘要和“未确认边界”也要在同一根因区给出。

传播路径、派生症状、证据与待排除项默认折叠；关键证据优先按 `Diagnosis.EvidenceChain` 引用过滤，
全部 Evidence 仍保留在完整异常附录。排查/修复/验证命令与修复说明放在同一个处置框内，正文按
Markdown 渲染，命令按代码块渲染。

完整 Finding 与 Evidence 必须保留，但默认折叠；故障链中的根 Finding 与 `Members` 的证据值都要
可落到 `FindingID#EvidenceID`。`Members` 只表示派生症状，不包含根 Finding。

容器探针配置（readiness / liveness / startup 的 HTTP path、端口、命令与时序）属于 Pod spec
只读元数据，必须进入采集和 Finding 证据；只为“探针失败”提供事件而丢失“探针检查哪里”，会让
根因结论不必要地依赖模型补全。

### 16.2 RBAC 只能声明 Binding 关系，不能冒充身份真值

体检能验证 `RoleBinding` / `ClusterRoleBinding` 把什么声明授予了哪类 subject；User / Group 是否
真实存在、Group 当前成员是谁，不在本期采集边界内。因此报告文案使用「Binding 将权限授予主体」，
不写成「该主体当前一定拥有并使用了权限」。本期也不通过新增 ServiceAccount 全量采集来补这个判断。

### 16.3 通配符按风险分级，不要求三维同时为 `*`

- `verbs + resources + apiGroups` 全通配，或 `nonResourceURLs + verbs` 全通配：全通配；
- 任一维度单独为 `*`：局部通配；
- ClusterRoleBinding 全通配为 High，局部通配为 Medium；
- RoleBinding 全通配为 Medium，局部通配为 Low；
- 只有全通配定义且确认 Binding 列表完整时，才允许输出“未绑定”Low；
- `resourceNames` 必须参与判定，受限命名不能描述成全集群全对象权限。

### 16.4 采集缺失与作用域

- `list_*_role_bindings` 失败时，不能把空切片解释为“没有绑定”；未绑定提示必须跳过，采集质量账
  负责说明缺口。
- 集群体检评估全局 RBAC；命名空间体检只分析该命名空间 RoleBinding，以及其引用的 ClusterRole；
  单 Pod 体检不混入 RBAC 结论。
- 业务体检的 `ClusterSummary` 不把 Nodes、Storage 集群对象、ClusterRoles、ClusterRoleBindings
  或全集群 Components 计入可见汇总。

### 16.5 门禁

`internal/scanner/collection_contract.go` 是体检采集所需 API Group / Resource / Verb 的唯一契约。
Collector 任务集合、运行期采集与 `deploy/base/clusterrole.yaml` 必须由自动化测试交叉校验；新增采集项
但没有登记权限时，测试直接失败。

### 16.6 LLM 主导修复方案，规则层负责无 LLM 兜底

体检报告面向可能不知道如何描述 Kubernetes 故障的用户，修复区首先展示 `remediationText`
Markdown 方案，至少包含目标、按序步骤、预期结果和回退方式；`remediationDirection` 单独展示
前置条件、外部系统操作与安全边界。

命令分三类：

- `investigation`：只读确认，系统中强制 `SAFE`；
- `remediation`：只在命名空间、资源名、字段和目标值均已确认时输出可复制写命令，允许为空；
- `verification`：只读验证，系统中强制 `SAFE`。

工具侧不得为了“至少一条写命令”追加 `rollout restart`、`scale` 或占位符 `patch`。模型返回的
命令若因占位符、未知资源、交互语法或不完整参数被过滤，必须写入
`DiagnosisValidation.CommandIssues` 并在报告中展示摘要，不能静默消失。

无 LLM 时，确定性诊断继续提供现象、初步根因、只读排查命令、修复方向与验证方式；无法确定的写操作
保持为文字边界，不伪造可执行命令。

## 17. 证据语义与诊断事实源（v1.3 / v1.4 口径统一）

架构决策记录见 `04-架构决策记录-ADR.md` ADR-047。

### 17.1 扫描器保留，问题在结果契约

`internal/scanner` 的两阶段设计保持不变：

1. Phase1 只做资源与事件的全量轻量 list，按并发上限执行；
2. 单任务失败只进入 `collection_errors`，不中断整轮体检；
3. Phase2 只对规则声明的异常 Pod 取日志，日志在采集边界脱敏与截断；
4. Collector、Reader 与部署 RBAC 通过 `collection_contract.go` 共用同一份资源/动作清单。

这次发现的歧义不在采集器并发模型，而在下游同时存在本地证据编号、两套根因字段和
“聚合关系即因果”的隐含假设。修契约比重写扫描器收益更高、风险更低，因此不推倒现有扫描引擎。

### 17.2 证据引用必须全局唯一

`Evidence.ID` 只在单个 Finding 内稳定，进入 Incident、CausalEdge、Diagnosis 和报告后统一写成：

```text
<findingID>#<evidenceID>
```

例如 `f-2#E1`。校验、LLM 上下文和 Web 证据定位都只认 canonical ref；历史输入中的裸 `E1`
只在入口兼容归一化，不能继续写入新结果。诊断上下文预算裁剪同样按 canonical 证据行识别，
否则日志证据会在预算超限时无法被移除。

### 17.3 最终 Diagnosis 是根因唯一事实源

`Incident.RootCause*`、`Confidence*`、`EvidenceRefs`、`EvidenceGaps` 等字段保留用于报告兼容，
但它们是最终 `Diagnosis` 的投影，不是第二套可独立演进的结论。服务层在合并确定性诊断与 LLM
增强结果后，统一把最终诊断回写 Incident；旧规则层根因不得覆盖更具体的最终结论。

### 17.4 Finding 角色表达报告语义

Finding 增加 `role`：

| role | 含义 |
|---|---|
| `anchor` | 故障链主信号 |
| `symptom` | 主信号引发的派生症状 |
| `impact` | 工作负载副本不足、Service 无端点等业务影响 |
| `advisory` | 安全/治理建议，不是业务故障 |
| `independent` | 未进入故障链的独立异常 |

角色由 Incident 聚合完成后统一注入，报告不得靠标题或规则名猜语义；业务故障与治理建议因此可以
稳定分开计数、排序和折叠。

### 17.5 故障链是一棵树，不是两两关系网

关联层只生成 `method=correlation`、`confidence=probable` 的候选边；每个症状最多保留一条最能
解释它的入边，从根 Finding 向外生长一棵故障树。确定性诊断器可留下更具体的
`method=deterministic` 边，并在证据充分时标记 `confirmed`。关联层永远不能自行把边升格为
confirmed。这样既保留真实传播链，又避免同一 Incident 内所有合法 cause/effect 两两组合造成边爆炸。

### 17.6 采集质量不等于证据充分度

`CollectionQuality` 只回答“计划内的 API 采集是否成功”，不能回答“这个根因是否有足够证据”。
每个结论仍由诊断器的 `EvidenceRefs` 与 `EvidenceGaps` 自证：

- 无真实证据不得 `confirmed`；
- 有对象状态但缺日志/事件时要明确降为 `probable`；
- 未覆盖的诊断器返回 `unknown`，不得把症状硬写成根因。

例如容器 `restartCount` 很高但上次退出码为 0 时，只能先确认“进程正常结束后被再次拉起”，
不能写成“异常崩溃”；必须列出 `previous logs`、启动命令与 `restartPolicy` 的证据缺口，
且未确认原因前不得自动建议 `rollout restart`。
