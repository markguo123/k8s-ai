- 关联模块：Agent、Tools、Approval、Executor、SSE、Session API、Web Chat

## 1. 背景与结论

核心问诊链路已经具备自然语言对话、Tool Calling、审批、审计、会话回放和写操作执行能力，基础分层与安全底线方向正确。当前影响生产可信度的主要问题不是功能数量，而是四个跨层契约没有收敛：

1. 工具结果没有稳定的后端展示与状态协议。
2. 平台用户授权与 Kubernetes 执行身份没有形成明确的交集。
3. 权限失败在 Agent Loop 中被当成普通工具输出，导致失败批次继续执行。
4. 长任务 SSE、历史回放和前端渲染依赖多套启发式判断。

本方案优先修复这些边界，不在前端继续叠加显示猜测，也不通过给共享 ServiceAccount 绑定全局写权限来绕过平台用户权限。

## 2. 现状问题

### 2.1 kubectl 结果状态与渲染失真

`kubectl` 工具返回 `executor.Result`：

```text
command / stdout / stderr / exitCode
```

改造前，`tools.DisplayType` 没有显式的 terminal 类型，`agent.toolResultOK` 也只检查结构化 `error` 字段。实际效果包括：

- `Forbidden`、`Unauthorized` 等非零退出被判为成功；
- 工具卡状态可能显示绿色完成；
- 同签名失败熔断不生效；
- 一个批量修复中的第一个权限失败不会阻止后续写操作；
- 结果对象进入前端的文本/KV/表格启发式分支，出现空表、对象字符串或结构错位。

### 2.2 平台权限与集群 RBAC 未形成交集

平台侧 `AuthzGrant` 定义用户可访问的 namespace 与写/销毁能力；Kubernetes RBAC 定义执行身份实际能执行的操作。当前：

- `AccessScope` 已返回 `CanWrite`、`CanDestroy`，但执行检查没有消费；
- 非 admin 的 kubectl 检查只允许读动词，命名空间写授权无法正常落到审批后的执行；
- `destroy` 没有独立执行门禁；
- Web 请求体可以携带 `skipPermissions`，审批绕过不应由客户端决定；
- 集群管理页面保存的凭据没有进入当前聊天执行路径。

### 2.3 工具结果缺少稳定展示契约

结构化工具、日志、`kubectl`、资源创建返回的数据形状不同。前端同时依赖 `displayType`、启发式识别、固定字段表和工具专属特判，导致：

- 诊断需要的嵌套字段被固定列裁剪；
- 实时流与历史回放表现不一致；
- 旧会话缺少 `ok` 时被误判为失败；
- 原始 JSON 成为主要排障界面，而用户更熟悉 kubectl 终端输出。

### 2.4 权限失败缺少结构化语义

当前工具错误大多是文本。模型无法稳定区分 `RBAC_DENIED`、`NOT_FOUND`、`CONFLICT`、`TIMEOUT` 和参数错误，容易出现重复调用、换命令继续撞权限墙或把可执行修复错误地降级成普通失败。

### 2.5 长任务断线恢复不完整

SSE Broadcaster 在客户端队列满时会丢弃事件。重连时只下发已持久化消息快照，运行中的工具事件、审批请求和阶段进度没有可回放日志。慢网络下可能出现工具卡丢失或执行过程不完整。

## 3. 目标架构

```text
平台用户身份
    ↓
平台 AuthzGrant（namespace / write / destroy）
    ↓
集群执行身份
    ↓
SelfSubjectAccessReview 预检
    ↓
EffectiveCapability（读 / 写 / 销毁 / namespace）
    ↓
Agent Planner
    ↓
AccessScope ∩ Cluster RBAC ∩ 人工审批
    ↓
Executor
    ↓
ToolResult（terminal / structured / status / error_code）
    ↓
SSE / 历史快照
    ↓
前端统一渲染
```

### 3.1 权限原则

平台授权与集群 RBAC 是两级门禁，必须同时满足：

- 平台授权决定“这个用户能否提出该操作”；
- Kubernetes RBAC 决定“当前执行身份能否实际完成该操作”；
- 审批决定“用户是否确认本次变更”；
- 任一门禁不满足都不能执行。

平台用户权限管理不读取或复制集群 RBAC；集群 RBAC 只作为执行能力探测和最终保护。禁止通过给共享执行账号增加全局写权限来隐式扩大所有平台用户权限。

### 3.2 工具结果原则

每个工具结果至少包含：

```go
type ToolPresentation struct {
    DisplayType string // terminal | table | kv | events | yaml | logs | text
    Command     string
    Stdout      string
    Stderr      string
    ExitCode    int
    ErrorCode   string
    Status      string // ok | error | denied | partial
}
```

`kubectl` 默认采用 terminal 视图，完整展示命令、stdout、stderr 和退出码。表格、YAML、日志结构化视图是二级视图，不覆盖终端事实。

### 3.3 失败原则

稳定错误码至少包括：

```text
RBAC_DENIED
AUTHENTICATION_EXPIRED
NOT_FOUND
CONFLICT
INVALID_ARGUMENT
TIMEOUT
UNSUPPORTED
CLUSTER_UNAVAILABLE
```

`RBAC_DENIED` 属于不可重试的权限失败：

- 不进入审批；
- 不继续执行同批次剩余写操作；
- 不再用相同或等效参数重试；
- 返回“平台授权 / 集群能力 / 建议动作”三段式结论。

## 4. 实施范围

### 4.1 后端工具结果契约

- 增加 terminal 展示类型；
- 对 `executor.Result` 做统一演示模型转换；
- 非零退出码判失败；
- 从 stderr 识别权限、未找到、冲突和超时；
- 将命令、stdout、stderr、退出码和错误码传递到 SSE 与会话回放；
- Agent 失败熔断使用结构化状态。

### 4.2 权限交集

- `AccessScope.Check` 真正执行 `CanWrite`、`CanDestroy`；
- 非 admin 的合法 namespace 写操作在 `CanWrite=true` 时允许进入审批；
- 销毁类操作要求 `CanDestroy=true`；
- Web `send-message` 忽略/拒绝 `skipPermissions`；
- 对已知核心资源写操作增加 `SelfSubjectAccessReview` 预检；
- 将有效能力写入 Agent Prompt，只读时不再尝试写操作；
- Chat 页面展示只读/可写状态与修复能力说明。

### 4.3 前端展示

- 增加 `TerminalBlock`；
- kubectl 卡默认 terminal；
- 失败时同时展示错误摘要与 stdout/stderr；
- `observation.created` 的 `ok=false` 正确转成失败；
- 旧历史缺少 `ok` 时不伪造成功或失败；
- 权限拒绝使用明确的能力不足文案。

### 4.4 恢复与可观测性

- 为统一事件增加会话内单调递增 `seq`；
- 运行中会话保留有界事件缓存；
- 重连先发历史快照，再补发当前回合缓存事件；
- 前端按 `seq` 去重，避免回放与实时帧重复生成工具卡；
- 后续再演进到持久化 `Last-Event-ID` 回放和跨进程事件总线。

### 4.5 审批卡信息架构（已实施）

#### 4.5.1 当前问题

当前审批事件只有一段 `prompt`，Agent 把标题、风险、工具、命令和“是否执行”拼成同一个字符串。示例：

```text
将执行以下操作（风险等级：HIGH）：

工具：kubectl
参数：{"command":"kubectl ... -p='[{...}]'"}

是否执行？
```

这会带来明显的可读性问题：

- 用户先看到的是 `工具/参数`，而不是“改哪个资源、改什么、影响多大”；
- JSON Patch 被塞在一行里，路径和值难以辨认；
- 命令与参数原文混在一起，缺少复制、折叠和行号/路径高亮；
- 目标 namespace、资源 kind/name、操作类型没有独立字段；
- 没有展示平台授权、集群 RBAC 预检、Code Guard 结果和 dry-run 状态；
- LOW/MEDIUM/HIGH 都显示同一组操作按钮，高危操作仍可能出现“本次会话不再询问”的误导；
- 没有明确展示执行后的验证条件和失败后的替代路径。

#### 4.5.2 卡片目标结构

审批卡以“人做风险决策”为目标，而不是复述 Agent 的 prompt。推荐固定为七段：

```text
┌──────────────────────────────────────────────┐
│ ⚠ 需要审批       HIGH 风险       等待处理   │
│ 修改 Deployment / test-complex/app-backend   │
├──────────────────────────────────────────────┤
│ 操作    patch Deployment                     │
│ 范围    test-complex / app-backend           │
│ 工具    kubectl                              │
├──────────────────────────────────────────────┤
│ 将发生的变更（2 项）                         │
│ 1. livenessProbe.httpGet.path → /             │
│ 2. readinessProbe.httpGet.path → /            │
│                                              │
│ [查看完整 JSON Patch]                         │
├──────────────────────────────────────────────┤
│ 执行前检查                                  │
│ 平台授权  允许                               │
│ 集群 RBAC 已通过预检                         │
│ Dry-run   未启用                             │
├──────────────────────────────────────────────┤
│ 执行后验证                                  │
│ • Pod 2/2 Ready                              │
│ • Deployment 可用副本 = 期望副本             │
│ • 重启次数不再增长                            │
├──────────────────────────────────────────────┤
│ [确认执行]  [复制命令]  [拒绝]               │
└──────────────────────────────────────────────┘
```

信息优先级必须是：

```text
资源目标 → 变更内容 → 影响/风险 → 安全检查 → 命令原文 → 执行按钮
```

#### 4.5.3 结构化审批载荷

审批卡不能继续依赖 `prompt` 文本解析。后端应下发稳定结构：

```go
type ApprovalData struct {
    ID          string
    Title       string
    Tool        string
    Operation   string
    Risk        string
    Target      ApprovalTarget
    Changes     []ApprovalChange
    Command     string
    Checks      []ApprovalCheck
    Verification []string
    Options     []ChoiceOption
    Secret      bool
    ExpiresAt   *time.Time
}

type ApprovalTarget struct {
    Cluster   string
    Namespace string
    Group     string
    Version   string
    Kind      string
    Name      string
}

type ApprovalChange struct {
    Path        string
    Operation   string
    Before      any
    After       any
    Description string
}

type ApprovalCheck struct {
    Name    string // platform_authz / cluster_rbac / code_guard / dry_run
    Status  string // passed / denied / skipped / unknown
    Message string
}
```

兼容策略：

- `prompt` 保留为旧客户端回退字段，但新前端不再把它当作主结构；
- CLI 仍可直接渲染 `prompt`；
- Web 统一事件优先消费结构化字段；
- 所有命令、diff、stdout/stderr 继续经过现有脱敏和截断；
- Secret 审批仍通过既有的带外取值通道，不把明文放入 `ApprovalData`。

#### 4.5.4 kubectl 变更的表达规则

对 `kubectl patch --type=json`：

- 解析 patch JSON，按 `op/path/value` 生成变更表；
- 把 JSON Pointer 转为人类可读路径，例如
  `/spec/template/spec/containers/0/livenessProbe/httpGet/path`
  → `containers[0].livenessProbe.httpGet.path`；
- 无法读取 before 值时，`Before` 明确标记“未读取”，不能伪造旧值；
- 原始命令放在“完整命令”区域，可复制，但默认不抢占首屏；
- JSON 本身可展开/折叠，并用终端块展示，避免一行超长字符串。

对 merge patch / strategic merge patch：

- 展示可识别的字段变化；
- 无法安全解释的嵌套字段保留“查看原始 Patch”入口；
- 显式标注“完整字段影响需结合对象当前状态确认”。

对 `create_resource`：

- 展示 `kind/name/namespace`、创建或更新的对象清单；
- 展示 dry-run/validated/applied 阶段；
- Secret 只展示 key、长度/指纹，不展示值。

#### 4.5.5 审批动作规则

- LOW/MEDIUM：可以提供“确认执行”“本次会话不再询问”“拒绝”；
- HIGH/CRITICAL：只提供“确认执行”“拒绝”，禁止展示“不再询问”；
- 高危操作执行按钮必须使用明确动作文案，例如“执行 patch”，不显示泛化的“是”；
- 同一卡片提交时禁用按钮，防止重复审批；
- 审批过期、预检失效或目标资源变化时，重新展示审批，不自动复用旧授权；
- 卡片明确显示“审批通过不等于执行成功”，执行结果进入工具卡和会话记录。

#### 4.5.6 前端实现边界

本批已按以下顺序落地：

1. 扩展 `sse.ApprovalData` 和 `ApprovalUiData`，保留 `prompt` 兼容；
2. 在 Agent/Service 组装 `Target / Changes / Checks / Verification`；
3. `ApprovalCard` 改为分区渲染，不再把完整 prompt 当作主体；
4. 为 JSON Patch、merge patch、create_resource 分别增加展示适配；
5. 增加结构化审批字段、高危无“不再询问”、重复拒绝按钮防护和本地浏览器验收测试。

本批先覆盖 kubectl JSON Patch、merge patch 和既有 `create_resource` 的通用描述；
审批过期后的重新审批、批量审批卡和移动端专用布局仍作为后续增强项。

## 5. 验收标准

1. `kubectl` 非零退出在 Agent、SSE、历史会话和前端均显示失败。
2. `Forbidden` 被归类为 `RBAC_DENIED`，同批次剩余写调用停止。
3. 真实 `executor.Result` 在工具卡中显示命令、stdout、stderr 和退出码。
4. 非 admin 用户具备 namespace 写授权时可以进入审批，但不具备写授权时在执行前被拒绝。
5. 删除 namespace/PVC/PV 等销毁操作必须具备 `CanDestroy`。
6. Web 客户端无法通过请求体启用 `skipPermissions`。
7. 只读执行身份在会话欢迎区和 Agent 推理上下文中明确可见。
8. Go 测试、vet、前端测试、类型检查与构建通过。
9. HIGH/CRITICAL 审批卡不展示“本次会话不再询问”选项。
10. kubectl JSON Patch 审批卡能展示目标资源、变更路径和变更值。
11. 审批卡能展示平台授权、集群 RBAC 预检、Code Guard 和 dry-run 状态。
12. 审批卡主界面不依赖长 `prompt` 文本换行，旧客户端仍有兼容回退。

- 每个会话绑定明确集群与执行 profile；
- 将 `kubectl` 与结构化工具统一到 `K8sOperation`；

- SSE 增加持久化 `Last-Event-ID` 和跨进程事件总线（当前仅有进程内有界回放）；

## 7. 模型主导诊断升级（v2）

### 7.1 设计判断

当前 Agent 已经具备 Tool Calling，但系统提示词把大量诊断路径写成了固定决策树：

- 先判断意图属于第几层；
- 诊断必须优先 `kubectl -o yaml`；
- 命名空间问题优先 `scan_cluster`；
- 工具调用尽量控制在固定次数内；
- 健康检查必须按固定维度顺序执行。

这些规则适合做兜底，不适合承担诊断智能。强模型的优势是形成假设、选择有区分力的观测、发现证据矛盾后改变方向；固定路径会把这些优势压缩成“按流程选工具”。

模型主导不等于模型不用工具，更不等于模型绕过工具。目标是：

```text
模型决定调查路径
工具提供事实观测和执行能力
平台负责证据保存、权限、审批、审计和验证
```

### 7.2 工具分层

工具不删除，按职责分层：

#### 快速结构化工具

保留 `get_pods/get_deployment/get_service/get_events/get_logs` 等工具，用于低成本浏览和快速定位。

#### 原始证据工具

提供完整 YAML、原始 API 对象、selector、日志时间窗口、previous logs 和资源关系查询。原始证据是根因判断的事实面，摘要工具只作为索引。

#### 关系与变化工具

增加：

- Service → Endpoints/EndpointSlice → Pod；
- Deployment → ReplicaSet → Pod；
- Ingress → Service → Endpoints；
- PVC → PV → StorageClass；
- Node → Pods；
- 同一资源在指定时间或变更前后的 diff。

#### 动作工具

`kubectl` 和 `create_resource` 继续作为写操作工具；审批、RBAC、执行器和审计边界不变。

### 7.3 模型主导调查协议

系统提示词降级为原则和边界，而不是固定流程图：

1. 先识别用户目标，建立初始假设；
2. 选择能区分假设的最小证据集；
3. 优先使用结构化工具快速定位，根因字段不足时读取原始证据；
4. 发现证据矛盾时更新假设，不机械重复同一工具；
5. 记录证据 ID、支持的假设和待补证据；
6. 证据足够时停止，不足时明确说明缺口；
7. 修复必须通过审批，修复后验证闭环。

不再强制固定的工具调用次数、固定健康检查顺序或固定工具树。

### 7.4 证据账本

每个工具结果分配稳定 `evidence_id`，包含：

```text
evidence_id
tool
operation
target
timestamp
summary
raw_reference
```

最终报告必须引用证据 ID。对话历史只承担叙事，证据账本承担可复核事实。

### 7.5 分阶段落地

本批先实现：

- 将诊断 Prompt 从“固定工具决策树”改为模型主导原则；
- 为工具结果分配证据 ID，并传递到 LLM/SSE/前端；
- 新增资源关系查询工具；
- 保留结构化快速工具，同时明确原始证据优先级；
- 增加 Prompt、证据 ID 和关系工具测试。

后续实现：

- 资源 diff 和时间窗口；
- 假设/证据账本持久化；
- 真实故障集 A/B 评测；
- 原始资源查询的分页与上下文预算；
- 模型主导与流程主导的线上指标。

### 7.6 验收标准

1. Prompt 不再要求固定的工具调用顺序；
2. 工具仍由模型自主选择，安全审批与执行器边界不变；
3. 每个工具观察结果都有稳定 evidence ID；
4. 最终报告能引用 evidence ID；
5. 关系查询能返回 Service/Deployment/PVC 等核心故障链；
6. 模型在证据不足时继续调查，而不是凑固定调用次数；
7. 现有聊天、工具、审批和前端功能无回归。
