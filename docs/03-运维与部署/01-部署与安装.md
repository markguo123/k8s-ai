# k8s-ai 安装部署手册

> 版本：DEV-v4.0.0（四期开发中；部署形态见 §4.9）
> 适用：本地命令行 / 企业 Web 平台 / 集群内 CronJob 巡检 / 一体化或前后端分离部署
> 说明：`scan` 提供只读巡检；`chat` 与平台 Web 提供自然语言运维；写操作统一经过审批、
> Code Guard 与 Executor；`create_resource` 提供 dry-run、SSA、verify 与 Secret 专用通道。

---

## 1. 前置要求

| 项              | 要求                                        | 说明                                     |
| --------------- | ------------------------------------------- | ---------------------------------------- |
| 操作系统        | Windows / Linux / macOS                     | 二进制或 Docker 镜像均可                 |
| Go（源码构建）  | ≥ 1.26（go.mod 指定 1.26.0）                | 仅源码构建需要；直接使用镜像不需要       |
| Kubernetes 集群 | ≥ 1.27（CronJob `timeZone` 字段需要 1.27+） | 已实测 1.28                              |
| 访问凭证        | kubeconfig 或集群内 ServiceAccount          | 只读权限即可（见 §4.4）                  |
| LLM 网关        | OpenAI Compatible Chat Completions          | OpenAI / Qwen / DeepSeek / vLLM / Ollama |
| Docker（可选）  | 构建镜像时需要                              | 本机需启动 Docker Desktop/daemon         |

## 2. 安装方式

### 2.1 源码构建（本地命令行）

```bash
# 1) 获取源码后进入项目根目录
cd k8s-ai

# 2) 构建二进制
make build
# 产物：bin/k8s-ai(.exe)

# 3) 验证
./bin/k8s-ai version
# 期望输出：k8s-ai dev (commit none, built unknown)
```

### 2.2 Docker 镜像构建

```bash
# 构建（多阶段：golang:1.26-alpine → distroless static nonroot）
make docker VERSION=1.0.0

# 推送私有仓库（按需）
docker tag k8s-ai:1.0.0 registry.example.com/k8s-ai:1.0.0
docker push registry.example.com/k8s-ai:1.0.0
```

镜像说明：基于 `gcr.io/distroless/static-debian12:nonroot`，非 root（uid 65532）、无 shell、小体积；系统提示词已 go:embed 内嵌，无需额外挂载。

### 2.3 升级

- 本地：重新 `make build` 或拉新镜像；
- 集群内：更新 CronJob 的 image 标签（`kubectl edit cronjob k8s-ai-daily -n k8s-ai`）或重新 apply 新清单；
- 报告 PVC 保留历史报告，升级不丢失。

## 3. 配置

### 3.1 生成配置

```bash
./bin/k8s-ai config init
# 默认生成 ~/.k8s-ai/config.yaml（可用 --config 指定路径，--force 覆盖）
```

### 3.2 配置项详解

`k8s-ai config init` 生成的 `~/.k8s-ai/config.yaml` 按消费面拆成两类：

1. **终端直用配置（引擎键）**：`kubernetes/llm/scan/report/agent/rules` 等供 `k8s-ai chat / k8s-ai scan`
   终端直用；企业平台运行时不再从 YAML 消费这些动态键。
2. **平台静态配置（`platform:` 段）**：生产平台配置文件见 §3.5，只承载静态/启动级参数；7 组动态键
   （model/skill/approval/memory/retention/mcp/ops）唯一落 DB `settings` 表，由配置中心页面维护。

终端直用配置示例：

```yaml
kubernetes:
  kubeconfig: "" # 留空 = 使用 KUBECONFIG 环境变量或默认 ~/.kube/config
  context: "" # kubeconfig 上下文；留空用当前
  namespace: "" # 留空 = 全集群；非空 = 默认只扫该命名空间
  timeout: 30s # 单次 API 请求超时
  qps: 20 # API Server 访问 QPS 上限
  burst: 40 # 突发上限

llm:
  enabled: true # 关闭则只出规则结论
  endpoint: "http://localhost:8000/v1" # OpenAI Compatible 基础地址（自动拼 /chat/completions）
  api_key: "" # 也可用环境变量 K8S_AI_LLM_API_KEY 注入
  model: "qwen-plus" # 建议：快速非思考型模型；思考型大模型较慢
  temperature: 0.1
  max_tokens: 4096
  max_input_tokens: 8192 # 单 Finding 上下文上限
  max_total_tokens: 32768 # 诊断阶段总预算
  max_findings: 30 # 最多送诊 Finding 数
  timeout: 120s # 单次 LLM 调用超时
  stream: true # chat 流式输出（true = SSE 逐 token 推送到终端/Web）
  thinking:
    type: enabled # 标准思考参数：enabled | disabled

scan:
  concurrency: 8 # Phase1 并发
  phase2_concurrency: 4 # Phase2 日志采集并发
  thinking:
    type: enabled # 一期 Scan 思考控制：enabled | disabled
  collect_logs: true
  collect_previous_logs: true
  collect_events: true
  max_log_lines: 500 # 每容器日志行数上限
  max_log_bytes: 65536 # 单容器日志字节上限
  max_log_line_bytes: 1024 # 单行截断
  pod_logs_timeout: 30s # 单 Pod 日志超时
  timeout: 10m # 整次扫描超时（LLM 场景建议 10m）

report:
  directory: "./reports" # 报告目录（集群内 CronJob 用 /reports）
  format: markdown

agent:
  max_iterations: 15 # Agent 往返上限
  max_tool_calls: 20 # 单轮工具调用上限
  timeout: 5m # Agent 单次会话超时
  tool_calling: native # native | shim | auto
  require_approval: true # 写操作必须人工确认
  skip_permissions: false # 非交互自动化，慎用
  session_dir: "~/.k8s-ai/sessions"
  audit_dir: "~/.k8s-ai/audit"
  create:
    enabled: true # create_resource 开关
    deny_kinds: [] # 黑名单，默认空
    allow_kinds: [] # 白名单，默认空
    cluster_kinds: [] # cluster-scoped 授权白名单，默认空即禁止集群级资源
    max_objects_per_call: 3 # 单次最多对象数（1-10）
    max_manifest_bytes: 8192 # 单次 manifest 最大字节数（1KiB-1MiB）
  secret:
    access: "create_only" # off | create_only；read_write 未开放

rules:
  enabled: [] # 非空则只启用这些规则
  disabled: [] # 禁用指定规则
```

> 现状提醒（v1.11 修订）：`config init` 模板当前仍输出引擎键，四期将收敛为只输出静态/`platform:` 启动键
> 与 CLI 直用缺省；引擎键仅作为终端直用的本地配置保留，7 组动态键唯一落 DB `settings` 表，不再维护
> "文件 vs 页面"双权威（见 ADR-031，落地任务 P6.12）。

### 3.3 环境变量与优先级

优先级：**CLI > 环境变量 > YAML > 默认**。

常用环境变量：`KUBECONFIG`、`K8S_AI_LLM_ENDPOINT`、`K8S_AI_LLM_API_KEY`、`K8S_AI_LLM_MODEL`、`K8S_AI_LLM_TIMEOUT`、`K8S_AI_SCAN_TIMEOUT`、`K8S_AI_LLM_DISABLE_THINKING`（true/false）。

> 注意：以上优先级只作用于**静态配置**。四期平台的 7 组动态键另有运行时优先级（环境变量覆盖层 >
> DB `settings` > 内置默认），且 env 覆盖面是收窄且固定的集合；DB `settings` 仍是动态键的默认唯一权威源与唯一写入目标，
> env 命中不回写 DB，见 §3.5 与 ADR-040。

### 3.4 校验配置与连通性

```bash
./bin/k8s-ai config validate --config ~/.k8s-ai/config.yaml
# 期望：config OK: server version v1.28.13
```

### 3.5 四期平台配置面（静态/动态拆离 + 动态键运行时优先级）

> 状态：口径已定（ADR-031 v1.13 / ADR-040 / ADR-042，决策 D-21 / D-29 / D-31）。`platform:` 静态段已被
> `server` 消费；动态键的运行时读取（含 env 覆盖层与未配置显式报错）随 P6.1 落地，模板收敛与键集合测试
> 锁定随 P6.12 落地。

四期平台运行参数拆成两层，目标是"一份 ConfigMap（静态）+ 一份 Secret（敏感）+ DB settings（动态）就能完整描述"：

```yaml
platform:
  server:
    addr: "127.0.0.1:8080"      # 平台主进程监听地址（server）
    tls:
      enabled: false
      cert_file: ""
      key_file: ""
  store:
    driver: "mysql"             # mysql | sqlite（四期主存储为 MySQL，见 ADR-042）
    sqlite_path: "~/.k8s-ai/k8s-ai.db"
    dsn: ""                     # 值只接受 K8S_AI_PLATFORM_STORE_DSN / Secret 注入；YAML 留空，非空会告警
  auth:
    admin_username: "admin"
    token_ttl: 24h
    session_store: "memory"     # 本期固定内存态，扩副本前需持久化
```

六条边界：

1. **静态/动态拆离**：`config.yaml` 只承载 `platform:` 静态/启动级参数；7 组动态键（model/skill/approval/
   memory/retention/mcp/ops）**不在 YAML 中出现**，唯一权威源是 DB `settings` 表，由配置中心页面维护；
   server 启动只读静态段，Chat/Agent/LLM 运行时统一从 Store 读 DB。
2. **敏感值不落 YAML 明文**：`K8S_AI_ADMIN_PASSWORD`（首启引导 admin）、`K8S_AI_LLM_API_KEY`、需要时
   `K8S_AI_PLATFORM_STORE_DSN` 走环境变量 / Secret；模型 api_key、MCP env、kubeconfig 等动态敏感值
   加密落 DB（`SecretCipher`/`K8S_AI_ENC_KEY`）。
3. **优先级（静态段）不变**：CLI > 环境变量 > YAML > 默认；`server --addr/--db` 保留为覆盖手段，不是唯一入口。
4. **优先级（动态键）= 环境变量覆盖层 > DB `settings` > 内置默认**（ADR-040），其中 DB `settings` 是默认唯一权威源与唯一写入目标，env 命中不回写 DB。
   env 覆盖面收窄且固定：
   `K8S_AI_LLM_{ENDPOINT,MODEL,API_KEY,TEMPERATURE,MAX_TOKENS,TIMEOUT}` 与 `K8S_AI_PLATFORM_STORE_DSN`，
   其余动态键只认 DB。内置默认（`http://localhost:8000/v1` + `qwen-plus`）仅兜底，容器内两处都没配时
   Chat 返回明确错误提示，不静默失败；被 env 覆盖的键在配置中心页面标注「已被环境变量覆盖」。
5. **模板收敛 + 显式迁移**：`config init` 只输出静态/`platform:` 键与 CLI 直用缺省，不再输出全量引擎键；
   `config validate` 对未识别键给出告警，并支持 `--mode server|cli`。
   导入 settings 后以 DB 为权威，不随启动自动导入。
6. **迁移入口分工**：平台 schema 幂等升级用 `k8s-ai db migrate`（仅 schema，可作 K8s Job / initContainer，
   `server` 启动内保留同一迁移的幂等兜底）；`k8s-ai migrate` 只做三期旧配置的一次性导入，两者不可混用。

## 4. Kubernetes 集群内部署（每日巡检 CronJob）

### 4.1 清单总览

`deploy/` 目录包含：

| 文件                    | 资源                        | 用途                  |
| ----------------------- | --------------------------- | --------------------- |
| namespace.yaml          | Namespace k8s-ai            | 部署命名空间          |
| serviceaccount.yaml     | ServiceAccount k8s-ai       | 运行身份              |
| clusterrole.yaml        | ClusterRole k8s-ai-readonly | 只读权限              |
| clusterrolebinding.yaml | ClusterRoleBinding          | SA 绑定只读角色       |
| configmap.yaml          | ConfigMap k8s-ai-config     | 非敏感配置            |
| secret.example.yaml     | Secret k8s-ai-llm（示例）   | LLM api_key（需替换） |
| pvc.yaml                | PVC k8s-ai-reports          | 报告持久化 1Gi        |
| cronjob.yaml            | CronJob k8s-ai-daily        | 每日 08:00 巡检       |

> deployment.yaml / service.yaml（Server 模式，一期 1.2）见 §4.7。

### 4.2 分步安装

```bash
# 1) 命名空间 + 身份 + 只读 RBAC
kubectl apply -f deploy/namespace.yaml
kubectl apply -f deploy/serviceaccount.yaml
kubectl apply -f deploy/clusterrole.yaml
kubectl apply -f deploy/clusterrolebinding.yaml

# 2) 配置（LLM 端点/模型/扫描参数）
kubectl apply -f deploy/configmap.yaml

# 3) LLM api_key（复制示例并替换）
cp deploy/secret.example.yaml deploy/secret.yaml
# 编辑 deploy/secret.yaml：把 stringData.api_key 的 REPLACE_ME 换成真实 key
kubectl apply -f deploy/secret.yaml

# 4) 报告 PVC
kubectl apply -f deploy/pvc.yaml

# 5) 每日巡检 CronJob
kubectl apply -f deploy/cronjob.yaml
```

### 4.3 安装后验证

```bash
kubectl get cronjob -n k8s-ai
# NAME           SCHEDULE      SUSPEND   ACTIVE
# k8s-ai-daily   0 8 * * *     False     0

# 手动触发一次立即巡检（可选，只读）
kubectl create job --from=cronjob/k8s-ai-daily k8s-ai-manual -n k8s-ai
kubectl logs job/k8s-ai-manual -n k8s-ai -f
# 期望看到：Phase1 采集完成 → LLM 诊断进行中 → LLM 诊断完成 → 终端摘要

# 查看报告
kubectl exec -n k8s-ai $POD -- cat /reports/latest.md | head -50
```

### 4.4 RBAC 说明（deploy/clusterrole.yaml）

- 只授权 `get/list/watch` + `pods/log get`；secrets 仅元数据/键级读取（内容值禁止）；**不含** pods/exec、pods/portforward、metrics；
- 一期为全集群只读 ClusterRole（ClusterRoleBinding）；如需最小化，可改为仅巡检特定 namespace 的 Role；
- 清单由架构测试解析断言（`go test ./tests/arch/`），误加写权限会测试失败。

### 4.5 CronJob 特性

- 调度：`0 8 * * *`，`timeZone: Asia/Shanghai`；
- `concurrencyPolicy: Forbid`：上一次未跑完不并发；
- `restartPolicy: OnFailure` + `backoffLimit: 2`；
- 非 root：`runAsUser/Group: 65532`、`fsGroup: 65532`、drop ALL capabilities；
- 报告写入 PVC `/reports`（latest.md / latest.json / 时间戳 .md）；
- LLM api_key 通过 Secret 环境变量注入（`optional: true`，未配置时 LLM 自动降级为规则结论）。

### 4.6 Server 模式部署（一期 1.2，HTTP API）

可选部署：`k8s-ai server` 提供健康检查、版本与异步扫描 API（供平台/二期 Agent 调用）。

> **现状提示（2026-10-23）**：本节的清单尚未按企业平台两种形态补齐。已知缺口：
> 未挂载 ConfigMap、没有传 `--config`；没有数据 PVC，`--db` 默认落在容器可写层，**重启即丢数据**；
> 未注入 `K8S_AI_ADMIN_PASSWORD`（四期 `server` 首次启动缺少它会直接失败）；没有 Ingress 清单与
> migration Job/initContainer；`server` 也没有 SPA 静态资源通道，页面仍靠 Vite dev server 提供。
> 四期口径见 §4.9 与 ADR-029 / ADR-030，补齐动作排在开发计划 P6.1 / P6.2 / P6.11。

```bash
# 部署 Server（需先完成 4.2 的 SA/RBAC/配置/Secret）
kubectl apply -f deploy/deployment.yaml
kubectl apply -f deploy/service.yaml

# 验证
kubectl get deploy,svc -n k8s-ai
```

API：

| 方法 | 路径               | 说明                                                                  |
| ---- | ------------------ | --------------------------------------------------------------------- |
| GET  | /healthz           | 存活探针                                                              |
| GET  | /readyz            | 就绪探针                                                              |
| GET  | /version           | 版本信息                                                              |
| POST | /api/v1/scans      | 创建异步扫描（body=ScanOptions），返回 scanId；已有任务运行时返回 409 |

注意：与 CronJob 共用报告 PVC 时需 RWX 存储类；否则给 Server 单独挂载或不同卷。

### 4.7 历史对比（日报趋势）

### 4.9 四期平台部署架构（默认一体化 + 可选前后端分离）

四期采用「前后端工程分离 + 单二进制一体化交付」架构，支持两种部署形态：
**形态 A 一体化部署（默认）** 与 **形态 B 前后端分离部署（可选）**，两者共享同一套业务代码与
`/api/v1` API 契约，默认单副本稳定运行。Kubernetes 是生产主场景。

| 项 | 形态 A 一体化（默认） | 形态 B 前后端分离（可选） |
| --- | --- | --- |
| 前端交付 | `web/dist` 经 `go:embed` 内嵌进 Go 二进制 | `web/dist` 打进独立 `k8s-ai-web`（Nginx）镜像 |
| 后端职责 | `k8s-ai server` 同端口提供 `/api/v1`（含 Chat SSE）与 SPA | 后端关闭静态路由，只提供 `/api/v1`（含 Chat SSE）与 `/healthz`/`/readyz`/`/version` |
| 路由 | 单域名、单入口 | 同域名按路径分流：`/assets/*` 与 `/` → 前端；`/api/v1/*` → 后端 |
| 前端 API 地址 | 相对路径 `/api/v1` | 相对路径 `/api/v1`（构建期可用 `VITE_API_BASE` 覆盖；跨域/独立子域非强制） |
| 副本 | `replicas: 1` | 前后端各 `replicas: 1`；多副本仍需满足 ADR-030 前置条件 |
| 适用 | 单机、POC、测试、企业常规、离线交付、快速升级 | 客户要求前后端独立发布/回滚、企业统一静态托管/网关/CDN |

### 4.9.1 构建产物

```bash
# 默认路径（可复现）：镜像构建自带 node 阶段，干净检出即可产出含前端的镜像
make docker VERSION=4.0.0        # node 构建 web/dist → golang 内嵌 → distroless

# 本地开发/调试：先手工构建前端，再编译二进制（web/dist 经 go:embed all:web/dist 内嵌）
cd web && npm ci && npm run build && cd ..
make build                       # bin/k8s-ai（内含 web/dist）

# 离线/加速路径：用 BuildKit named build context 覆盖 node 阶段，复用本地已构建产物
docker build --build-context webdist=./web/dist -t k8s-ai:4.0.0 .

# 形态 B：两个独立 Dockerfile —— 后端 API 镜像 + 前端 Nginx 静态镜像（可各自构建与升级）
make docker VERSION=4.0.0
docker build -f deploy/web.Dockerfile -t k8s-ai-web:4.0.0 .
```

构建口径（ADR-041）：

- **两个 Dockerfile 各自独立**：仓库根 `Dockerfile` 只构建后端镜像（形态 A 内嵌 `web/dist`；形态 B 复用
  同一后端镜像，以 `platform.server.static_enabled: false` 关闭静态托管），`deploy/web.Dockerfile` 只构建
  Nginx 前端静态镜像；两者互不依赖，可分别构建、发布与回滚。
- 默认路径必须是 Dockerfile 内的 node 构建阶段，保证「克隆即构建」可复现；`--build-context` 只是可选加速，
  不是默认。node 阶段需要 npm registry，**纯离线环境**必须走 `--build-context` 或配置内网 npm 镜像源。
- `web/dist` 目录由 `web/dist/.gitkeep` 占位入库，`web/.gitignore` 用 `dist/*` + `!dist/.gitkeep`
  （整目录忽略 `dist` 会让反向放行失效）。
- `dist` 为空时编译与启动都不失败，访问页面返回「前端产物未构建」的明确提示。
- `.dockerignore` 排除 `web/node_modules`，避免宿主机依赖树进入构建上下文。
- 运行镜像是 distroless static nonroot：无 shell、无 kubectl，写执行只走 client-go。
- BuildKit 不可用（无法用 named build context）时，退化到 `deploy/Dockerfile.prebuilt-dist`：
  该变体不含 node 阶段，直接 COPY 宿主机已构建好的 `web/dist`，仅供离线交付使用。

> 随 P6.11 落地，形态 B 镜像随 P6.13 落地。

### 4.9.3 形态 B：前后端分离部署（K8s 可选）

两个 Deployment，共用一个 Ingress：

```text
Deployment/k8s-ai-web     : Nginx，托管 /usr/share/nginx/html（web/dist）
Deployment/k8s-ai-server  : 纯 API，静态路由关闭
Service/k8s-ai-web        : 80
Service/k8s-ai-server     : 8080
Ingress                   : /api/v1/* → k8s-ai-server；/assets/* 与 / → k8s-ai-web
```

前端 Nginx（`deploy/web.Dockerfile` + `deploy/nginx.conf`）关键配置：

```nginx
server {
    listen 80;
    root /usr/share/nginx/html;

    location = /index.html {
        add_header Cache-Control "no-cache";
    }
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }
    location / {
        try_files $uri $uri/ /index.html;      # SPA history fallback
    }
    # SSE：仅当由本 Nginx 反代后端 API（不走 Ingress 同域分流）时需要
    location /api/v1/ {
        proxy_pass http://k8s-ai-server:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;                 # 后端 SSE 已自带 X-Accel-Buffering: no，此处显式兜底
        proxy_cache off;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
    # 如前端与后端不同域名，才需要在 Nginx/Ingress 做 API 反代；同域路径分流由 Ingress 完成
}
```

> SPA fallback 只允许覆盖前端路由。后端侧未知 `/api/v1/*` 必须返回 JSON 404，不得被 fallback 吞成
> `index.html`，否则前端拿到一坨 HTML 无法定位错误。

Ingress（同域路径分流，推荐）：

```yaml
spec:
  rules:
    - host: k8s-ai.example.com
      http:
        paths:
          - path: /api/v1
            pathType: Prefix
            backend: { service: { name: k8s-ai-server, port: { number: 8080 } } }
          - path: /
            pathType: Prefix
            backend: { service: { name: k8s-ai-web, port: { number: 80 } } }
```

SSE 反代要点（聊天长连接）：

- 关闭响应缓冲（Nginx `proxy_buffering off`；Ingress Controller 对应 annotation 视实现而定）
- 放大读超时（如 `proxy_read_timeout 3600s`）
- 保留 `Host`/`X-Forwarded-*` 头，便于审计与登录态判断
- 前端只使用相对路径 `/api/v1`，因此默认不需要 CORS
- 服务端配合：Chat SSE 响应带 `X-Accel-Buffering: no`，Nginx 收到即自动关闭该响应的缓冲

nginx-ingress 参考 annotation：

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/proxy-buffering: "off"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "3600"
```

部署步骤：

```bash
kubectl apply -f deploy/namespace.yaml
kubectl apply -f deploy/serviceaccount.yaml
kubectl apply -f deploy/clusterrole.yaml
kubectl apply -f deploy/clusterrolebinding.yaml
kubectl apply -f deploy/configmap.yaml
kubectl apply -f deploy/secret.yaml
kubectl apply -f deploy/pvc.yaml                   # 可选，同上
kubectl apply -f deploy/db-migrate-job.yaml
kubectl apply -f deploy/deployment.yaml            # 后端纯 API（已关闭静态路由）
kubectl apply -f deploy/service.yaml
kubectl apply -f deploy/web-deployment.yaml        # 前端 Nginx + dist
kubectl apply -f deploy/web-service.yaml
kubectl apply -f deploy/ingress.yaml               # 按路径分流
```

### 4.9.6 数据库前置（MySQL 主口径）

产品**不执行** `CREATE DATABASE`：库、账号与权限由 DBA 预建，`k8s-ai server` 与 `k8s-ai db migrate`
只在已授权的库内建表与升级 schema。

```bash
# 由 DBA 执行（库名与账号按现场规范替换，本手册不给具体环境值）
CREATE DATABASE k8s_ai DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'k8s_ai'@'%' IDENTIFIED BY '<由密码管理系统生成>';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, DROP, REFERENCES,
      CREATE TEMPORARY TABLES, LOCK TABLES ON k8s_ai.* TO 'k8s_ai'@'%';
```

- 库默认字符集建议 utf8mb4。即使库默认是 utf8mb3，产品建表 DDL 也会显式带
  `DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci`（`internal/store/dialect.go`），不依赖库默认；
  但库与表保持一致可避免临时表、比较与排序意外降级。
- 平台账号只授予该库的 DML 与建表/改表/索引/DROP，不需要 `SUPER`、`FILE` 等全局权限。
- DSN 只经 `K8S_AI_PLATFORM_STORE_DSN` / Secret 注入，必须带 `parseTime=true`；集群内部署填集群内
  Service 地址，本地开发与门禁实跑填外部可达地址。两者都只是注入值，不写进清单、文档与测试代码。
- `deploy/example/` 提供 MySQL 接入示例清单（Secret/Deployment/迁移 Job 占位），属**示例口径、非产品
  默认**，不含任何现场地址与口令。
- 门禁实跑：`K8S_AI_TEST_MYSQL_DSN` 注入测试库后，连通、schema 迁移幂等、重启续用三类用例必须真实
  执行；测试库与产品库分开（如 `k8s_ai_test` 与 `k8s_ai`），MySQL 门禁用例不得长期处于 skipped。

### 4.10 一键安装（deploy/install.sh）

`deploy/install.sh` 只做参数替换、顺序编排与幂等重跑，不替代正式 YAML：正式清单必须能独立
`kubectl apply` 跑通。

```bash
IMAGE=<registry>/<repo>/k8s-ai TAG=4.0.0 \
NAMESPACE=k8s-ai STORAGE_CLASS=<storage-class> INGRESS_HOST=<host> \
STORE_DRIVER=mysql ENABLE_WRITE=false ./deploy/install.sh
```

| 参数 | 含义 |
| --- | --- |
| `IMAGE` / `TAG` | 镜像地址与标签；必填，脚本不内置任何默认仓库地址 |
| `NAMESPACE` | 命名空间，默认 `k8s-ai` |
| `STORE_DRIVER` | `mysql`（默认）或 `sqlite` |
| `MYSQL_DSN` | MySQL 模式下必填，写入 Secret，不进 ConfigMap |
| `STORAGE_CLASS` | 为空则不创建 PVC（MySQL 模式下常见） |
| `INGRESS_HOST` | Ingress 域名/VIP 主机名，必填 |
| `ENABLE_WRITE` | `true` 时显式 apply `rbac-write.example.yaml` 并要求二次确认 |
| `ADMIN_PASSWORD` | 缺省随机生成，只打印一次 |

密钥与口令语义（必须照此实现）：

- `K8S_AI_ENC_KEY`：Secret 已存在则**复用**，绝不覆盖；缺失才生成，并在本地备份一份（权限 600）。
  轮换只走显式 `--rotate`。**该密钥一旦丢失，已加密落库的模型 api_key、MCP env、kubeconfig 全部不可恢复。**
- `ADMIN_PASSWORD`：缺省随机生成，只在本次安装输出一次，不落文件、不重复打印。
- `ENABLE_WRITE=true`：显式 apply 写权限 RBAC 并二次确认，默认保持只读。
- 幂等：重复执行不重置密钥、不轮换口令、不改已存在的 Secret 数据；建议先 `kubectl diff` 预演。

脚本与清单中禁止硬编码任何环境信息，环境差异只由上述参数提供。

## 6. 故障排查（运维）

| 现象                     | 排查                                                                                                                |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| LLM 一直"诊断中"         | 思考型大模型单次 1.5-2 分钟属正常；确认 `llm.timeout`/`scan.timeout` 足够（10m）；或换快速模型 / 设置 `llm.thinking.type: disabled` 或 `scan.thinking.type: disabled` |

| RBAC 403                 | `kubectl auth can-i list pods --as=system:serviceaccount:k8s-ai:k8s-ai -n <ns>`；确认 clusterrolebinding 已应用     |

### 8.2 浏览器工作台

企业平台由单一主进程 `k8s-ai server` 提供认证、Session、Chat SSE、审批、配置、用户与审计 API；
形态 A 同进程托管 SPA，形态 B 由独立静态服务托管 `web/dist`。所有请求统一走 `/api/v1`。

```bash
K8S_AI_ADMIN_PASSWORD='你的强密码' \
  k8s-ai server --addr 127.0.0.1:8080 --config ~/.k8s-ai/config.yaml
```

本地前端开发：

```bash
cd web
npm run dev
# 打开 http://127.0.0.1:5173，/api/v1 代理到 8080
```

会话接口 `/api/v1/sessions*` 与平台 API 使用同一登录 Token。`user/operator` 只能查看和操作
自己的会话；admin 可查看并操作全部会话。

### 8.3 写操作与 RBAC

- 默认 `agent.require_approval: true`，每个写工具调用都弹审批卡片（展示人类可读命令 + 变更）；
- 非交互自动化可用 `--skip-permissions` 显式放行（审计会记录）；
- 需要让 Agent 执行写操作时，按需应用写权限示例：`kubectl apply -f deploy/rbac-write.example.yaml`（默认 clusterrole 保持只读）。

### 8.4 kubectl 兜底工具

- 通用 `kubectl` 工具需要本机安装 kubectl 并在 PATH（或配置 `kubernetes.kubectl_path`）；
- kubectl 工具会继承 `kubernetes.kubeconfig`（通过 `KUBECONFIG` 环境变量传入子进程），保证写命令与 client-go 使用同一集群配置；
- 只读结构化工具与容器内写操作统一走 client-go；kubectl 仅作为显式配置的非容器兜底通道。

### 8.5 常用配置（终端直用）

> 以下键用于 `k8s-ai chat / k8s-ai scan` 终端直用；企业平台运行的 7 组动态键（model/skill/
> approval/memory/retention/mcp/ops）唯一落 DB `settings` 表，由配置中心页面维护，不在 config.yaml 配置。

```yaml
agent:
  max_iterations: 15 # LLM 往返上限
  max_tool_calls: 20 # 累计工具调用上限
  tool_calling: native # native | shim | auto
  require_approval: true # 写操作默认要求确认
  skip_permissions: false # 配置级免审批（等效 --skip-permissions）
  deny_ops: [] # 可选硬拦截，如 ["delete namespace"]
  disabled_tools: [] # 注册后移除指定工具，例如 ["kubectl"] 禁止写入口
  session_dir: ~/.k8s-ai/sessions
  audit_dir: ~/.k8s-ai/audit
mcp:
  enabled: false
  servers: []
```
