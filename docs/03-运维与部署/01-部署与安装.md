# k8s-ai 安装部署手册

> 版本：DEV-v4.0.0（四期）
> 适用：企业 Web 平台生产部署（Kubernetes，一体化 / 前后端分离）、集群内 CronJob 每日巡检、本地与单机运行

## 1. 前置要求

| 项 | 要求 | 说明 |
| --- | --- | --- |
| 操作系统 | Windows / Linux / macOS | 二进制或 Docker 镜像均可 |
| Go（仅源码构建） | ≥ 1.26（`go.mod` 指定 1.26.0） | 用镜像部署时不需要 |
| Kubernetes 集群 | ≥ 1.27 | CronJob `spec.timeZone` 需要 1.27+；已实测 1.28 |
| Ingress Controller | 任一 `networking.k8s.io/v1` 实现 | 清单占位写的是 `nginx`；换成别的控制器要自行改 SSE annotation |
| 存储类 | 现场 `StorageClass` 名 | 仅创建 PVC 时需要（报告留档或 SQLite 兜底） |
| MySQL | 5.7+ / 8.x，库与账号由 DBA 预建 | 四期主存储；产品不执行 `CREATE DATABASE`，见 §3.6 与 §4.3 |
| 访问凭证 | kubeconfig 或集群内 ServiceAccount | 默认只读即可（见 §4.16） |
| LLM 网关 | OpenAI Compatible Chat Completions | OpenAI / Qwen / DeepSeek / vLLM / Ollama |
| Docker（可选） | 构建镜像时需要 | 构建与推仓由部署方执行，本仓库不产出镜像 |

## 2. 构建交付物

交付物是三件：后端镜像、（形态 B 才需要的）前端镜像、以及 `deploy/` 清单。清单不含任何环境专有值，
环境差异一律由占位值替换或部署参数提供。

### 2.1 二进制（本地命令行 / 单机）

```bash
cd k8s-ai
make build                 # 产物 bin/k8s-ai(.exe)
./bin/k8s-ai version       # 期望：k8s-ai dev (commit none, built unknown)
```

### 2.2 后端镜像（仓库根 `Dockerfile`）

```bash
make docker VERSION=4.0.0            # IMAGE ?= k8s-ai，产出 k8s-ai:4.0.0

# 或直接
docker build --build-arg VERSION=4.0.0 --build-arg COMMIT=<sha> -t <registry>/k8s-ai:4.0.0 .
docker push <registry>/k8s-ai:4.0.0
```

三阶段构建：`node:22-alpine` 构建 `web/dist` → `golang:1.26-alpine` 内嵌编译（`go:embed all:web/dist`，
ldflags 注入 version/commit/date）→ `debian:bookworm-slim` 运行阶段并加装排查工具层。运行镜像仍非 root
（uid/gid 65532），内置 `bash`、coreutils、`jq`、`curl`、DNS/ICMP 诊断工具，以及 `kubectl`。kubectl 有两条投递路径，**离线投递优先**：把 `kubectl`（连同内容为裸 hash 的
`kubectl.sha256`）放进 `deploy/kubectl/`，构建全程零外网——气隙现场只能走这条；该目录为空时
才按 `KUBECTL_VERSION`/`KUBECTL_DOWNLOAD_BASE` 下载并 `sha256sum -c` 校验（base 目录结构须与
`dl.k8s.io/release` 一致，国内可用 `https://files.m.daocloud.io/dl.k8s.io/release`，按
`TARGETARCH` 取架构）。Go 依赖同理传 `--build-arg GOPROXY=https://goproxy.cn,direct`。
系统提示词已内嵌，无需额外挂载。口径见 §4.17 与 ADR-044 v1.1。

硬合规现场可另建无 shell 变体（与形态 A/B 无关，也不影响 `static_enabled`）：

```bash
docker build -f Dockerfile.distroless --build-arg VERSION=4.0.0 -t <registry>/k8s-ai:4.0.0-distroless .
```

两个 Dockerfile 共用同一构建阶段，只差运行阶段与工具层，配 `platform.exec.shell_enabled: false` 使用。
变体档基座是 `gcr.io/distroless/static-debian12:nonroot`：现场访问不了 gcr.io 时，先把该基座镜像
同步进内网 registry（或 `docker load` 到构建机），再把 `Dockerfile.distroless` 的 `FROM` 指过去。

形态 A 与形态 B **共用这一个后端镜像**：形态 B 只是用环境变量把内嵌静态托管关掉，不需要单独构建后端镜像。

### 2.3 前端镜像（`deploy/separated/web.Dockerfile`，仅形态 B）

```bash
docker build -f deploy/separated/web.Dockerfile -t <registry>/k8s-ai-web:4.0.0 .
docker push <registry>/k8s-ai-web:4.0.0
```

基于 `nginxinc/nginx-unprivileged:1.27-alpine`，把 `web/dist` 与 `deploy/separated/nginx.conf` 打进镜像。
两个 Dockerfile 互不依赖、可各自构建与回滚（ADR-041）。

注意两点：

- `nginx-unprivileged` 变体以 uid 101 运行，绑不了 80，因此**容器监听 8080**，由 Service 做 80 → 8080；
- 前端只用相对路径 `/api/v1`，**没有构建期 API 地址开关**，也不需要（同域分流由 Ingress 完成，天然无 CORS）。

### 2.4 构建口径与离线交付

- 默认路径必须是 Dockerfile 内的 node 阶段，保证「克隆即可构建」可复现；node 阶段需要 npm registry
  或内网镜像源。
- 离线 / 加速：用 BuildKit named build context 覆盖 node 阶段，
  `docker build --build-context webdist=<dir-containing-dist> -t k8s-ai:dev .`。
  注意传入的目录**根下要有一个 `dist/` 子目录**（例如 `--build-context webdist=./web`）。
- `web/dist` 由 `web/dist/.gitkeep` 占位入库，`web/.gitignore` 用 `dist/*` + `!dist/.gitkeep`
  （整目录忽略会让反向放行失效）。
- `dist` 为空时编译与启动都不失败，访问页面返回 503 与「前端产物未构建」的明确提示，而不是空白 404。
- `.dockerignore` 排除 `web/node_modules`，避免宿主机依赖树进入构建上下文。

### 2.5 版本与升级物

`k8s-ai version` 与 `GET /version` 输出同一份 version/commit/date。升级只需要换镜像 TAG：
后端 Deployment、迁移 Job 用的是同一个镜像地址，**两处必须一起换**（清单里是同一个 `image:` 值）。

## 3. 配置

### 3.1 两套配置面与生成方式

k8s-ai 有两套彼此独立的配置面，别混用：

1. **终端直用配置（引擎键）**：`kubernetes` / `llm` / `scan` / `report` / `agent` / `rules`，
   供 `k8s-ai scan` / `k8s-ai chat` 命令行直用；企业平台运行时**不再从 YAML 消费这些动态键**。
2. **平台静态配置（`platform:` 段 + 落盘目录）**：描述「这个进程怎么起」，由 `server` 消费，见 §3.5。
   七组动态业务键（model / skill / approval / memory / retention / mcp / ops）唯一落 DB `settings` 表，
   由 Web 配置中心维护，刻意不出现在任何 YAML 里。

```bash
k8s-ai config init                       # 平台静态配置模板 → ~/.k8s-ai/config.yaml
k8s-ai config init --cli                 # 终端直用全量模板 → ~/.k8s-ai/cli.yaml
k8s-ai config init --force               # 覆盖已有文件
```

`config init` 只输出所属剖面的键，两套模板的键集合分别由测试锁定，多余的键 `config validate` 会告警。

### 3.2 终端直用配置详解（引擎键）

`k8s-ai config init --cli` 生成的 `~/.k8s-ai/cli.yaml`：

```yaml
kubernetes:
  kubeconfig: ""            # 留空 = 用 KUBECONFIG 环境变量或默认 ~/.kube/config
  context: ""               # kubeconfig 上下文；留空用当前
  namespace: ""             # 留空 = 全集群；非空 = 默认只操作该命名空间
  kubectl_path: ""          # 本机 kubectl 路径（PATH 找不到时指定）
  timeout: 30s              # 单次 API 请求超时
  qps: 20                   # API Server 访问 QPS 上限
  burst: 40                 # 突发上限

llm:
  enabled: true             # 关闭则只出规则结论
  endpoint: "http://localhost:8000/v1"   # OpenAI Compatible 基础地址（自动拼 /chat/completions）
  api_key: ""               # 也可用环境变量 K8S_AI_LLM_API_KEY 注入
  model: "qwen-plus"        # 建议快速非思考型模型；思考型大模型较慢
  temperature: 0.1
  max_tokens: 4096
  max_input_tokens: 8192    # 单 Finding 上下文上限
  max_total_tokens: 32768   # 诊断阶段总预算
  max_findings: 30          # 最多送诊 Finding 数
  timeout: 120s             # 单次 LLM 调用超时
  stream: true              # 流式输出（SSE 逐 token 推送到终端/Web）
  thinking:
    type: enabled           # enabled | disabled

scan:
  concurrency: 8            # Phase1 采集并发
  phase2_concurrency: 4     # Phase2 日志采集并发
  thinking:
    type: enabled           # 一期 Scan 思考控制
  collect_logs: true
  collect_previous_logs: true
  collect_events: true
  max_log_lines: 500        # 每容器日志行数上限
  max_log_bytes: 65536      # 单容器日志字节上限
  max_log_line_bytes: 1024  # 单行截断
  pod_logs_timeout: 30s
  timeout: 10m              # 整次扫描超时（LLM 场景建议 10m）

report:
  directory: "./reports"    # 报告目录（集群内 CronJob 用 /reports）
  format: markdown

agent:
  max_iterations: 15        # Agent 往返上限
  max_tool_calls: 20        # 单轮工具调用上限
  timeout: 5m
  tool_calling: native      # native | shim | auto
  require_approval: true    # 写操作必须人工确认
  skip_permissions: false   # 非交互自动化免审批，慎用
  session_dir: "~/.k8s-ai/sessions"
  audit_dir: "~/.k8s-ai/audit"
  create:
    enabled: true           # create_resource 开关
    deny_kinds: []          # 黑名单，默认空
    allow_kinds: []         # 白名单，默认空
    cluster_kinds: []       # cluster-scoped 授权白名单，默认空即禁止集群级资源
    max_objects_per_call: 3      # 单次最多对象数（1-10）
    max_manifest_bytes: 8192     # 单次 manifest 最大字节（1KiB-1MiB）
  secret:
    access: "create_only"   # off | create_only；read_write 未开放

rules:
  enabled: []               # 非空则只启用这些规则
  disabled: []              # 禁用指定规则
```

这些键只在终端直用路径生效。企业平台里对应的运行时参数来自配置中心写入的 DB `settings`，改完即时生效、
不回写文件（见 §3.3 与 §3.5）。

### 3.3 环境变量与优先级

**静态配置**优先级：CLI > 环境变量 > YAML > 默认。常用变量：`KUBECONFIG`、`K8S_AI_LLM_ENDPOINT`、
`K8S_AI_LLM_API_KEY`、`K8S_AI_LLM_MODEL`、`K8S_AI_LLM_TIMEOUT`、`K8S_AI_SCAN_TIMEOUT`、
`K8S_AI_LLM_DISABLE_THINKING`。

**动态业务键**走另一套口径：DB `settings` 是默认唯一权威源与唯一写入目标，环境变量只对**收窄且固定的
白名单**作部署期只读覆盖，命中不回写 DB，分两档（ADR-040 v1.2）：

| 档位 | 键 | 语义 |
| --- | --- | --- |
| 密钥态 | `K8S_AI_LLM_API_KEY`、`K8S_AI_PLATFORM_STORE_DSN` | env/Secret **恒优先**，页面值暂不生效（页面会标注来源、保存时给显式提示） |
| 种子态（seed-once） | `K8S_AI_LLM_{PROVIDER,ENDPOINT,MODEL}`、`K8S_AI_{KUBECONFIG,KUBE_CONTEXT,NAMESPACE,KUBECTL_PATH}` | 仅当该键在 DB **无值**时提供首启种子值；管理员在页面保存过一次之后，环境变量永久让位给页面 |

白名单之外一律不认环境变量（`temperature` / `max_tokens` / `timeout` 刻意不纳入），只认 DB。
内置默认（`http://localhost:8000/v1` + `qwen-plus`）仅兜底，两处都没配时 Chat 返回明确错误而不是静默失败。

一句话口径：**页面配过的以页面为准，页面没配过的用部署变量兜底，密钥永远以 Secret 为准。**

### 3.4 校验配置与连通性

```bash
k8s-ai config validate --config ~/.k8s-ai/config.yaml                       # 默认 server 剖面
k8s-ai config validate --config ~/.k8s-ai/cli.yaml --mode cli
k8s-ai config validate --config <path> --mode server --skip-connectivity     # 只校验，不连集群
```

`--mode server|cli` 决定「哪些键算认得的键」：server 剖面下出现引擎键、cli 剖面下出现 `platform:` 段，
都会给未识别键告警。期望输出形如 `config OK (server mode): server version v1.28.13`。

部署前建议直接校验 ConfigMap 里那份 `config.yaml`：平台清单在 `--mode server` 下应零告警
（需先注入 DSN 环境变量，否则报 `platform.store.dsn must not be empty`），巡检 ConfigMap 在 `--mode cli`
下应零告警。这两条已由 `go test ./tests/arch` 常驻锁定。

### 3.5 平台静态配置 `platform:` 详解

生产口径是「一份 ConfigMap（静态）+ 一份 Secret（敏感）+ DB settings（动态）」就能完整描述一个实例：

```yaml
platform:
  server:
    addr: ":8080"            # 监听地址（编排层 --addr 可覆盖）
    static_enabled: true     # 形态 A 内嵌 SPA；形态 B 置 false
    tls:
      enabled: false
      cert_file: ""          # 需要 TLS 时挂证书卷并把 cert_file/key_file 配成一对
      key_file: ""
  store:
    driver: mysql            # mysql（四期主存储） | sqlite（本地/单机兜底）
    sqlite_path: "/data/k8s-ai.db"   # 仅 driver=sqlite 使用，容器内必须落 PVC
    dsn: ""                  # 只经 K8S_AI_PLATFORM_STORE_DSN / Secret 注入；YAML 非空会告警
  auth:
    admin_username: admin    # 空库首启时创建的内置管理员用户名
    token_ttl: 24h
    session_store: memory    # 本期固定内存态；扩副本前需先支持持久化会话
```

七条边界：

1. **静态/动态拆离**：`config.yaml` 只承载静态/启动键；七组动态键不在 YAML 出现，server 启动只读静态段，
   Chat/Agent/LLM 运行时统一从 Store 读 DB。
2. **敏感值不落 YAML 明文**：`K8S_AI_ADMIN_PASSWORD`、`K8S_AI_ENC_KEY`、`K8S_AI_LLM_API_KEY`、
   `K8S_AI_PLATFORM_STORE_DSN` 全走环境变量 / Secret；模型 api_key、MCP env、kubeconfig 等动态敏感值
   用 `K8S_AI_ENC_KEY` 加密后落 DB。
3. **`static_enabled` 是两种形态的唯一开关**：`true` 时同端口内嵌托管 SPA，`false` 时只保留 API 与探针。
   该键必须可被环境变量覆盖，否则形态 B 会静默跑成形态 A（由 `internal/config` 测试锁定）。
4. **优先级（静态段）**：CLI > 环境变量 > YAML > 默认；`server --addr/--db` 是覆盖手段，不是唯一入口。
5. **优先级（动态键）**：见 §3.3 两档语义。
6. **落盘目录是静态键**：`report.directory` / `agent.session_dir` / `agent.audit_dir` 属于静态配置，
   镜像根文件系统只读，必须显式指向可写卷，架构测试会断言它们落在挂载点之下。
7. **模板收敛 + 显式迁移**：`config init` 不再输出全量引擎键；导入 settings 后以 DB 为权威，
   不随启动自动导入。

### 3.6 两个迁移入口的分工

| 命令 | 用途 | 备注 |
| --- | --- | --- |
| `k8s-ai db migrate --config <path>` | 平台 schema 幂等升级 | 仅 schema，可重复执行；适合做成 K8s Job（`deploy/base/db-migrate-job.yaml`）或 initContainer；`server` 启动内保留同一迁移的幂等兜底，但不替代 Job |
| `k8s-ai migrate --db <sqlite>` | 三期本地数据一次性导入 | 把三期 CLI 的会话 / 审计 / 报告导入平台库，只在从三期升级时用一次 |

```bash
k8s-ai db migrate --config /etc/k8s-ai/config.yaml
k8s-ai migrate --db ~/.k8s-ai/k8s-ai.db --sessions-dir ~/.k8s-ai/sessions --audit-dir ~/.k8s-ai/audit
```

两者不可混用。产品**不执行** `CREATE DATABASE`：库、账号与权限由 DBA 预建，
`server` 与 `db migrate` 只在已授权的库内建表与改表。

```sql
-- 由 DBA 执行；库名与账号按现场规范替换，本手册不写具体环境值
CREATE DATABASE k8s_ai DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'k8s_ai'@'%' IDENTIFIED BY '<由密码管理系统生成>';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, DROP, REFERENCES,
      CREATE TEMPORARY TABLES, LOCK TABLES ON k8s_ai.* TO 'k8s_ai'@'%';
```

库默认字符集建议 utf8mb4；即使库默认是 utf8mb3，产品建表 DDL 也会显式带
`DEFAULT CHARSET=utf8mb4`（`internal/store/dialect.go`），不依赖库默认。平台账号不需要
`SUPER` / `FILE` 等全局权限。

## 4. 生产部署（Kubernetes）

### 4.1 两种部署形态

四期是「前后端工程分离 + 单二进制一体化交付」，两种形态共享同一套业务代码与 `/api/v1` 契约：

| 项 | 形态 A 前后端一体化（默认） | 形态 B 前后端分离（可选） |
| --- | --- | --- |
| 前端交付 | `web/dist` 经 `go:embed` 内嵌进后端镜像 | `web/dist` 打进独立 `k8s-ai-web`（Nginx）镜像 |
| 后端职责 | 同端口提供 `/api/v1`（含 Chat SSE）与 SPA | 关闭静态路由，只提供 `/api/v1` 与 `/healthz`/`/readyz`/`/version` |
| 需要构建的镜像 | 1 个 | 2 个（后端镜像与形态 A 同一个） |
| 入口 | 单域名单 path `/` | 同域名按路径分流：`/api/v1/*` → 后端，其余 → 前端 |
| 副本 | `replicas: 1` + `Recreate` | 前后端各 1 副本；扩副本仍需先满足 ADR-030 前置 |
| 适用 | 单机、POC、测试、企业常规、离线交付、快速升级 | 要求前后端独立发布/回滚、企业统一静态托管或 CDN |
| 清单目录 | `deploy/base/` + `deploy/allinone/` | `deploy/base/` + `deploy/separated/` |

选型建议：没有明确的「前端要单独发版」诉求就选形态 A，运维面小一个数量级。两种形态可以在不停库的前提下
互相切换（同名 Deployment 就地 apply 另一形态那份 `deployment.yaml`），见 §4.5 末尾。

### 4.2 `deploy/` 目录与清单总览

**两种形态的 YAML 分目录存放**，`base/` 是共用前置，`allinone/` 与 `separated/` 互斥：

```
deploy/
  base/          两形态共用：namespace / serviceaccount / clusterrole / clusterrolebinding
                 configmap / secret.example / db-migrate-job / service / pvc
  allinone/      形态 A：deployment.yaml（内嵌 SPA）+ ingress.yaml（单 path /）
  separated/     形态 B：deployment.yaml（纯 API）+ web-deployment.yaml + web-service.yaml
                 + ingress.yaml（按路径分流）+ web.Dockerfile + nginx.conf
  scan/          可选：一期每日巡检 CronJob（独立 ConfigMap，见 §5）
  example/       参考示例与 kubectl patch 补丁（含 networkpolicy.yaml 出站限制样例），
                 不是清单，不能 apply
  rbac-write.example.yaml   可选：开放写权限的 ClusterRole（跨形态）
```

三条硬规则：

1. **只 apply 一个形态目录**。`allinone/deployment.yaml` 与 `separated/deployment.yaml` 是同名
   Deployment `k8s-ai-server`，两个都 apply 会互相覆盖。
2. **不要 `kubectl apply -R -f deploy/`**。`example/` 下是 strategic patch，刻意不写 `apiVersion`/`kind`，
   整目录递归会在它这里报校验错误。按下面小节逐文件 apply。
3. **两份后端 Deployment 除 `K8S_AI_PLATFORM_SERVER_STATIC_ENABLED` 一条 env 之外必须逐字段一致**，
   由 `tests/arch/deploy_manifest_test.go` 挡住漂移。

### 4.3 部署前置

1. 镜像已推到现场仓库：后端 `k8s-ai:<TAG>`（§2.2），形态 B 另需 `k8s-ai-web:<TAG>`（§2.3）。
2. 数据库已建好（§3.6），拿到 DSN；DSN **必须带 `parseTime=true`**。
3. 生成凭据加密密钥：`openssl rand -hex 32`（64 位 hex，或任意 base64 编码的 32 字节）。
   丢失即已加密落库的凭据全部不可恢复，轮换须知见 §4.10。
4. 替换占位值：

| 位置 | 占位值 |
| --- | --- |
| `base/secret.example.yaml`、`example/secret-mysql.example.yaml` | `REPLACE_ME` |
| `allinone/ingress.yaml`、`separated/ingress.yaml` | `k8s-ai.example.com`、`ingressClassName: nginx` |
| `base/pvc.yaml` | `REPLACE_WITH_STORAGE_CLASS`（留占位 PVC 会一直 Pending） |
| `scan/configmap.yaml` | `REPLACE_WITH_LLM_HOST`、`REPLACE_WITH_MODEL_NAME` |
| 两份 `deployment.yaml`、`base/db-migrate-job.yaml`、`separated/web-deployment.yaml` | `image:` 换成现场仓库地址与 TAG |

Secret 有四种，`store` 与 `enc` 必填，`admin` 只在空库首启需要、`llm` 可选：

| Secret | key | 用途 |
| --- | --- | --- |
| `k8s-ai-store` | `dsn` | MySQL 连接串（含口令） |
| `k8s-ai-enc` | `key` | 动态敏感值的落库加密密钥 |
| `k8s-ai-admin` | `password` | 空库首启的 admin 引导口令 |
| `k8s-ai-llm` | `api_key` | 模型网关密钥 |

### 4.4 形态 A：前后端一体化（默认）

```bash
# 1) 共用前置：命名空间 + 身份 + 只读 RBAC + 平台静态配置
kubectl apply -f deploy/base/namespace.yaml
kubectl apply -f deploy/base/serviceaccount.yaml
kubectl apply -f deploy/base/clusterrole.yaml
kubectl apply -f deploy/base/clusterrolebinding.yaml
kubectl apply -f deploy/base/configmap.yaml

# 2) Secrets（复制模板填值，不要直接 apply 模板）
cp deploy/base/secret.example.yaml ./secrets.yaml   # 替换全部 REPLACE_ME
kubectl apply -f ./secrets.yaml

# 3) 报告与导出 PVC（默认建议创建；确认不需要留档时才跳过）
#    storageClassName 留注释 = 用集群默认存储类；要指定就改成 kubectl get sc 里的名字
kubectl apply -f deploy/base/pvc.yaml

# 4) 结构升级：Job spec 不可变，重跑前先删旧 Job
kubectl -n k8s-ai delete job k8s-ai-db-migrate --ignore-not-found
kubectl -n k8s-ai apply -f deploy/base/db-migrate-job.yaml
kubectl -n k8s-ai wait --for=condition=complete job/k8s-ai-db-migrate --timeout=300s

# 5) 后端（内嵌 SPA）+ Service
kubectl -n k8s-ai apply -f deploy/allinone/deployment.yaml
kubectl -n k8s-ai apply -f deploy/base/service.yaml
kubectl -n k8s-ai rollout status deploy/k8s-ai-server --timeout=180s

# 6) 对外入口二选一（详见 §4.6）：
#    a. NodePort（默认推荐，不需要域名）：把 §4.3 建好的 ClusterIP 改成 NodePort
kubectl -n k8s-ai patch svc k8s-ai-server -p "{\"spec\":{\"type\":\"NodePort\"}}"
kubectl -n k8s-ai get svc k8s-ai-server -o "jsonpath={.spec.ports[0].nodePort}"
#    b. Ingress（有可解析域名时）：先替换 host 与 ingressClassName
kubectl apply -f deploy/allinone/ingress.yaml
```

迁移 Job 必须 `Succeeded` 之后再放行 Deployment：`/readyz` 会把「schema 迁移完成」作为就绪条件之一，
跳过 Job 的话 Pod 会一直 not ready（这不是故障，是在保护你不去连一个 schema 不全的库）。

### 4.5 形态 B：前后端分离

`base/` 前置、Secrets、迁移 Job 与形态 A **完全相同**，只是工作负载换成 `separated/`：

```bash
# （§4.3 前置 + §4.4 第 1~4 步已完成）
kubectl -n k8s-ai apply -f deploy/separated/deployment.yaml   # 后端纯 API（已关内嵌 SPA）
kubectl -n k8s-ai apply -f deploy/base/service.yaml
kubectl -n k8s-ai apply -f deploy/separated/web-deployment.yaml
kubectl -n k8s-ai apply -f deploy/separated/web-service.yaml
kubectl -n k8s-ai rollout status deploy/k8s-ai-server --timeout=180s
kubectl -n k8s-ai rollout status deploy/k8s-ai-web  --timeout=180s

# 对外入口：替代 allinone/ingress.yaml，不要两个都留
kubectl apply -f deploy/separated/ingress.yaml
```

形态 B 的前端镜像构建见 §2.3。前端只用相对路径 `/api/v1`，所以**必须同域按路径分流**；
`separated/nginx.conf` 里另留了一段 `/api/v1/` 反代兜底，只在你不走 Ingress、直接暴露 Nginx
（例如前端挂到独立子域）时才用得上，同域分流场景那段不参与匹配。

两种形态互切（同一数据库，无需停库）：

```bash
kubectl -n k8s-ai apply -f deploy/separated/deployment.yaml   # A → B（同名 Deployment 就地改）
kubectl -n k8s-ai apply -f deploy/allinone/deployment.yaml    # B → A
```

切到 B 之后再补 web 工作负载与分流 Ingress；切回 A 之后把 `k8s-ai-web` 与 `separated/ingress.yaml` 删掉。

### 4.6 对外暴露与 SSE 流式

**入口默认 NodePort，Ingress 是可选件**。理由很实际：现场常常没有可用域名，Ingress 用自定义域名的话
要逐台改客户端 hosts，交付体验很差；NodePort 用 `http://<节点IP>:<端口>` 直连就能用，且与 SPA 的同源
相对路径、`Authorization` 头天然兼容，不涉及 cookie 与跨域（这也是为什么切暴露方式**不需要改任何代码**）。

| 方式 | 何时用 | 端口 | 说明 |
| --- | --- | --- | --- |
| NodePort（默认） | 无域名、内网直连、交付验收期 | `NODE_PORT` 指定；留空由集群随机分配 | `install.sh` 在 apply 后回读实际端口，并列出所有节点 IP 的访问 URL |
| Ingress（可选） | 有可解析域名或 VIP、需要标准 80/443 | 80/443 | 给了 `INGRESS_HOST` 才启用，可与 NodePort 并存 |
| port-forward（兜底） | 临时排障、集群暂无外部入口 | 本地自选 | `kubectl -n k8s-ai port-forward svc/k8s-ai-server 8080:8080` |

正式清单的 Service 固定 `ClusterIP`（保持零环境专有值、可独立 `kubectl apply`），暴露层由 `install.sh`
按 `EXPOSE=nodeport|ingress` 渲染，默认 `nodeport`；手工部署时按 §4.4 步骤 6 自行 patch Service。

下面是 Ingress 侧的 SSE 流式要点（用 NodePort 直连时没有中间层，天然不缓冲）：

Chat 是长连接流式接口，**中间层一旦缓冲，前端就会「憋到最后一次性吐出来」**。服务端已在 SSE 响应里带
`X-Accel-Buffering: no`（有测试锁定），Nginx 收到即关闭该响应缓冲；Ingress 侧的 annotation 是显式兜底。

形态 A：单 Ingress、单 path `/` → `k8s-ai-server:8080`，SSE annotation 直接挂在它上面。

形态 B：刻意拆成两个 Ingress，因为 SSE 要关缓冲放大超时、静态资源希望保留缓冲，塞在同一个 Ingress 上会
互相将就：

| Ingress | path | 后端 | 关键 annotation |
| --- | --- | --- | --- |
| `k8s-ai-api` | `/api/v1` | `k8s-ai-server:8080` | `proxy-buffering: "off"`、`proxy-request-buffering: "off"`、`proxy-read/send-timeout: "3600"`、`proxy-body-size: "16m"` |
| `k8s-ai-web` | `/` | `k8s-ai-web:80` | 无（静态资源保留缓冲） |

非 nginx 控制器请把 annotation 换成各自等价配置。要点：关响应缓冲、放大读超时、保留
`Host` / `X-Forwarded-*` 头（审计与登录态判断要用）、`proxy-body-size` 覆盖报告导出与技能包上传体量。

SPA fallback 只允许覆盖前端路由：后端侧未知 `/api/v1/*` 一律返回 JSON 404，绝不能被 fallback 吞成
`index.html`，否则前端拿到一坨 HTML 无法定位错误。

### 4.7 探针、就绪与首启语义

```yaml
args: ["server", "--config", "/etc/k8s-ai/config.yaml", "--addr", ":8080"]
env:
  - name: K8S_AI_PLATFORM_STORE_DSN   # MySQL 主存储，含口令，只走 Secret（密钥态）
    valueFrom: { secretKeyRef: { name: k8s-ai-store, key: dsn } }
  - name: K8S_AI_ENC_KEY              # 动态敏感值落库加密
    valueFrom: { secretKeyRef: { name: k8s-ai-enc, key: key } }
  - name: K8S_AI_ADMIN_PASSWORD       # optional，仅空库首启用
    valueFrom: { secretKeyRef: { name: k8s-ai-admin, key: password, optional: true } }
  - name: K8S_AI_LLM_API_KEY          # optional（密钥态）
    valueFrom: { secretKeyRef: { name: k8s-ai-llm, key: api_key, optional: true } }
```

- **`/healthz`** 是进程级 liveness，不触碰外部依赖；**`/readyz`** = Store 连通性探测 + schema 迁移完成
  标记，任一不满足返回非 200。两者不是同义空壳，别改成一样。
- **首启**：`K8S_AI_ADMIN_PASSWORD` **只在空库首启**时必需；已完成初始化的库重启不再要求该变量，
  引导完成后可以把 `k8s-ai-admin` Secret 与对应 env 摘掉。
- 副本固定 `replicas: 1` + `strategy: Recreate`：登录会话本期是内存态，滚动更新会短暂双实例，
  所以用 Recreate；扩副本的前置条件见 ADR-030。
- 安全上下文：容器与 Pod 都是 `runAsNonRoot` + uid/gid 65532、`readOnlyRootFilesystem: true`、
  drop ALL capabilities、seccomp `RuntimeDefault`、`fsGroup: 65532`；
  `automountServiceAccountToken: true`（平台要用自身身份访问本集群 API，形态 B 的前端容器为 false）。

### 4.8 数据与落盘

| 项 | 口径 |
| --- | --- |
| 主存储 | MySQL，DSN 经 Secret 注入；库与账号由 DBA 预建（§3.6） |
| SQLite 兜底 | `driver: sqlite` 时数据目录**必须**挂 PVC（`platform.store.sqlite_path` 指向 `/data/...`），禁止落在容器可写层 |
| 报告 / 会话 / 审计 | `report.directory: /reports`、`agent.session_dir: /data/sessions`、`agent.audit_dir: /data/audit`，清单里默认是 emptyDir；MySQL 主存储下 PVC 可选、仅承载报告与导出 |
| 根文件系统 | 只读；`/tmp` 用 emptyDir |
| MySQL 与 CronJob 共用报告 PVC | 需要 RWX 存储类，否则给两者挂不同卷 |
| 日志 | 标准输出，由集群日志采集接管 |

### 4.9 部署期环境变量

默认清单**只注入密钥态**：`K8S_AI_PLATFORM_STORE_DSN` 与 `K8S_AI_LLM_API_KEY`（后两个可选）。
非敏感的业务配置一律在配置中心页面填，ConfigMap 与 Deployment 里都不写动态键。

确实需要用部署变量给首启播种（模型地址 / 模型名 / 默认命名空间）时，用示例补丁追加，
不要改正式清单：

```bash
kubectl -n k8s-ai patch deploy k8s-ai-server --type=strategic \
  --patch-file deploy/example/env-overrides.example.yaml
# 撤销某个变量
kubectl -n k8s-ai set env deploy/k8s-ai-server K8S_AI_LLM_ENDPOINT-
```

两档语义见 §3.3。`KUBECONFIG` 在集群内不要设：平台用自身 ServiceAccount 的 in-cluster 身份访问本集群
API。`KUBECTL_PATH` 只在本机 CLI 直用（非容器）时才需要——默认交付镜像已在构建期把 `kubectl` 装到
`/usr/local/bin` 并通过 sha256 校验（P6.3 / D-33），容器内无需任何配置即可用；换 `Dockerfile.distroless`
变体时镜像内没有解释器与 `kubectl`，Chat 会拿到可指导文案而不是执行失败。

### 4.10 一键安装与密钥轮换

> **本节参数表是安装口径的唯一权威源**：`deploy/README.md`、PRD §27、ADR-045 只引用不复制，改参数只改这里。
> **脚本已落地**（开发计划 v1.58，路径 `deploy/install.sh`）；§4.4 / §4.5 的手工 `kubectl apply` 路径继续有效，两者语义与下表完全一致。
> Windows 上取到脚本后先确认它是 LF：仓库已用 `.gitattributes` 把 `*.sh` 钉成 `eol=lf`，正常克隆即可，别手工转成 CRLF（Linux 执行会报 bad interpreter）。

```bash
# 最小可用：一条命令装完（默认 NodePort 暴露、PVC 走集群默认存储类、默认只读 RBAC）
IMAGE=<registry>/<repo>/k8s-ai TAG=4.0.0 \
  MYSQL_DSN="<user>:<pass>@tcp(<host>:3306)/k8s_ai" ./deploy/install.sh

# 反复重跑：参数写进 install.env（KEY=VALUE 一行一个），别在命令行里重复贴
./deploy/install.sh --env-file install.env

# 预演与排障
./deploy/install.sh --dry-run    # 只渲染清单到临时目录并做占位符残留断言，不碰集群
./deploy/install.sh --diff       # 渲染后走 kubectl diff，先看再装
./deploy/install.sh -v           # 展开各阶段的原始 kubectl 输出
./deploy/install.sh --yes        # 全无人值守（写权限等危险动作仍要求显式参数）
./deploy/install.sh --rotate     # 仅轮换 ENC_KEY；非交互模式直接拒绝
./deploy/install.sh --no-build   # 跳过构建只发布（镜像已在仓库）
./deploy/install.sh --load-tar=./k8s-ai-4.0.0.tar   # 离线导入镜像再发布，跳过构建

# 参数三种写法等价，优先级 CLI > 环境变量 > env 文件 > 内置默认；CLI 写法必须带等号
./deploy/install.sh --IMAGE=registry.local/k8s-ai --TAG=4.0.0 --dry-run
IMAGE=registry.local/k8s-ai TAG=4.0.0 ./deploy/install.sh
```

**配置来源三层**：`CLI flag` > `环境变量` > `install.env` > 内置默认。交互只做两件事——必填参数缺失时补问、
危险动作二次确认；`--yes` 下不提问。**必填项缺失一律拒绝并说明缺哪个，绝不猜默认值**。

env 文件取值规则：`KEY=VALUE` 一行一个，`#` 开头为注释；值允许带**成对引号**（`MYSQL_DSN="user:pass@tcp(db:3306)/k8s_ai"`），
脚本只剥掉最外层成对引号，**不做变量展开、不做二次求值**，含 `~` 的键（如 `ENC_KEY_BACKUP_DIR`）请写绝对路径。
**未知键名直接报错**而非静默忽略，参数改名会被门禁拦下。

**两段一体**（`install.sh` 同时管镜像构建与服务发布）：

| 段 | 触发条件 | 行为 |
| --- | --- | --- |
| BUILD | `BUILD=true` 且探测到 docker/podman | `docker build`（自动带 `GOPROXY` 与 P6.3 的 kubectl 离线投递）→ `push`；`--load-tar` 改走 `docker load` 离线导入 |
| BUILD 降级 | 无容器运行时或 `BUILD=false` | 跳过构建只做发布，要求 `IMAGE:TAG` 已就绪 |
| DEPLOY | 总是执行 | 下方九阶段 |

**DEPLOY 段九阶段**（每阶段带序号与耗时，失败即停在当阶段并给出下一条命令）：

| # | 阶段 | 关键动作与卡点 |
| --- | --- | --- |
| 1 | 前置检查 | `kubectl` 可用、集群可达、`auth can-i` 逐项自检、StorageClass 可用性、IngressClass（启用 Ingress 时）、nodePort 占用、必需 API 组 |
| 2 | 命名空间 + RBAC + ConfigMap | `base/namespace.yaml`、`serviceaccount/clusterrole/clusterrolebinding`、`configmap.yaml` |
| 3 | Secret 幂等 | 走 `create secret --dry-run=client -o yaml \| kubectl apply -f -`；DSN 与口令经 stdin 注入，不进 `ps` 与 shell history |
| 4 | PVC | `STORAGE_CLASS` 为空则省略字段走集群默认存储类；apply 后 `wait --for=condition=bound`，超时附 `describe pvc` 与 `get sc` |
| 5 | 迁移 Job | 先删同名旧 Job（Job spec 不可变）→ apply → `wait --for=condition=complete`；失败自动附 `logs --tail=50` |
| 6 | 工作负载 | 形态 A `allinone/`、形态 B `separated/`，`rollout status`；超时区分 ImagePullBackOff（凭据/网络）与探针不过（先查 `/readyz` 的迁移与 Store 条件） |
| 7 | 对外暴露 | `EXPOSE=nodeport`（默认）/ `ingress`；`NODE_PORT` 为空则随机分配，回读实际端口并列出全部节点 IP 的 URL |
| 8 | 写权限 RBAC | 仅 `ENABLE_WRITE=true` 时 apply `rbac-write.example.yaml`，并要求二次确认 |
| 9 | 验收摘要 | 访问 URL、admin 口令（本次随机生成时只打印一次）、ENC_KEY 本地备份路径、下一步建议命令 |

**参数表**（★ = 必填，缺失即拒绝）。本表、`deploy/install.sh --help` 与 `deploy/install.env.example` 三处参数集合由
`tests/arch/install_script_test.go` 三向锁定，任何一处不同步 CI 直接失败：

**渲染与幂等红线**：清单只渲染进 `mktemp -d`（`trap` 清理），只替换已知锚点串（namespace、image、
`storageClassName`、Ingress host、Service 类型与端口），产物断言**零 `REPLACE_` 残留、零示例域名残留**；
**仓库里的 YAML 不被就地改写**，正式清单必须继续能独立 `kubectl apply` 跑通。重复执行不重置密钥、
不轮换口令、不改已存在的 Secret 数据。

密钥与口令语义（必须照此实现，也是运维要知道的行为）：

- **`K8S_AI_ENC_KEY` 复用优先**：Secret 已存在就复用，绝不覆盖；缺失才生成，并在本地留一份权限 600 的备份。
- **该密钥一旦丢失，已加密落库的模型 api_key、MCP env、kubeconfig 全部不可恢复**，离线备份不是可选项。
- **轮换只走显式 `--rotate`**，非交互模式下直接拒绝。**当前版本没有自动重加密能力**：脚本只做「备份旧 key →
  写入新 key → 滚动重启」并在验收摘要里打印警告——已用旧 key 加密落库的模型 api_key、MCP env、集群凭据
  必须在配置中心逐条重录，否则运行期解密失败。重加密工具落地前，生产环境优先复用密钥而不是轮换。
- **`ADMIN_PASSWORD`** 缺省随机生成，只在本次安装输出一次，不落文件、不重复打印；已存在的口令不被重跑覆盖。
- **`ENABLE_WRITE=true`** 显式 apply 写权限 RBAC 并二次确认，默认保持只读。
- **幂等**：重复执行不重置密钥、不轮换口令、不改已存在的 Secret 数据；建议先 `--diff` 预演。
- **DSN 与口令不进命令行参数**：五个 Secret 统一 `create secret generic --dry-run=client -o yaml | kubectl apply -f -`，
  敏感值经 `--from-file=<key>=/dev/stdin` 注入，既不出现在 `ps` 与 shell history 里，也不落进渲染后的清单文件。

**失败怎么读**：全程 tee 到 `install-<ts>.log`；失败信息固定三段——阶段名、根因摘要、下一条可复制命令；
原地重跑不需要先清理密钥或口令。

**LLM 仅作辅助安装**（ADR-045）：脚本本体零 LLM、零外呼。`k8s-ai install doctor`（装后只读诊断，复用平台
agent 与只读工具，日志摘要先脱敏，只给结论不自动修复）与 `k8s-ai install plan`（读集群实况产出
`install.env` 草稿与理由）是可选子命令（开发计划 P6.14/P6.15），**不进安装关键路径**；**没有模型时，
用户手改参数执行脚本也必须装通**。

### 4.11 升级与回滚

```bash
# 形态 A：整体升级（先跑迁移 Job，再换镜像）
kubectl -n k8s-ai delete job k8s-ai-db-migrate --ignore-not-found
kubectl -n k8s-ai apply -f deploy/base/db-migrate-job.yaml
kubectl -n k8s-ai wait --for=condition=complete job/k8s-ai-db-migrate --timeout=300s
kubectl -n k8s-ai set image deploy/k8s-ai-server k8s-ai=<registry>/k8s-ai:4.0.1
kubectl -n k8s-ai rollout status  deploy/k8s-ai-server --timeout=180s
kubectl -n k8s-ai rollout undo    deploy/k8s-ai-server          # 回滚

# 形态 B：前后端各自独立升级 / 回滚（容器名分别是 k8s-ai 与 web）
kubectl -n k8s-ai set image deploy/k8s-ai-web web=<registry>/k8s-ai-web:4.0.1
kubectl -n k8s-ai set image deploy/k8s-ai-server k8s-ai=<registry>/k8s-ai:4.0.1
kubectl -n k8s-ai rollout undo deploy/k8s-ai-web
```

前后端独立发布时以 `/api/v1` 契约测试守住兼容面；当前不建设多版本兼容体系，只要求版本标识与必要契约测试。
数据库迁移经 Job 或 initContainer 执行，**迁移失败阻塞启动**；`server` 启动内的幂等迁移只是兜底。
回滚镜像前要注意 schema 是否向前兼容：本期迁移只做增量加表加列，不做破坏性删除，因此旧镜像配新 schema
通常可运行，但仍应先备份再动版本。

### 4.12 换命名空间

清单里 namespaced 对象都显式写了 `metadata.namespace: k8s-ai`，`kubectl -n` **不会**覆盖它。换命名空间
要把 `namespace: k8s-ai` 整串替换（`ClusterRoleBinding` 的 `subjects[].namespace` 同形式，一起改）：

```bash
# Linux / macOS
find deploy -name '*.yaml' -exec sed -i 's/^namespace: k8s-ai$/namespace: my-ns/' {} +
```

```powershell
# Windows PowerShell
Get-ChildItem deploy -Recurse -Filter *.yaml | ForEach-Object {
  $p = $_.FullName
  [IO.File]::WriteAllText($p, ([IO.File]::ReadAllText($p) -replace '(?m)^namespace: k8s-ai$', 'namespace: my-ns'))
}
```

### 4.14 常见故障

| 现象 | 原因与处理 |
| --- | --- |
| `/readyz` 503、Pod 一直 not ready | 迁移未到位或 Store 不通：先跑迁移 Job 并确认 `Succeeded`，再核对 DSN（`parseTime=true`、库已建、网络可达） |
| 启动即退出并提示 DSN | 没建 `k8s-ai-store` Secret，或 `driver: mysql` 却没注入 DSN |
| 首启退出并提示 `bootstrap admin ... must not be empty` | 空库首启缺 `K8S_AI_ADMIN_PASSWORD`；带一次完成引导，之后可摘掉 |
| 集群端点列表 501 / 敏感配置保存失败 | `K8S_AI_ENC_KEY` 未注入或长度不对（需 32 字节：64 位 hex 或 base64） |
| 页面 404 但 API 正常 | 形态 A 用了未内嵌 dist 的镜像（此时是 503 + 明确提示）；或形态 B 忘了用 `separated/deployment.yaml` / 没部署 web |
| 形态 B 页面能开但接口 404 | 只 apply 了 `separated/ingress.yaml` 的 web 那半，或 `/api/v1` 分流被覆盖 |
| SSE 攒到最后一次性输出 | Ingress 缓冲没关：核对 `proxy-buffering: "off"` 与读超时，见 §4.6 |
| Chat 报「模型未配置」 | 页面没配、也没给种子态部署变量：内置默认只在 CLI 兜底，容器内两处都空会显式报错 |
| 配置中心保存了但行为没变 | 该键被密钥态 Secret 覆盖（页面会标注来源）；见 §3.3 |
| PVC 一直 Pending | `storageClassName` 还是占位值，或存储类不支持 RWO 供给 |
| 事件里有 restricted warning | 预期内的 warn（未 enforce）；确认无告警后可自行把 `pod-security.kubernetes.io/enforce` 升上来 |

### 4.16 部署侧安全基线

- 默认 ClusterRole 只授权 `get/list/watch` + `pods/log get`；secrets 仅元数据/键级读取（内容值禁止）；
  **不含** `pods/exec`、`pods/portforward`、`pods/attach` 与写能力。清单由架构测试解析断言，误加写权限
  会让 `go test ./tests/arch/` 失败。
- 写权限是显式动作：`kubectl apply -f deploy/rbac-write.example.yaml`，并在配置中心按命名空间授权。
- 默认交付镜像内置 shell 与 kubectl（见 §4.17），写执行仍只经 Code Guard + `internal/executor` 唯一出口；
  含 shell 语法的命令必须真人审批，`--skip-permissions` 与 `require_approval=false` 都不免除。
- 容器加固为必配：非 root 65532、`allowPrivilegeEscalation: false`、drop ALL capabilities、
  `seccompProfile: RuntimeDefault`、只读根文件系统 + 可写 emptyDir；开放环境建议启用 NetworkPolicy。
- 敏感值（admin 首启口令、LLM api_key、DSN 口令）只经 Secret / 环境变量；api_key 永不写入
  ConfigMap、日志或报告；日志 / Events / ConfigMap / 注解一律视为不可信数据，先脱敏再分析。
- 交付物（清单、镜像、安装脚本）中禁止硬编码任何具体环境信息。

### 4.17 容器内执行通道与镜像分档

默认交付镜像自带 `/bin/bash`、coreutils、`grep/sed/awk/sort/uniq`、`jq`、`curl`、DNS/ICMP 诊断工具与
`kubectl`，容器内 Chat 的读命令、shell 管道与 kubectl 写通道与本地 CLI 等价，平台已有能力不因部署进
Kubernetes 而丢失（ADR-044 v1.1、`docs/02-架构与设计/16-方案-容器执行通道与镜像基座-四期.md`）。运行阶段
基座是 `debian:bookworm-slim`，运行用户仍是 uid/gid 65532，镜像体积约 20MB → 约 180MB。

静态开关 `platform.exec.shell_enabled`（`config.yaml` 的 `platform:` 段，启动级参数、不是页面动态键，
默认 `true`）：

- `true`：shell 通道可用；含管道、重定向、命令替换等 shell 语法的命令一律走人工审批，`--skip-permissions`
  与 `require_approval=false` 都不能免除，也不进 grant 命中。
- `false`：在构造执行命令之前返回可指导文案、不 fork 进程，配 `Dockerfile.distroless` 产物，给禁止容器内
  shell 或入口直接暴露公网的现场。

启动时探测 `bash` 与 `kubectl`：开启态缺失打 WARN、关闭态打 INFO，都不阻塞启动（读链路不依赖它们）。
Secret 内容值与 `--raw`、交互式动词、`deny_ops` 红线与集群 RBAC 均不因工具齐备而放宽——默认 ClusterRole
不含 `pods/exec`，给了写权限就是给了真实破坏力（§4.16）。

Deployment 加固项（`deploy/allinone/deployment.yaml` 与 `deploy/separated/deployment.yaml` 逐字段一致）：
`runAsNonRoot: true` + `runAsUser: 65532`、`allowPrivilegeEscalation: false`、`capabilities.drop: ["ALL"]`、
`seccompProfile.type: RuntimeDefault`、`readOnlyRootFilesystem: true` 并挂 `/tmp` 与 `/home/k8sai`（kubectl
发现缓存写入处）两个 emptyDir、`resources.requests/limits`。出站收口样例见 `deploy/example/networkpolicy.yaml`。

真机冒烟六条（人工构建镜像后执行）：`kubectl get deploy -A` argv 成功；`kubectl get pods -A -o json | jq -r ...`
经批准成功；`kubectl logs ... | grep ... | sort | uniq -c` 经批准成功；`shell_enabled=false` 时返回可指导文案；
一次写操作经审批后仍成功（证明写通道未被误伤）；只读根文件系统下 kubectl 发现缓存写入不报错。默认镜像的 CVE
扫描报告随交付归档，HIGH/CRITICAL 逐条给处置结论。

## 5. 每日巡检 CronJob（一期通道，可选）

这条通道与平台 Chat 无关：CronJob 用独立 ConfigMap `k8s-ai-scan-config`（引擎键），不读平台的
`k8s-ai-config`，也不需要 Store DSN。只要定时巡检报告时可以只装这一套（`deploy/base/` 的
namespace / RBAC + `deploy/scan/`）。

```bash
# 前置：deploy/base/{namespace,serviceaccount,clusterrole,clusterrolebinding}.yaml
kubectl apply -f deploy/scan/configmap.yaml     # 先替换 REPLACE_WITH_LLM_HOST / REPLACE_WITH_MODEL_NAME
kubectl apply -f deploy/base/pvc.yaml           # 报告跨重启保留（cronjob 的报告卷指向 PVC k8s-ai-data）
kubectl apply -f deploy/scan/cronjob.yaml
```

`scan/configmap.yaml` 在 `config validate --mode cli` 下应零告警（同 §3.4）。不需要 LLM 就把
`llm.enabled` 置 false，只出规则结论。

```bash
kubectl get cronjob -n k8s-ai
# NAME           SCHEDULE      SUSPEND   ACTIVE
# k8s-ai-daily   0 8 * * *     False     0

# 手动触发一次立即巡检（只读）
kubectl create job --from=cronjob/k8s-ai-daily k8s-ai-manual -n k8s-ai
kubectl logs job/k8s-ai-manual -n k8s-ai -f
# 期望：Phase1 采集完成 → LLM 诊断进行中 → LLM 诊断完成 → 终端摘要
```

行为要点：调度 `0 8 * * *` + `timeZone: Asia/Shanghai`（需 1.27+）；`concurrencyPolicy: Forbid`；
`restartPolicy: OnFailure` + `backoffLimit: 2`；非 root 65532 + `fsGroup: 65532` + drop ALL；
报告写 PVC 的 `/reports`（`latest.md` / `latest.json` / 时间戳 .md）；LLM api_key 经 Secret 注入且
`optional: true`，未配置时自动降级为规则结论。

卸载：`kubectl delete -f deploy/scan/`。

### 5.1 历史对比（日报趋势）

每次扫描自动读取报告目录里上一份 `latest.json`，按 Finding 指纹对比输出**新增 / 持续 / 恢复**三类问题，
报告新增「历史对比」段，终端摘要显示计数。`latest.json` 的 `history` 字段是 Agent 会话记忆契约
（`scan_cluster` 工具自动携带，无需手动挂载）。

```bash
k8s-ai config init --cli && k8s-ai config validate --config ~/.k8s-ai/cli.yaml --mode cli
k8s-ai scan                                  # 全集群巡检，写 reports/latest.md + latest.json
k8s-ai chat "为什么 payment-api 一直重启？"    # 单发；不带参数进交互模式
```

### 6.2 本地起平台（SQLite 兜底）

```bash
./bin/k8s-ai config init                      # 需要把 platform.store.driver 改成 sqlite
K8S_AI_ADMIN_PASSWORD='你的强密码' \
  ./bin/k8s-ai server --addr 127.0.0.1:8080 --config ~/.k8s-ai/config.yaml
```

形态 A 的二进制已内嵌 `web/dist`（前提是先 `cd web && npm ci && npm run build` 再 `make build`），
浏览器直接开 `http://127.0.0.1:8080`。SQLite 路径由 `platform.store.sqlite_path` 或 `--db` 决定，
**单机跑也要放到持久目录**，别丢在临时目录。

### 6.3 前端开发服务器

```bash
cd web && npm run dev        # http://127.0.0.1:5173，/api/v1 代理到 8080
```

会话接口 `/api/v1/sessions*` 与平台 API 共用同一登录 Token；`user` / `operator` 只能查看和操作自己的
会话，admin 可查看并操作全部会话。

### 6.4 kubectl 兜底工具（仅本机）

- 通用 `kubectl` 工具需要本机安装 kubectl 并在 PATH（或配 `kubernetes.kubectl_path`）；
- 它继承 `kubernetes.kubeconfig`（以 `KUBECONFIG` 传给子进程），保证与 client-go 打同一个集群；
- 含 shell 语法的命令**一律走人工审批**，`--skip-permissions` 不覆盖它；
- 容器内没有 kubectl 与 shell，这条通道在生产镜像里不存在。

## 7. 使用指导

### 7.1 命令一览

| 命令 | 说明 |
| --- | --- |
| `k8s-ai scan` | 全集群巡检，默认写 `reports/latest.md` + `latest.json` |
| `k8s-ai scan -n <ns>` | 只巡检某命名空间，终端直出（不写文件） |
| `k8s-ai scan pod <name> -n <ns>` | 单 Pod 诊断（含关联 Deployment/Service/Node 证据） |
| `k8s-ai scan --report-mode daily` | 日报模式，追加时间戳文件 |
| `k8s-ai scan --report-mode none --format json` | 终端输出 JSON（脚本用） |
| `k8s-ai scan --fail-on HIGH` | 存在 HIGH 及以上时退出码 2（CI 用） |
| `k8s-ai chat [问题]` | 自然语言运维（交互 / 单发 / stdin / `--format json`） |
| `k8s-ai config init [--cli] [--force]` | 生成平台或 CLI 配置模板 |
| `k8s-ai config validate --mode server\|cli [--skip-connectivity]` | 校验配置与集群连通性 |
| `k8s-ai db migrate --config <path>` | 平台 schema 幂等升级（§3.6） |
| `k8s-ai migrate --db <sqlite>` | 三期本地数据一次性导入（§3.6） |
| `k8s-ai server [--addr] [--db] --config <path>` | 启动平台主进程（认证、Session、Chat SSE、审批、配置、审计） |
| `k8s-ai version` | 版本 |

### 7.2 参数详解

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--kubeconfig` | 配置或默认 | 指定 kubeconfig |
| `--context` | 当前 | 指定上下文 |
| `-n, --namespace` | 全集群 | 目标命名空间 |
| `--since <dur>` | 无 | 日志时间窗口（如 1h） |
| `--format` | markdown | 终端完整报告格式 markdown/json/yaml |
| `--report-mode` | none(目标)/latest(全集群) | none=仅终端 / latest=latest 文件 / daily=加时间戳 |
| `--verbose` | false | 终端输出完整报告（默认一屏摘要） |
| `--fail-on <sev>` | 无 | 达到严重级退出码 2 |
| `--config` | `~/.k8s-ai/config.yaml` | 配置文件路径 |

### 7.3 输出解读

```text
k8s-ai scan　Scope: cluster
集群健康度：65/100  ██████░░░░
CRITICAL 0 | HIGH 2 | MEDIUM 1 | LOW 0 | INFO 0

重点问题：
🟠 HIGH ns/deploy：副本数不匹配：0/1 ready
　现象：desiredReplicas=1；readyReplicas=0
　根因：...（LLM）或 初步判断（规则）+ 日志关键行
　建议：kubectl ...（风险 HIGH）
```

报告文件：`latest.md`（人读）、`latest.json`（机器读，含 findings 指纹 + diagnoses）。
退出码：0 成功；1 执行错误；2 `--fail-on` 达到阈值。

### 7.4 识别效果示例

| 场景 | 工具输出 |
| --- | --- |
| nginx 配置错误 | 日志关键行：`[emerg] host not found in "80x" of the "listen" directive` |
| OOM | 证据：OOMKilled / exitCode 137 / memory.limit |
| RocketMQ topic 缺失 | 日志关键行：`panic: StartConsumer fail ... route info not found` |
| Service 无后端 | 规则：readyEndpoints=0 + selector 匹配数；LLM 结合关联 Pod 崩溃证据定位 |

## 8. 故障排查（运行期）

| 现象 | 排查 |
| --- | --- |
| LLM 一直「诊断中」 | 思考型大模型单次 1.5-2 分钟属正常；确认 `llm.timeout` / `scan.timeout` 足够（10m）；或换快速模型、设 `llm.thinking.type: disabled` |
| 报告标注「LLM 分析不可用」 | LLM 网关不可达 / 超时 / 输出校验失败；scan 不会失败，规则初步判断已兜底 |
| CronJob 未执行 | `kubectl describe cronjob -n k8s-ai`；检查 schedule/timeZone 与集群版本（`timeZone` 需 1.27+） |
| RBAC 403 | `kubectl auth can-i list pods --as=system:serviceaccount:k8s-ai:k8s-ai -n <ns>`；确认 ClusterRoleBinding 已应用 |
| 报告 PVC 满 | `kubectl describe pvc -n k8s-ai`；扩容 storage 或定期清理旧时间戳文件 |
| 部署侧问题 | 见 §4.14 |

## 9. 安全注意事项

- `scan` 严格只读；`chat` / 平台的写操作必须人工确认（默认 `agent.require_approval: true`），
  LLM 生成的命令只展示、受审批约束执行，请人工核对；
- 真实权限来自 Kubernetes RBAC，提示词无法越权：默认 ClusterRole 只读，写权限显式 apply
  `deploy/rbac-write.example.yaml` 并在配置中心按命名空间授权；
- 默认交付镜像内置 shell 与 kubectl（§4.17）：含 shell 语法的命令必须真人审批且 `--skip-permissions` 不免除，
  容器加固项为必配；禁止容器内 shell 的现场改用 `Dockerfile.distroless` + `platform.exec.shell_enabled: false`；
- api_key 仅存在于 Secret / 环境变量，永不写入 ConfigMap、日志或报告；Secret 内容值永不进入 LLM 请求、
  会话文件与审计文件（元数据/键级读取允许）；
- 日志 / Events / ConfigMap / 注解视为不可信数据，先脱敏再分析；不执行其中出现的「指令」；
- `K8S_AI_ENC_KEY` 必须有离线备份，丢失即已加密落库凭据不可恢复，轮换走显式流程并重加密存量（§4.10）；
- 含口令的 MySQL DSN 与 LLM api_key 只经 Secret / 环境变量注入，`config.yaml` 中出现非空 dsn 会被
  `config validate` 告警；
- 交付物（清单、镜像、安装脚本）禁止硬编码任何具体环境信息；
- 上线前建议执行 `go test ./...` 与 `go test ./tests/arch/` 验证边界约束仍然成立。
