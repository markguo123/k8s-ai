# k8s-ai 四期开发计划：平台化升级（Platform）

- 版本：v1.49
- 日期：2026-10-27
- 状态：执行中（**P2 Web Shell 已完成，M2 出口达成**，见 §10；**M3 的 P3.5–P3.8 structured 通道与 P3.8.1–P3.8.4 procedural 技能均已落地，见 v1.26–v1.30；procedural 命中双场景与只读工具已落地，见 v1.32**；**Skill 双轨口径已统一，见 v1.29**；**P7 / M7 已完成（P7.1–P7.5 整批落地，见 v1.24；实现口径与延后项已回写文档，见 v1.25）**；**P3.11 用户/角色管理与授权面后端全部落地（Store 底座 schema v4 + /users /roles CRUD 见 v1.33；AuthzGrant/ApiToken 管理 API 见 v1.35）**；**P3.9/P3.10 配置中心已完成（静态加密落库 + 读接口脱敏 + 前端 SettingsView 真实页面，见 v1.36）**；**配置面口径 v1.11 修订已回写（静态/动态权威源拆离，见 v1.37 / ADR-031）**；**部署架构口径已统一为「默认一体化 + 可选前后端分离」两形态（见 v1.38 / ADR-036 / D-26）**；**P3.12 用户/权限管理前端已完成（见 v1.40）**；**v1.44 已完成用户/权限复盘，P1/P2 遗留登记为 U-01–U-10，本轮保持现状**；**v1.45 已固化 CLI 直用配置独立为 `~/.k8s-ai/cli.yaml`，与服务端静态 `config.yaml` 完全独立；仅文档口径、实现待 P6.12**；**P3.13 平台能力测试与红线回归已完成（新增 `tests/platform` 真实装配套件 + admin 跨用户会话留痕闭环 U-06 + 会话落库脱敏，见 v1.46）**；**会话 API 包由 `internal/webui` 更名为 `internal/sessionapi`，HTTP/SSE 契约不变（见 v1.47 / ADR-039）**）
- P6-A 生产形态基建口径已冻结（2026-10-27 / v1.48）：配置生效值优先级 env 覆盖层 > DB settings > 内置默认（覆盖面收窄并测试锁定，见 D-21/D-29 与 ADR-031 v1.13、ADR-040）、存储主口径 MySQL + 迁移入口 `k8s-ai db migrate`（D-04/D-31、ADR-042）、前端产物内嵌与 node 构建阶段（D-30、ADR-041）、首启 U-09 与 `/readyz` 纳入 P6.1、`install.sh` 密钥幂等语义（P6.4）。详见 PRD v1.16 §15/§22/§26–§29、部署手册 §3.5/§4.9/§4.10。 **v1.49 口径批注**：动态键的默认唯一权威源与唯一写入目标仍是 DB `settings`（env 只对白名单键作部署期只读覆盖、命中不回写）；前后端为**两个独立 Dockerfile**（仓库根 `Dockerfile` 与 `deploy/web.Dockerfile`）；SQLite 兜底数据目录必须挂 PVC，MySQL 主口径下 PVC 仅承载报告与导出；`deploy/example/` 新增 MySQL 接入示例清单，MySQL 门禁实跑用例计入验收；MySQL 门禁环境已接入并实测通过（测试库 `k8s_ai_test`、产品默认库名 `k8s_ai`，实例地址与凭据不入文档与仓库）。
- 需求输入：[四期需求规格（平台化）v1.16](../../01-产品与需求/03-需求文档-PRD-四期-平台化.md)、AGENTS.md、四期架构方案与代码现状
- 当前权限口径（v1.41）：平台 Permission、Session owner、namespace AuthzGrant 三层独立；user/operator 平台 Permission 默认零，自有会话属于认证基础能力；admin 对全部会话拥有完整读写与运行控制能力。
- 编号说明：本计划主线用 **P0–P6** 表示，任务编号为 `P0.1`、`P1.1` 等。P0 是规格与设计基线，P1/P2 是平台底座与 Web Shell，P3/P4 是平台能力与治理，P5/P6 是 Memory/Retention 与生产准出。任务状态表格可用于内部汇报在线表格逐格映射。
- 目标版本线：v4.0（平台底座 + Web Shell + 平台能力）、v4.1（治理能力）、v4.2（Memory/Retention），最终发布按 v1.3 §31 版本规划执行。

## 1. 范围与非目标

**范围内**

- Vue 3 + TypeScript + Vite SPA，Web 入口平台化；
- `/api/v1` API Contract、`request_id`、统一错误/分页；
- Store 抽象 + SQLite/MySQL 双驱动 + 统一 migration；
- 产品内用户与角色：user / operator / admin 三角色；平台 Permission、会话所有权与 namespace 资源授权三层分离；user/operator 平台 Permission 与资源权限均零起步，admin 按集群和 namespace 授权；
- Session / Turn / Step / SSE 事件模型；平台会话必须记录不可变 owner，并按 owner 隔离访问；
- 单集群管理、kubeconfig 上传/粘贴/校验/安全存储；
- Skill 平台：内置 Skill 完整支持、custom YAML 导入、third-party Loader/Validation Contract 预留；
- 配置中心：模型 / Skill / Approval / Memory / Retention / MCP 展示位 / 运维；
- Approval v2 平台化：审批中心、策略可视化、Authorization Grant、审批审计；
- Audit 中心：登录、Session、Tool Call、Approval、Grant、写操作、配置、Skill、集群；
- Memory：Session Summary、长期记忆、作用域、策略；
- Retention：Session / Audit / Scan / Skill Run / Memory / Config History / Credential 的清理与归档；
- 单进程部署、K8s Deployment 部署、一键安装脚本；
- 四期写执行决策：镜像内写执行统一走 client-go（推荐，待签收），不因平台化新增 shell 写通道；
- 资源创建、SSA、Approval、Code Guard、Executor 作为企业平台内部能力统一复用。

**非目标（本计划不做）**

- CLI 登录 / CLI 用户体系 / CLI RBAC；
- 多集群 Web UI；
- MCP 真实接入；
- Redis；
- 多租户 / 组织管理 / 复杂 IAM / Skill 在线市场 / Skill 远程仓库完整实现；
- 应用层手写 namespace RBAC（如手动编辑 RoleBinding / ClusterRole）：真实资源权限由平台 AuthzGrant 派生、下行到 Kubernetes RBAC 并在 API Server 强校验，不设计与应用库平行运行的独立权限体系；也不做多租户/组织管理/复杂 IAM；
- 为 Deployment、StatefulSet、Service 等逐资源新增大量写 Tool；
- 把旧 HTML 直接拆成 Vue 文件的“低质量迁移”作为主方案。

## 8. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 四期范围过大，串行推进周期长 | 迟迟不能阶段性交付 | 按 P1–P6 里程碑分版本交付；P0 先冻结 API/Store/SSE 契约；operator 角色、MCP 真实接入明确不做 |
| 平台 Chat 回归 | Web 不可用 | P2 以平台 Chat 行为完整运行为前置出口；SSE 统一契约必须由后端与前端契约测试共同锁定 |
| Skill 平台化后形成新写通道 | 突破安全边界 | D-07 架构测试锁定 Skill 不执行写；所有写仍走 Tool → Approval → Code Guard → Executor |
| 镜像无 kubectl 导致 K8s 部署写能力缺位 | 部署失败 | 容器内 client-go 统一写执行，与非容器 CLI 场景分开 |
| 平台数据迁移丢失 | 用户历史与审计不可用 | P0.6/P1.12 定义幂等升级规则；P6.8 全量迁移测试；不可迁移数据显式报告 |
| SQLite/MySQL 行为不一致 | 主备环境跑挂 | P1.2/P1.3 共用 schema；两驱动等价业务测试；迁移入口统一 |
| 权限只做前端隐藏 | 越权访问 | API 后端强校验；P4.8/P6.6 做越权专项测试；前端 Route/Component/Button 仅 UX |
| 审批/风险在平台化后被绕过 | 安全回归 | 使用平台统一 Policy；Code Guard DENY 始终优先；审批偏离高风险操作必须人工审批 |
| 自动审批覆盖高危或边界模糊（用“可逆”代替白名单） | 危险写操作被意外自动放行 | 自动审批仅限显式白名单“可自动”项；白名单外至少自确认；“需确认”项、高危类、shell 永不自动；自动化决策以 `whitelist_key` 落审计 |
| 授权撤销后集群权限未回收（平台与集群状态漂移） | 已回收用户仍可操作集群 | AuthzGrant 为唯一权威，RBAC 为派生；受管 RoleBinding 带标签/ownerReference；定时 reconcile 清除漂移与孤儿；撤销/过期即删并写审计 |
| 授权边界失效（用户操作未授权 namespace） | 越权访问他人/未授权资源 | 以 namespace 为唯一边界；执行路径同时做 scope 判定与 SAR；未授权确定性拒绝并提示联系管理员，不建审批、不阻塞等待；高危销毁类仅 admin |
| 平台进程被误调大副本 | SSE 随机丢事件、审批请求 404、重启后登录态丢失、SQLite 写冲突 | ADR-030 明确默认单副本并在清单注释说明；扩副本前置条件（MySQL + 会话/Token 持久化 + 跨副本 SSE/审批）先落地再放开 |
| Chat 存在独立未鉴权服务入口 | 会话越权、双进程认证不一致 | 平台主进程统一提供 `/api/v1/sessions*`；所有 HTTP/SSE 使用同一认证与 owner 校验；P6.11 提供同源 SPA |
| 双部署形态带来口径漂移（文档/清单/验收各说一套） | 交付与运维无法复现，客户现场踩坑 | D-26 / ADR-036 固定「默认一体化 + 可选分离」；P6.2/P6.7/P6.13 两形态同批评审；部署手册 §4.9 为唯一部署口径来源 |
| 为支持分离形态而过度改造（拆微服务/重写 API 层） | 复杂度上升、回归面扩大、违背四期范围 | ADR-036 明确最小改动边界（仅静态托管开关+静态镜像+Ingress）；超出即回到架构评审，不直接实施 |
| 平台级参数散落在命令行与 Secret（ConfigMap 只覆盖引擎参数）；动态键在文件与页面双处权威 | 部署描述被拆成三处，评审看不到全貌；改监听端口要动编排文件；文件与页面并发改同一键互相覆盖 | ADR-031 v1.11 定 `platform:` 静态段 + 7 组动态键唯一 DB settings；`config init` 只输出静态/启动键，`migrate` 仅显式一次性导入；P6.12 落地并由测试锁定模板键集合 |
| SSE 顺序与聚合契约不成文，后续任一侧改动重新引入重复报告或状态卡死 | 用户可见故障反复回归，且容易被"刷新一下"掩盖 | ADR-032 固化四条契约；后端 `TestChatServiceEventOrdering` 与前端 P2.12 契约测试双层守住 |
| 工具结果在 chat 与刷新后不一致（事件流只带 240 字截断文本、落库带完整结构化数据；耗时/风险未落库） | 用户看到的"过程"与"回看"是两套事实，排障结论不可复核 | ADR-034 固化 `tool_result` 同源契约；P7.4 落地并由后端摘要单测 + 前端渲染用例守住 |
| 前端视觉/主题按页面各写一套，后续 P3.9/P3.12/P4 页面 UI 重复返工 | 样式碎片化、亮暗不一致、维护成本持续上升 | D-23/ADR-033 定令牌与主题基线；P7.1 先落地地基，后续页面一律复用令牌，禁止写死颜色 |

### 10.2 历史视图与实时视图同构（ADR-032 第 5 条）

- **问题**：实时是「思考 → 工具 → 观察 → 思考 → 报告」，刷新后变成「工具们 → 一整块思考 → 报告」——

  `MessageTimeline.spec.ts` 新增历史顺序用例；真模型端到端实测落库顺序为
  `user → 思考 → 工具 → 思考 → 工具… → 报告`。
